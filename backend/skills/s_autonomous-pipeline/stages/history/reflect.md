# REFLECT — history and rationale
Not read at runtime. Why the REFLECT card looks the way it does, for humans and for the
evolution pipeline. Rules live in `stages/reflect.md` and `stages/ref/reflect/*.md`.
## The 2026-10 split (design `docs/design/pipeline-speed-systematic-fix.md` §4-C)
The old single-file `stages/reflect.md` (~10.9K) became a ≤5K execution card plus three
refs (`goal-mode.md`, `lessons.md`, `writes.md`). Rule IDs R-reflect-001 (the methodology
`[MUST]` heading) and R-reflect-002 (no validator-required artifact fields; every step is
agent discipline) are tagged on the card.
Changes made during the split, and why:
- **Entry/exit**: `stage-start` / `stage-complete` replace the hand-built
  `run-update --stage-json '{"stage":"reflect",...,"token_cost":...}'` record. The command
  fills `status`, `token_cost` and `stage_doc_consumed`; the record schema now requires
  `lessons` (each >20 chars), matching the completion gate.
- **Step order**: old order was 7 cultivate → 8 record → 9 learn → 10 run-report. New
  order is 7 learn → 8 record (Exit) → 9 cultivate → 10 run-report. `run-cultivate` reads
  lessons from run.json, so under the old order a lesson REFLECT added in step 1 was not
  yet recorded when cultivation ran; it only saw DELIVER's seeded set. `learn` takes its
  lessons as an argument and has no ordering dependency. `run-report --force` stays
  step 10, after the record and before COMPLETE, because `stages/complete.md` and
  `ref/complete/report-ordering.md` cite "reflect.md step 10" as the report generator
  that inlines the lessons.
- **MEMORY.md writes**: the old doc said only "Update MEMORY.md". The card and
  `writes.md` now name `backend/scripts/locked_write.py`, per the repo rule that every
  MEMORY.md write is locked (concurrent writes corrupt it).
- **Continuation block**: now says to relay `_display_block` (design §4-E) instead of
  "output the completion summary", since the summary is rendered by code.
## Why lessons are seeded in DELIVER and reused here
DELIVER writes REPORT.md and commits it before REFLECT runs. With lessons extracted only
in REFLECT, the committed audit report had an empty §9. DELIVER's "Pipeline Report" step
therefore seeds the reflect record's `lessons`, and REFLECT reuses them. A second,
different set would give §9 two sources that drift apart, which is why the card forbids
re-extraction.
## Why REFLECT regenerates REPORT.md
DELIVER generated the report before REFLECT ran, so lessons REFLECT finalized were
missing. Step 10 (`run-report --force`) regenerates the report so §9 holds the final
lessons. Since §4-A, `stage-complete --stage deliver` auto-generates REPORT.md when it is
missing, and `run-update --status completed` refreshes an auto-generated report itself
(see INSTRUCTIONS Step 6). Step 10 is kept for hand-written reports and reports that
predate the `report_autogenerated` flag, which the completion refresh deliberately skips.
## Why the continuation contract lives on this card
REFLECT issues no `advance` (it is the last stage), so nothing hands the agent a
`next_action` the way earlier boundaries do. A run that finishes its work and never
surfaces the summary is indistinguishable from one that crashed.
`tests/test_advance_continuation.py::test_reflect_doc_carries_a_terminal_continuation_contract`
pins the phrase and the COMPLETE route.
## Why checklist maintenance exists
Without it, lessons from post-pipeline reviews live in IMPROVEMENT.md but never reach
REVIEW_PATTERNS.md or the BUILD Resource Lifecycle table, the checklists that would have
caught the bug. The pipeline should learn from every review cycle.
## Why REFLECT exists at all
REFLECT closes the DDD learning loop: lessons reach IMPROVEMENT.md so future runs learn
from this one. Without it the pipeline generates value but does not compound it.
## Common rationalizations (moved from the old card)
The actionable parts are in `ref/reflect/lessons.md` § "Nothing went wrong".
| Rationalization | Reality |
|---|---|
| "Nothing went wrong — no lessons to capture" | If nothing went wrong, capture WHY. What structural decisions prevented errors? Positive lessons compound: "vertical TDD eliminated all rework" is a lesson that reinforces the pattern. Empty reflect = missed compounding. |
| "Lessons are generic — 'be careful' isn't worth recording" | Generic = sign you haven't gone deep enough. Good lessons cite: file path, line number, exact mistake, structural fix, which future scenario it prevents. "Be careful with async" → bad. "asyncio.to_thread for subprocess in async context" → good. |
| "DDD docs are fine, no update needed" | Every pipeline run generates knowledge. If nothing in IMPROVEMENT.md changed, either: (1) the run was trivial (fine), or (2) you're not extracting insights (not fine). At minimum update PROJECT.md "Recent Decisions" with this run's key choices. |
| "I'll reflect later / next session" | Reflection quality degrades with time. In-context you have the full reasoning chain. Next session you have summaries. The difference between "I traced this specific code path and found X" vs "something about async was tricky" is the difference between useful and useless. |
## Dropped as duplication
- Nothing substantive was dropped. INSTRUCTIONS.md's REFLECT section (Step 5, "Execute
  the 9-step methodology") and Step 6's completion-gate list already describe the gate
  conditions; the card restates them in one line each rather than copying the prose.
