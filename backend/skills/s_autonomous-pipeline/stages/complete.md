# COMPLETE Stage — Output Format Spec

Pipeline-owned stage (no sibling skill). This is the **terminal output** of every
pipeline run — the code-rendered delivery summary (`_display_block`, relayed verbatim)
plus one ```next-steps block. Nothing else is written to chat after it.

> **Why this is a fresh-read stage doc (read it AT Step 6, not from memory):**
> Every other stage (evaluate…reflect) reads its `stages/<stage>.md` at the moment
> it executes, so the spec is fresh in the reading path at the decision point.
> COMPLETE used to be the ONE exception — its format lived ~750 lines deep inside
> INSTRUCTIONS.md, far past the file-head execution entry, so by the time a run
> reached COMPLETE the spec had decayed out of the attention window (F004) and the
> completion summary silently "disappeared." This doc fixes that: Step 6 reads it
> fresh, exactly like the other stages.

This doc owns the format ONLY. The COMPLETE mechanics (run-report, run-update
`--status completed`, the mechanical completion gate, and the final STOP) stay in
INSTRUCTIONS.md Step 6 — read both.

---

## Step 0: Surface this run's changes to Canvas (MANDATORY — before the summary) `[GATE·artifact_cli]`

> The `outputs_surfaced` step is code-enforced for source-committing runs: if this run
> committed run-scoped source and you skip surfacing (step 2/3), `run-update --status
> completed` BLOCKS (see the "GATED" note below). A knowledge/docs-only run is exempt.

> **⛔ ORDER PREREQUISITE: `run-report` MUST run BEFORE `surface_run_outputs`.**
> `surface_run_outputs` appends the run's `REPORT.md` as the LAST OUTPUTS row (kind=knowledge)
> so the Canvas auto-SELECTS + renders the report — but ONLY if `REPORT.md` already exists on
> disk at surface time (`build_surface_events` is exists-guarded: no file → the report row is
> silently skipped, and the finish batch auto-opens on a source file instead of the report).
> Step 0 sits at the TOP of this doc, so a top-to-bottom reader could surface BEFORE any report
> exists and lose the report row. **Therefore: REPORT.md must already be on disk before you call
> `surface_run_outputs` here.** The ONLY doc that actually invokes the generator is
> `reflect.md` step 10 (`run-report --force`, which also inlines the lessons) — `deliver.md`
> contains a report TEMPLATE but no `run-report` call, so do not rely on DELIVER to have
> produced it. If REPORT.md is absent, run `run-report` explicitly before surfacing.
>
> Note the report is NO LONGER generated by an explicit `run-report` call in INSTRUCTIONS Step 6.1:
> that step now runs `run-update --status completed` FIRST (so `completed_at` exists and the
> report's `Duration:` is real, not `N/A`), and the completion branch regenerates the report
> itself — **but only when it is AUTO-generated** (`report_autogenerated`). A hand-written
> report, or one predating that flag, is deliberately left alone and still needs an explicit
> `run-report --force`. This note is about the SURFACE dependency, which is unchanged.

Stand on GIT — surface WHAT THIS RUN CHANGED to the Canvas review panel. Do this
BEFORE `run-update --status completed` (INSTRUCTIONS Step 6.1 — it is gated on
`outputs_surfaced`, and the delivery summary it returns links the same files). Full behavior +
rationale in `stages/deliver.md` § "COMPLETE-stage Canvas review"; the sequence:

```bash
python backend/scripts/artifact_cli.py run-surface-changes
# → {"content":[...], "knowledge":[...], "source":[...], "process":[...]}
```

1. **content + knowledge** (DDD / design docs / MEMORY / KNOWLEDGE) → these already
   surfaced IMMEDIATELY as they were written (per-change rail rows — no action needed;
   `run-surface-changes` just confirms them). This is the immediate-trigger regime.
2. **source** (code) → surface the run's committed coding files as a PR-review BATCH of
   rail rows. Call the `surface_run_outputs` tool ONCE with this run_id;
   the backend emits one OUTPUTS row per committed file (kind=source-final), each
   openable as that file's changes (a local-PR review experience):
   ```
   ui_action-style tool:  surface_run_outputs   run_id=<run_id>
   ```(Mid-run coding edits are NOT displayed; only this finish batch. There is NO LOCAL_PR.md — removed ; the per-file rows ARE the deliverable.)
3. **Record it** — `run-update --stage-json '{"stage":"deliver","status":"completed","outputs_surfaced":true,...}'`.

**GATED:** if this run committed run-scoped source (commits ∩ files_touched) and you
skip step 2/3, `run-update --status completed` BLOCKS. A knowledge/docs-only run (no
source commits) is not gated — skip steps 2-3, still do step 1.

## Output the delivery summary to chat (MANDATORY — never skip) `[MUST]`

The summary is RENDERED BY CODE from recorded data — intent (the user's own words),
final requirements, real token cost, runtime, added/modified files with links that
open in Canvas (modified files open against their pre-run base), quality and the
REPORT.md link. Design: `docs/design/pipeline-speed-systematic-fix.md` §4-E.

1. `run-update --status completed` returns it as `_display_block`. If you lost it,
   re-render: `python backend/scripts/artifact_cli.py run-summary --project <P> --run-id <R>`.
2. Output `_display_block` **verbatim** — no retyping, no reformatting, no code fence
   around it (a fenced block makes the file links unclickable).
3. Then add 2-3 next steps the user would type next, in a ```next-steps block (the chat
   renders them as clickable chips).
4. STOP — nothing after the ```next-steps block (no recap, no "shall I push?"). The
   stage-by-stage process view (①–⑩), decisions and lessons live in REPORT.md, which
   the summary links to — do not repeat them in chat.
