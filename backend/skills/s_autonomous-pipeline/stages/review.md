# REVIEW

Dispatch exactly the `handouts` of `"$SWARM_BACKEND_BIN" pipeline-v1 review-start --project <P> --run-id <R>` in one parallel message, foreground, each `prompt` unchanged (a changed prompt is not counted). If `next.why` says a spawn or answer was rejected, dispatch that handout's `spawn_prompt` again.

Who is dispatched is decided by the engine, not by you:
- correctness for a change of 50 or more source lines, with the rows of each repo's `.swarmai/review.md` pattern table the change triggers (read at the run's base; a run cannot change its own review);
- security only when the change is declared security-relevant: a matching `security:` line in `.swarmai/review.md`, `"risk": ["security"]` in your BUILD report, or a design that names security boundaries. There is no built-in path or API rule. At 50+ lines its handout starts with a HIGH-RISK CHANGE line (there is no second security reviewer);
- nobody for a small or docs-only change unless one of these requires it.

R1 reviews the complete diff. Collect the whole round, cluster by cause, fix once, and record it with `"$SWARM_BACKEND_BIN" pipeline-v1 review-address --project <P> --run-id <R> --artifact <handoff.json>` (findings within ±10 lines are one cluster; it names any you left out). Its returned handouts are the complete R2 roster: dispatch them together. R2 only rechecks the addressed findings of the experts that reported them.

A behavior/contract fix is proven by a test you ran: record it with `"$SWARM_BACKEND_BIN" pipeline-v1 report-tests --project <P> --run-id <R> --artifact -`, then give the item `"proof": {"evidence_type": "reported_test", "command": "<the command as in that report>"}`. It must pass on the current code; R2 judges whether it shows the fix (ADEQUATE / TEST_INADEQUATE). For docs/design/security-policy or refuted findings, call `"$SWARM_BACKEND_BIN" pipeline-v1 review-proof --project <P> --run-id <R> --artifact <proof.json>` where the file is exactly `{"pass": <n>, "proofs": [...]}` and each row is `{finding_id, evidence_type}` (`diff_assertion`) or `{finding_id, evidence_type, refs}` (`refuted`, concrete `path:line` refs); `pass` is the 1-based proof pass; the engine derives every tree and diff fact. A diff_assertion is judged on the finding's own file; when the fix of a docs/design/security-policy finding landed in other files (a boundary written into a design document), give its review-address item `"fix_files": ["<path from the repository root>", ...]`: R2 is shown those files' diff and the assertion checks them.

Rounds are counted per visit: the first visit, and each time TEST or a landing sends the run back to REVIEW (that visit's first round is an incremental review of the change since the last review). A visit has one fixing pass and its R2. If a HIGH / CRITICAL this visit raised is still open after that R2 (OPEN, TEST_INADEQUATE, or new in R2), one more pass may address those findings and their ±10-line cluster, then one more R2. After that the visit's review is closed: every other open finding is a residual risk listed in the REPORT, `review-address` with items is refused, and `findings` / `next` say "residual" instead of "fix it". Do not change code after the review closed: no review would see the change, so it cannot land; `next` gives the command that restores the reviewed code. A change that must still happen goes in TEST, which opens a new visit.

If an expert's first-round answer could not be read, `next` says `review-start` before anything else: it asks that review once more, with the parser's reasons. A second unreadable answer is not asked again; the review checks decide.

RV-4: REVIEW completes only on code a review round saw. RV-5: every addressed finding reached an R2; `review-address` with `"items": []` dispatches a missing R2 or re-asks a wrong R2 word once. `pipeline-v1 findings` (same `--project`/`--run-id`) lists each finding's id, status and `close_with`; `next` lists the open ones. Audit checks: RV-1a, RV-2: an unresolved HIGH/CRITICAL finding is one line in the audit's Quality cell and does not block landing; MEDIUM/LOW are residual risks. No extra experts, no third round.

Complete with `"$SWARM_BACKEND_BIN" pipeline-v1 stage-complete --project <P> --run-id <R>` and continue.

A valid example of this stage's document, with placeholders for your own values: `"$SWARM_BACKEND_BIN" pipeline-v1 template review_address`.
