# BUILD

Input: the DESIGN_SPEC tasks and exit criteria (direct: the requirement given at create; it has no DESIGN_SPEC).

Write and test the change your own way, in the run's worktree, with the repo's own commands. The pipeline does not say how. If a dependency is installed in editable form from the main checkout (an editable Python install, an npm/yarn link), code run in the worktree can load the main checkout's copy: start the tests from the worktree's own source directory or install the environment in the worktree, and give that directory as `cwd`.

End BUILD with your validation report on stdin: `"$SWARM_BACKEND_BIN" pipeline-v1 stage-complete --project <P> --run-id <R> --artifact -` with `{"reports": [{"repo", "commands": [{"command", "cwd", "result": "pass|fail|not_run|pre_existing", "reason"}], "tests_changed", "rationale", "risk"}]}`, one report per repo. Every result but `pass` needs a reason. `pre_existing`: the command fails the same way on the run's base (red before the run); check it there with `"$SWARM_BACKEND_BIN" pipeline-v1 base-tree --project <P> --run-id <R> --repo <name>`, which prints a directory holding the base's files, and run the command there. Like `not_run` it does not stop the stage; the REPORT lists it apart. A judgment call made while building (a deviation from the plan, a choice the plan left open) goes in the report's optional `decisions` list, in the shape PLAN uses; the REPORT lists it under Decisions. Add `"risk": ["security"]` when the change touches authentication, permissions, input validation, credentials, network, file paths or shell commands: it dispatches the security review (nothing else infers it). The pipeline does not rerun anything: review judges whether the report is enough.

Required check: BX-3 (a change exists, and every repo has a BUILD report on its current code tree).

A valid example of this stage's document, with placeholders for your own values: `"$SWARM_BACKEND_BIN" pipeline-v1 template validation_report`.

## Using the person's Hives (a Swarm Run, optional)

When parts of the change stand on their own and are large, you may hand them to the person's Hives as children of this run and keep what you judge good. Everything about them is yours to decide: whether to split, how, which execution each gets, whether to trust a result, whether to correct it, take it over or drop it. What lands is still only this run's own change, through its own REVIEW and TEST.

1. Split into work packages that stand alone (each task text complete: nothing from this conversation, no path on this machine), each with its acceptance, what comes back and the packages it waits for (`after`). Packages that would change the same files: make them one, or first write the contract yourself (interfaces, stubs, a failing test) and give the children `"base": ["@worktree"]` so they start from it. Cannot be split: do not fan out.
2. Write the plan and dispatch what is ready: `"$SWARM_BACKEND_BIN" pipeline-v1 child plan --project <P> --run-id <R> --file -` with `{"children": [{"wp", "title", "task", "acceptance", "execution", "returns", "why", "after", "base"}]}`, then `"$SWARM_BACKEND_BIN" pipeline-v1 child dispatch --project <P> --run-id <R> W1 W2`. Say the split in your reply as you dispatch, for the person to see: one line per package with what it asks, its acceptance, what comes back and what it waits for, and why you split it this way (the Swarm Run card in the chat shows the packages' rows and states; what each asks and why is yours to say). Say each later decision on a child the same way, in a line: taken, corrected and why, taken over, dropped.
3. Wait: end your turn; the run is woken when a child changes. `"$SWARM_BACKEND_BIN" pipeline-v1 child status --project <P> --run-id <R>` shows them; a child's wait you answer with `child card` then `child answer`, or `child escalate` when only the person can.
4. Review each result as its risk needs (read the commits in `refs/hive/...`, or send the review experts as for your own change).
5. For each: take it (`"$SWARM_BACKEND_BIN" pipeline-v1 child merge --project <P> --run-id <R> <dispatch>`, then `child accept <dispatch> --ended-at <its result's ended_at> --why ...`), correct it (`child rerun` for a native child, `child dispatch --again <wp> --note-file -` for a pipeline one), take it over, or `child discard`. Correct it when the fix is small and the child still has its context; take it over when it conflicts with another child, the correction is hard to say, or the budget is nearly used (one package goes out at most three times).
6. `"$SWARM_BACKEND_BIN" pipeline-v1 child apply --project <P> --run-id <R>` lays the merged children into the worktree, keeping your own edits; then finish BUILD as above.
7. In the delivery summary say what each child was used for, what you corrected or took over, and anything left undone.
