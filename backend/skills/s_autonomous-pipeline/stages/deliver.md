# DELIVER

Write `artifacts/reflect.json` through `"$SWARM_BACKEND_BIN" pipeline-v1 reflect-prepare --project <P> --run-id <R> --artifact <json>`, then land. The report's keys are `delivered`, `decisions`, `corrections`, `practices`, `gaps`, each a list (any may be empty or left out; a `lessons` list is refused). An invalid entry is dropped and named in the reply's `dropped` (the rest is kept; shape: `pipeline-v1 template reflect`); REFLECT never blocks landing. Each row is one unit with no other keys:

- `delivered`: what the run produced, as `{"kind": "event", "when", "title", "what", "impact" or "outcome"}`, or a cognition unit. An event may add `"closes": [<gap id>, …]`: the `open_gaps` of `pipeline-v1 events` that this run fixed, with `outcome` saying how each was fixed. Name only gaps the landed code fixes; other ids are dropped. When the run lands, CDF withdraws those gaps and records which run closed them; a run that does not land closes nothing. Events follow its `event_rule`; one in its `timeline_events` adds `"same": "<ref>"`.
- `decisions`: `{"kind": "cognition", "type": "decision", "scope", "title", "what", "why", "rejected_alternatives", "applicability"}` (`none` when there was no alternative). Every cognition row has `applicability`: when it applies.
- `corrections`: cognition of `type` `correction` or `pitfall`.
- `practices`: cognition of `type` `guideline` or `process`.
- `gaps`: `{"kind": "gap", "gap_kind": debt | risk | deferred_finding | process_issue, "scope", "title", "what", "proposed_next"}`: the concrete next step.

Every row's `evidence` cites this run's anchors: the `anchors` of `"$SWARM_BACKEND_BIN" pipeline-v1 events --project <P> --run-id <R>`. `scope` says where it belongs: `project:<P>` (its DDD, or the repo's shared file when the project has none), `world`, or `user`. A cognition unit that replaces an existing entry of the project says so in `overrides`: `["<8-character id> | <the entry's first line, copied>"]`, the id as `cognition find` / `get` printed it. CDF retires that entry once the unit is written, only if the id and first line name exactly one entry CDF wrote and this run said it later; a replacement that is only related is not an override.

Normal landing evaluates RF-1–RF-4 and LG-1, LG-3, LG-4 (LG-1: the TEST report is on the landing tree and the change is the reviewed one). If main moved without touching the run's files, the report stands; otherwise test the synced tree and send it with `"$SWARM_BACKEND_BIN" pipeline-v1 report-tests --project <P> --run-id <R> --artifact -`. On a merge conflict, resolve it in the run's worktree and `land` again (it continues the rebase); main moving or conflicting never uses up the run's three landing failures. A change that differs from the reviewed one (a conflict resolution, an edit in DELIVER) goes back to REVIEW once for an incremental review of that difference (only doc-class files: REVIEW completes itself); after that a further difference lands and the REPORT says no review saw it. No push verdict: an open audit check is one line in the REPORT's Quality cell and never blocks landing; pushing is the user's call.

The renderer creates REPORT before commit-tree. Do not hand-edit `.aidlc/deliverables/<run_id>/REPORT.md`.

Run `"$SWARM_BACKEND_BIN" pipeline-v1 land --project <P> --run-id <R> --message <message>`. The engine computes code_tree, the open audit checks, land_intent, the REPORT, delivery_tree, the LG checks and commit-tree in a fixed order, and never pushes. On a deterministic not-landed result continue to REFLECT and report the reason.

A research run lands nothing: after `reflect-prepare`, finish with `stage-complete` (it ends `no_code`).

For an abandoned, paused, or completed-not-landed run, use the explicit recovery commands: `resume`, `restore`, or `run-land --prepare`. `run-land` is yours, like a native commit, in two steps: prepare returns a request ID; then run `"$SWARM_BACKEND_BIN" pipeline-v1 run-land --project <P> --run-id <R> --request <request-id> --message <message>`. `run-land --prepare` takes `[--skip-tests] [--note ...]`. Give it as ONE command: it is recorded as yours, bound to session, run and request; the landing rechecks every tree. A failed action consumes the authorization: prepare again. Snapshot deletion and finding acceptance ask the person. Abandoned and not-landed work keeps its `run/<id>` branch, bundle and diff. When an abandoned run's change landed outside the pipeline, record it: `"$SWARM_BACKEND_BIN" pipeline-v1 landed-as --project <P> --run-id <R> [<repo>=]<commit>` (or `abandon ... --landed-as [<repo>=]<commit>`); the commit must be on the integration branch and carry the run's reviewed change, and the run then needs nobody. When the engine cannot show that (the commit differs, or the run predates reviews recording their base), `landed-as ... --prepare [<repo>=]<commit>` writes a one-use request with what the engine found and `landed-as ... --request <request-id>` records it.
