## TL;DR
**解决了什么问题**
- 原来：A turn lived inside the POST /chat SSE request: dropping that connection interrupted the CLI and a synthetic auto-continue prompt re-drove it, and every turn not started by a POST (pending drain, CLI-injected, channel, answer/permission continuation) reached the tab only through 3-15s polling or a DB reload, so short turns never showed a spinner and content appeared late or out of order.
- 现在：Every turn is owned by its session and published through one hub with a per-session sequence number; the desktop window holds one subscription that renders every turn of the sessions shown in tabs live, replays what it missed after a reconnect (the active turn from its start), and a disconnect never stops a turn. POST is a fallback only while the subscription is down; busy-polling and auto-continue are deleted.

**怎么做的**
- SessionEventHub: per-session eventSeq, replay ring, active turn kept whole, epoch, resync naming the active turn
- SessionRouter._published_turn wraps all four turn entry points (turn_start/turn_end, server client_id for keyless turns)
- sse_with_heartbeat detaches the consumer on disconnect instead of cancelling the turn; auto_continue and disconnect recovery removed
- GET /api/chat/events: one stream per window with cursors and epoch
- Frontend: sessionEvents client (watch/join/hello baseline) + pure sessionTurnRouter (ownership, dedup, rebuild on resync, single render source)

## 1. Requirement
The desktop chat must show what the backend is doing as it happens. Today the backend has no channel to push events to a tab outside a user-initiated POST /chat SSE stream, so anything that happens outside that stream reaches the UI only via polling (GET /streaming-state every 15s idle / 3s streaming) or a DB reload (tab switch, window focus, next send). Known instance: CLI-initiated (injected) turns landed in 17b14358 — a short one that starts and ends between two polls never shows a spinner and its content appears only on a later reload, so the UI is stale and misleading. XG: unacceptable, streaming loses its meaning. Systematically inventory EVERY similar case (backend state/events that change outside an active POST SSE stream: injected turns, pending-queue drains, post-disconnect flush/recovery, self-heal respawn, compaction, permission/ask-user requests, background-task progress, eviction/cold, sibling session writes, channel sessions), measure which reach the UI late or wrong, and fix the root: one per-session live event channel the frontend subscribes to (ACP session/update, Codex thread subscribe pattern) so polling/reconcile becomes a safety net, not the delivery path. Out of scope: Slack/channel forwarding of injected turns (record as known issue).

## 3. Design & Approach
**Research Findings (THINK):**
- Every turn's events are produced by an async generator (router.run_conversation / continue_with_answer / continue_with_cmd_permission, and unit._read_formatted_response for injected turns) that the CALLER drives: for desktop turns the caller is the POST SSE response (routers/chat.py:499/:675/:1483), so an SSE disconnect raises GeneratorExit/CancelledError inside run_conversation (session_router.py ~:4380 comments) and the turn dies with the request.
- Background turns (drain_pending session_router.py:3269, auto_continue.py:105, run_injected_turn :3114, channels/gateway.py:1913/:2040) drive the same generators but nothing receives their events live; only _persist_stream_event (:2163) writes complete assistant messages to the DB.
- The frontend renders a turn through createStreamHandler(assistantMessageId, tabId) (useChatStreamingLifecycle.ts:2331) fed by consumeSSEStream (services/chat.ts:277); the handler is source-agnostic (it takes StreamEvent objects), so a second source can feed it unchanged.
- A subscribe pattern already exists for tasks (routers/tasks.py:212 over task_manager.subscribe, task_manager.py:415: register queue, replay buffer, then live) but has no sequence numbers, so a reconnecting client cannot resume without duplicates or gaps.
- The frontend has one rescue per background source (busy-poll ~:3498, B1 drain surface ~:1475, symmetric re-arm ~:1532, pendingQuestion mirror ~:1440, force-clear) and the backend has disconnect recovery (chat.py:49) + auto_continue; all exist only because there is no session-owned subscribable stream.

**Alternatives Evaluated:**
- SPEED — effort: S
- QUALITY — effort: L
- SIMPLICITY — effort: M

**Chosen Approach:** Session-owned turns and one subscribable session event stream. Backend: a new SessionEventHub (core/session_events.py) assigns each session a monotonically increasing eventSeq and keeps a bounded per-session replay buffer plus per-subscriber bounded queues (register-then-replay, like task_manager.subscribe). The four router turn generators (run_conversation, continue_with_answer, continue_with_cmd_permission, run_injected_turn's loop) go through one wrapper that stamps every event with sessionId/turnId/turnClientId/eventSeq, publishes it, emits turn_start/turn_end, and closes the inner generator with aclosing. New GET /api/chat/events streams all sessions to one window with per-session cursors, an epoch hello and resync. sse_with_heartbeat detaches the consumer on client disconnect instead of cancelling it, so the turn runs to its own end; the disconnect interrupt (_recover_streaming_on_disconnect, _cleanup_subprocess_after_disconnect) and core/auto_continue are deleted. Frontend: services/sessionEvents.ts keeps ONE subscription per window (reconnect with cursors, epoch check, stall timeout on missing heartbeat); hooks/sessionTurnRouter.ts is a pure router that makes the subscription the single render source (POST turn events are dropped while it is connected and rendered only as a fallback while it is down, with an eventSeq gate for the switch), buffers subscription events while a POST send is unbound, begins a subscription turn for a tab with no active turn (placeholder id = turnClientId, existing message reused), completes each turn once (turn_end or POST complete), and turns a POST transport loss into a detach while the subscription is connected. useChatStreamingLifecycle wires it; polling reconcile stays as the safety net. The detached sse_with_heartbeat consumer stops queueing (drains and drops) so nothing grows unbounded. Deleted in this run: core/auto_continue.py and tests/test_auto_continue.py; chat.py _recover_streaming_on_disconnect, _cleanup_subprocess_after_disconnect, their 3 calls and the mark_user_stop call in stop_session; run_conversation's _auto_continue kwarg and its :3581 branch; the busy-poll DB loop. Kept for the follow-up (production readers remain): SessionUnit.recover_from_disconnect/schedule_pipe_flush/is_post_disconnect_flushing (read by eviction guards session_router.py:2902/:3633 and the streaming-state field chat.py:935 + frontend postDisconnectUncertain), B1 drain surface, symmetric re-arm, force-clear. Tests rewritten: test_sse_disconnect_chain.py (disconnect now detaches), test_session_release.py (comment/assert on the deleted recovery). task_manager/skill_creator/gateway turns are published too (the wrapper is in the router); only a desktop tab mapped to that session consumes them.

**Success Criteria:**
- backend: a POST client disconnect leaves the turn running to its result and persisted (test asserts no interrupt and a persisted assistant row)
- backend: injected, drained, answer-continuation and channel turns publish turn_start, their events and turn_end with strictly increasing eventSeq (tests)
- backend: GET /api/chat/events replays after a cursor, sends resync for a cursor older than the buffer, and an epoch hello (tests)

- frontend: tsc + targeted vitest green; backend targeted pytest + regression green

**Always:**
- every event of every router turn passes the single publishing wrapper
- dedup by per-session eventSeq before any render
- a turn completes in the UI exactly once
- existing polling reconcile stays functional as the safety net

**Never:**
- one long-lived stream per tab (WebKit per-host HTTP/1.1 connection cap)
- interrupting a turn because a client disconnected
- unbounded subscriber queues
- re-sending a user message from the frontend to recover a turn
