Stop the DDD archive from re-appending the same entries every lifecycle run. Observed 2026-10-20: the 9 projects' *-archive.md files total ~82MB but hold only ~407 distinct entries (SwarmAI 2-understanding/IMPROVEMENT-archive.md: 41.5MB, 116,194 bullets / 269 distinct; one entry appears 1,375 times). Never delete archive content. Out of scope: removing the dead ref counter, title truncation, MEMORY writer bugs, one-time de-dup of the existing archives.

## 3. Design & Approach
**Research Findings (THINK):**
- The decay pass in core/ddd_orchestrator.py:926-941 is the only archive_entries caller that never strips what it archived; reclaim_noise_entries (_archive_and_strip, key strip) and reclaim_duplicate_entries (line strip, ddd_entry_lifecycle.py:1634-1646) both strip.
- parse_entries gives every entry its 0-based line_number on the same content the decay pass later rewrites (ddd_entry_lifecycle.py:629); the decay pass never changes content between parse and archive, so line numbers are exact handles.
- Live IMPROVEMENT.md files hold 36 duplicate (title, section) keys (SwarmAI 26, AIDLC 5, ai_ready_repo 4, GitHub_Community 1); a (title, section) strip would remove a twin that was not archived, so the strip must be by line.
- archive_entries writes raw_text then a metadata line starting '  <!--' (ddd_entry_lifecycle.py:1044-1047) and raw_text never contains the metadata line, so 'raw_text followed by a metadata line' identifies an already-archived block exactly.
- The MEMORY/KNOWLEDGE/EVOLUTION decay paths in hooks/context_health_hook.py deliberately avoid archive_entries; they are not affected.

**Alternatives Evaluated:**
- QUALITY — effort: S
- SIMPLICITY — effort: S
- DELETION — effort: S

**Chosen Approach:** Make archiving a move in one place. (1) Extract archive_raw_lines' content_signature dedup into a shared helper and apply it in archive_entries for every caller (idempotent append, intra-batch too). (2) Add a line-precise archive+strip helper (archive_entries then _strip_entries_by_line, returns the stripped content, does not write) and use it in reclaim_duplicate_entries and in the orchestrator decay pass. (3) The decay pass strips the archived blocks from content first, then injects metadata for the surviving entries into the stripped content, then writes once.

**Success Criteria:**
- new tests fail on current main and pass after the change
- test_ddd_entry_lifecycle.py and test_ddd_orchestrator.py pass

**Always:**
- archive before strip; never strip an entry that was not archived
- strip by line number

**Never:**
- delete or rewrite existing archive files (the one-time dedup is a separate data step)
- touch the MEMORY/KNOWLEDGE/EVOLUTION decay paths
