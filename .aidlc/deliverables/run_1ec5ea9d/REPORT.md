## TL;DR
**解决了什么问题**
- 原来：Every DailyActivity writer appended: one session left dozens of checkpoint blocks a day (each listing the workspace's own auto-commits), repeated summaries and crash copies; file names were tokenizer junk (null, n, *.py); the capture hooks recorded system-injected preambles as user text. 2026-10-20: 312 blocks, 249 of them checkpoints.
- 现在：One writer: a session has one checkpoint and one summary block per day, moved to the end on every rewrite, under one hidden lock with atomic rename; the JSONL sidecar keeps one record per session; the checkpoint lists no workspace commits; file names come from the bash write-target parser; capture and correction hooks see only typed text, with block shapes shared by the builders. Replay on today's real file: 30 checkpoints + 3 summaries leave 1 + 1 blocks and 1 record, legacy text unchanged.

**怎么做的**
- Marker-delimited per-session blocks upserted by daily_activity_writer.upsert_session_block
- One hidden .DailyActivity.lock for every writer (incl. distillation mark, memory-health note, crash recovery)
- core/injected_blocks.py holds the resume/recall/UI/terminal/notification shapes; session_router, prompt_builder and run_delivery_summary import them
- Startup backlog skips a session only once its summary exists

## 3. Design & Approach
**Research Findings (THINK):**
- Four writers append to the day file with no session identity: daily_activity_writer._atomic_read_modify_write (post-session summary, appended on every hook run and counted as a new session each time), runtime_hooks.create_session_checkpoint (plain open('a') every 10 tool calls when files or SwarmWS commits grew), hooks/daily_activity_hook.recover_crash_checkpoint (plain append), runtime_hooks.create_high_signal_capture (plain append, multi-line prompt[:500]). The JSONL sidecar is appended per summary too.
- The checkpoint's git activity comes from git log in SwarmWS, whose commits are the workspace auto-commit hook's own snapshots (574 chore / 274 framework / 35 content / 11 project subjects in 14 days, 2 hand-written). The post-session summary already takes git ground truth from the source repos named in TECH.md, so the checkpoint's SwarmWS git lines are pure noise and the main reason it rewrites.
- Junk file names come from SummarizationPipeline._extract_files_modified: a hand tokenizer keeps any '/'-bearing token of a 'Running:' summary (so 2>/dev/null -> 'null', sed expressions, globs); the summary is cut at 200 chars, so the last token can be a fragment. core/file_change_classifier.parse_bash_write_targets is the SSOT write-target parser the file tracker already uses and returns [] for /dev/null and anything unconfident.
- Prompt-reading hooks see the whole query: cold resume prefixes the RESUMED block (header/footer constants in session_router), warm reuse prefixes the recall block ('## Recalled Knowledge' + provenance + agentic hint ending 'broader terms.)_') and the UI-state block ('## Current UI State' ... first blank line). runtime_hooks._strip_injected_prefix exists but only knows UI-state / task-continuation / SYSTEM NOTE shapes and is used only for language classification; run_delivery_summary._META_PREFIXES names the same shapes again.
- DailyActivity readers (prompt tail injection, proactive_intelligence session counting by '## ..|' headers, knowledge_fts, distillation JSONL + md fallback) do not parse HTML comments, so a comment marker line around a block is invisible to them.
