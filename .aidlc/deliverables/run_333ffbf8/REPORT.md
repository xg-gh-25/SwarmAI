## TL;DR
**解决了什么问题**
- 原来：When a background command or subagent finished, the CLI started a turn of its own that nobody read: invisible in the tab, and its first tool call waited until the user's next message (14 days: 36 such turns, 10 stalls of 103 s to 75 min).
- 现在：One reader per CLI process reads its output for its whole life: the CLI's own turn runs immediately, is saved to the session as 'injected', and the tab shows streaming while it runs; a message sent meanwhile is queued and delivered when the CLI is idle; a CLI that dies between turns is respawned with --resume instead of looking busy.

**怎么做的**
- CliStreamReader: claim-before-write per user turn, matched at init or by the replayed uuid echo
- send()/compact() write only when the CLI is quiescent; otherwise the message becomes pending
- the router's sink persists CLI-initiated turns through the existing _read_formatted_response + _persist_stream_event
- reader death and abandoned turns route into the existing respawn / pending paths, identity kept

**遗留问题**（24 条，见 §10）

## 3. Design & Approach
**Research Findings (THINK):**
- F1 SDK reader (claude_agent_sdk/_internal/query.py:388-505): one loop dispatches control_request then `await send`s every other frame into a 100-slot stream (:229-231); with no consumer it parks and hooks go unanswered. Even without partial messages a turn emits 15-25 thinking_tokens frames (spike).
- F2 the daemon reads the stream in 4 places only: streaming_orchestrator.py:1352 (user turn), :3059-3060 (leak continuation), :1134 (_interrupt_draining reuses the turn iterator), session_unit.py:4537-4541 (compact).
- F3 spike (bare SDK, real CLI): a CLI-initiated turn is TaskNotification → state{running} → init → frames → Result(origin.kind=task-notification) → state{idle}; a user message written while that turn is in a tool loop is folded into it (one Result, origin task-notification); with extra_args replay-user-messages the CLI echoes our message with our uuid exactly where it consumes it; a background agent's notification can arrive inside a user turn and the injected turn starts right after its Result with no idle; --resume starts with state{running} + init; a stopped task at idle produces no turn but re-emits state{idle}.
- F4 a turn nobody started from the daemon already has a display path: drain worker turn (session_router.py:3087-3175) + streaming-state poll arming the spinner (streaming-guards.ts:289) + MessageStore DB reconcile; busy sends become pending rows (session_router.py:3450-3470, 3525-3545).
- F5 orchestrator's UserMessage branch only acts on ToolResultBlocks (streaming_orchestrator.py:1920-1950), so a replay echo is harmless if it leaks, and TurnStream can swallow it anyway.
- F6 is_protected (session_unit.py:1178-1183) covers only STREAMING/WAITING_INPUT; eviction of an IDLE unit kills a running background task.

**Alternatives Evaluated:**
- QUALITY — effort: L (one run, ~6-8 files)
- SPEED — effort: M
- DELETION — effort: S

**Chosen Approach:** Continuous reader per SessionUnit (design v2 §4) with claim-at-init for the normal path and echo transfer only in the notification race; injected turns persisted by a router sink through _persist_stream_event; quiescence gate in send(); background-work guard at 4 reclaim sites. Fallback to receive_response when no reader exists keeps the 19 fake-client test files valid (strangler step; removed in the follow-up run).

**Success Criteria:**
- test_cli_stream_reader.py and test_session_injected_turn.py pass
- the 19 receive_response test files pass unchanged
- a real-CLI probe: background sleep finishes with no send and the follow-up turn's tool runs within 5 s and its rows are in the DB

**Always:**
- claim before query
- one consumer per SDK stream
- frames of a turn go to exactly one stream except the logged merge case

**Never:**
- read client.receive_response() where a reader exists
- write a user message while the CLI is not quiescent
- drop a pending message
