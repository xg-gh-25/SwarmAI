# Pipeline 评审收敛：修复循环的系统化方案

> **范围**：REVIEW 和 DELIVER Gate-2 中「发现 → 修复 → 再审」这个循环。不改评审标准，不减首轮 reviewer，不放宽任何 gate。
>
> **不在范围**：并行 session 的提交隔离（worktree 模式已实现，默认关闭）、单步模型延迟、测试机负载。

## 0. 一页摘要

| 机制 | 解决什么 | 怎么解决 |
|---|---|---|
| N1 行为基线 | 修复把 HEAD 原本正确的行为改坏了，或者匹配范围多了/少了，几轮之后才由 reviewer 碰巧发现 | 第一次修复之前，工具先冻结一个可执行的基线：AC 测试、每个反例的回归测试，以及（对替换行为的改动）HEAD 和改动后的版本在同一个输入语料上的差分。每次修复都必须保持基线全绿。修复的 hunk 由工具反向变异，对应的测试必须变红。两个条件都满足后才生成复核 prompt |
| N2 复核看改动，不看严重度 | LOW 级修复、没给置信度的风险修复不进复核，后来引出阻断问题；「是否阻断」有两套判定 | 只要有修复改动的代码，就要交给负责该区域的 reviewer。非阻断问题不在循环里修，记进 REPORT §10 和完成总结。「阻断」只保留一个判定函数，所有读者共用 |
| N3 终止规则 | 补丁循环没有终点，`over_budget_reasons` 只记理由、照样继续 | 一轮复核没有新的阻断发现，就判定为收敛（沿用 G2 的语义）。第 3 轮还没收敛，由系统做根因复盘：方案对 → 剩余项进 REPORT、本地 commit；方案根上错了 → 自动退回 PLAN 重设计一次。不交给人 |
| N4 发现台账 | 模型从 reviewer 的回答里手抄 findings；recheck 会把已经 RESOLVED 的 reviewer 也重派 | 台账由工具从 hook 已捕获的回答直接生成，合并重复条目。路由规则：只派还有待复核条目、或者负责区域被新修复改过的 reviewer |
| N5 一套引擎 | REVIEW 的 spec-compliance 也会多轮不收敛 | REVIEW 的复核共用 N1–N4 |

另有一个前置决定，不在本方案范围内：打开 worktree 隔离。`run_d8762bc8` 的 7 轮里有 2 轮是共享 checkout 造成的。

## 1. 证伪结果：v1 哪里错了

v1 认为根因是「修复只对着触发它的那一处验证，没检查其他读者」，主要机制是用工具算读者清单（code-intel + 字段 grep）。skeptic 逐条分类了两个慢 run 在第 2 轮及以后的阻断发现。

**数据来源**：两个 run 的 deliver 记录、transcript、git 历史和 code-intel 图。

### `run_5d894e22`（敏感信息遮蔽，Gate-2 共 8 轮）

第 2–8 轮共有 28 条阻断记录，归并后是 18 个不同的缺陷：

- 13–14 个是修复造成的，或者是修复不彻底，约占 75%。
- 4–5 个是本来就存在、第一轮漏掉的。

修复造成的那些里面：

- **9 个就在被修复的代码本身。** 正则多匹配或少匹配、正则变慢、相对 HEAD 退化。读者清单对这些完全没用。
- **5 个是流式遮蔽器和一次性遮蔽器的行为分叉。** code-graph 漏掉了这个依赖；grep 能找到，但每一轮的修复已经同时改了这两个文件，所以清单提供不了新信息。
- **读者清单的有效命中：约 0/14。**
- 有 4 个缺陷来自 3 轮以前的修复，属于潜伏型。其中 3 个是「相对 HEAD 退化」，第 6 轮的 reviewer 原话就是 "regression versus HEAD"。

### `run_d8762bc8`（files_touched，Gate-2 共 7 轮）

5 个缺陷，读者清单命中 1/4：

| 缺陷 | 读者清单能不能发现 |
|---|---|
| `_git_repo_root` 的 4 个调用方 | 能，但它们在调用图深度 2，不在深度 1 |
| 通过 `files_touched` 字段传播的问题 | 图里没有这条边；grep 有 487 行、56 个文件，全是噪音 |
| 测试测不到修复（修复撤掉后照样通过） | 不能；反向变异才能抓到 |
| 为一条没给置信度的 meta 风险做的修复，引出了回归 | 不能；这是「该不该在循环里修」的问题 |

另外 2 轮花在共享 checkout 的提交问题上。

### v1 没有看到的

1. **`run_5d894e22` 的轮数被一个已经修好的 bug 放大了。** 它的第一轮快照是空的（`round1/manifest.json` 里是 `files: {}`），所以每一轮名义上「只看修复」的复核，实际都是全量复审。`run_d8762bc8` 修掉了这个 bug。
2. **LOW 级修复不进复核，却引出了后续的阻断问题。** 两个 run 各有，共 3 例。
3. **第 6–8 轮的阻断发现全部来自 red-team。** red-team 每轮都在找新的攻击形状，循环没有终止条件。

### 源码核实

以下两点已对照源码确认：

- 「阻断」有两套判定：
  - `_binding_findings`：没给置信度 → 必须记录（fail closed）。
  - `_recheck_items`：没给置信度 → 按 0 处理 → 不进复核。
  
  同一条发现，两个读者的结论相反。
- `_recheck_items` 只收 HIGH 和置信度 ≥7 的 MED，LOW 级修复不会作为复核条目出现。

### 已有、不必重做的机制

- 只有 reviewer 本人回答 RESOLVED 才算解决，并且绑定到 prompt 的 sha：`_gate2_recheck_errors`。
- 记录必须覆盖 reviewer 的原话：`_binding_findings` / `_match_one_to_one`。
- spawn 的文本必须与发放记录一致：`_ledger_add` / `_spawn_text`。
- 每个反例一条回归测试，以及退出契约：G1。
- 一轮无新发现即收敛：G2 probe。
- 隔离 worktree 里的 mutation：G2 mutation 模式。
- HEAD 失败基线：B2。

### 被砍掉的部分

- **M2.1 读者清单**：命中率约 0/14 和 1/4，字段 grep 噪音太大。
- **M3「第二次修复引出问题就强制重设计」**：在 `run_b550de31` 上会误触发（那个 run 第 2 轮就收敛了）。在 `run_5d894e22` 上，重设计其实已经发生（第 3 轮删掉了分词器），之后照样又跑了 5 轮。
- **M4「没给置信度一律当备注」**：和现有的 fail-closed 记录规则冲突。由 N2 代替。

## 2. 根因（修订）

1. **修复之前没有冻结行为基线。** 「HEAD 原本做对了什么」和「这次改动必须做到什么」从来没有变成一份可执行的语料。所以一个修复弄坏已固定的行为，只能靠后面某一轮的 reviewer 碰巧找到；这个 run 里有三例，找到时已经隔了 5–6 轮。这对应 18 个缺陷里的 9 + 5 + 4 个。
2. **「要不要复核」按严重度过滤，而不是按「代码有没有被改」。** LOW 级修复和没给置信度的修复，作为改动进来了，却没有对应的复核条目。
3. **循环没有终止规则。** red-team 每轮都能产出新的形状，`over_budget_reasons` 只记录不拦截。
4. **记录和路由由模型手工完成**，被轮数放大，占了记录类时间的大头。

## 3. 方案

### N1 行为基线（在出复核 prompt 之前检查）

**基线内容**，在 Gate-2 第一次修复之前冻结：

1. 本 run 的 AC 测试。
2. 每个反例的回归测试（G1 已经要求；这里只是把它们放进基线集合，之后每次修复都要跑）。
3. **HEAD 差分 probe**，仅限替换行为的改动（遮蔽规则、解析器、路径解析、判定函数）：
   - PLAN 里声明一个 probe：一条命令，对一份输入语料输出逐条结果。
   - 工具分别在 HEAD worktree（复用 B2 建 HEAD 基线的那一套）和改动后的树上运行，然后比对。
   - 规则：HEAD 处理对的输入，改动后不能变错；有意改变的行为必须在 PLAN 里逐条列出。
   - 输入语料的来源：本 run 的 AC 例子、reviewer 给出的每个反例（must-match 和 must-not-match 两类），以及真实使用样本（例如 transcript 里真实出现过的命令）。
   - 语料只增不减。

   如果 PLAN 声明了 `parity_paths`（同一个行为有两种实现，例如流式和一次性），语料要在每条路径上都跑一遍。

**每次修复都要满足下面两条**，`gate2-recheck` 检查后才生成复核 prompt：

- 基线全绿，包括 HEAD 差分。差分走 `pipeline_test.py --mode probe`，直接沿用 G2 的跨轮去重和收敛判定。
- **反向变异**：工具把修复 hunk 还原，交给 `--mode mutation` 跑，条目登记的测试必须变红。hunk 无法精确还原时，要求模型给出 find/replace。

**这一步不能省：** 基线和反向变异只由工具计算，结论不由模型自报。

### N2 复核看改动；只有一个「阻断」判定

- **复核单位是修复 hunk，不是严重度。** 自上次复核快照以来，所有被改动的区域都要进入复核：
  - 交给最初报告该条目的 reviewer；
  - 这个区域在首轮由哪个 reviewer 负责，也一并交给他。
- **循环里只修阻断项。** 非阻断项不修，由工具写进 REPORT §10「Known Gaps & Attention Flags」和完成总结的遗留项，不写进 SwarmAI 的 ToDo 列表（XG 2026-10-19）。模型仍可以顺手修，但修了就作为一个复核条目，同样要过 N1。
- **一个判定函数** `is_blocking(finding)`，由 `_binding_findings`、`_recheck_items` 和完成审计共用。没给置信度时，统一按 fail closed 处理：既要记录，也要复核。

### N3 终止规则

- 一轮复核里，所有被派出的 reviewer 都没有新的阻断发现 → 收敛，不再派下一轮。
- red-team 每一轮找到的新形状，同时追加进 N1 的语料。之后同类形状由基线自动拦住，不用等下一轮人工复核。
- 第 3 轮仍未收敛时，`gate2-recheck` 不再生成补丁复核，改为根因复盘（见下方「N3 规则定稿」）。这一步替代 `over_budget_reasons`。

#### N3 规则定稿：再一再二不再三，不收敛就查根因（XG 2026-10-19 14:58 / 16:06 修订）

目标是**自动、快速地收敛质量**，整个过程不需要人介入。一次 review 把问题找全，一次把阻断项全部修掉；最多修两次。第 3 轮还没收敛，不交给人，而是由系统自己回头查：**是不是根上就有问题**。

| 轮 | 做什么 | 结束条件 |
|---|---|---|
| 第 1 轮 | 全量评审：所有声明的 expert 并行，一次交出全部发现 | 没有阻断项 → 收敛 |
| 修复 ① | 一次修掉第 1 轮的**全部阻断项**（`is_blocking`）；非阻断项记进 REPORT §10，不进循环 | — |
| 第 2 轮 | 只复核修复 ① 改到的 hunk | 没有新的阻断项 → **收敛** |
| 修复 ② | 一次修掉第 2 轮的全部阻断项 | — |
| 第 3 轮 | 复核修复 ② | 没有新的阻断项 → 收敛；**还有 → 根因复盘**，不存在修复 ③ |
| 根因复盘 | 派一个 fresh-context 的 root-cause expert，只读需求、PLAN、三轮发现、每轮修复引出了什么。回答一个问题：这些问题是**方案根上错了**，还是**方案对、只剩边角问题** | 见下 |

根因复盘有两种结论，都由系统自动处理：

- **方案对，只剩边角问题**：不再修。剩下的阻断项和非阻断项全部写进 REPORT §10，附上 root-cause expert 的理由，和代码一起 **commit（本地）**。这一轮的 `push_ready` 为 false，原因写成「Gate-2 第 3 轮剩 N 个阻断项，根因复盘判定为方案外的边角问题」。push 仍然由 push 前检查把关。
- **方案根上错了**：自动退回 PLAN，带着根因结论重新设计，而不是在错的方案上继续打补丁。重新设计后，评审重新获得 3 轮额度。**每个 run 只能重新设计一次。** 第二次设计还是不收敛，就按上一条处理：本地 commit，问题写进 REPORT，`push_ready` 为 false，run 结束。

规则：

1. **复核轮的范围就是修复的 hunk。** 复核轮里落在修复之外的新发现不会让循环继续：非阻断项记进 REPORT §10；阻断项也记进 REPORT §10，并作为根因复盘的输入。不降级、不丢弃任何发现。
2. **人不在循环里。** 不弹审批框，不等人回复。人看到的是结果：完成总结和 REPORT 里写明收敛了没有、剩下什么、根因复盘的结论、是否重新设计过。
3. **没有逃生口。** 删掉 `over_budget_reasons`；`--force` 不能让 `gate2-recheck` 生成第 4 轮。
4. **REVIEW 阶段用同一个计数**：spec-compliance 同样最多 3 轮，不收敛同样走根因复盘。

验收标准（Run 2 的 exit criteria）：

> 实现方案、关键决定和风险见 `pipeline-review-n3-implementation.md`。

> **已先落地（c247dca3）：轮数上限本身。** `core/review_round_gate.py` 在派 sub-agent 之前数这个 expert 在当前 stage 已完成的轮数，第 4 轮直接拒绝。拒绝文本要改成「去做根因复盘」，原来是「交给 XG」，这部分随 Run 2 一起改。

- AC1 `gate2-recheck`：第 3 轮复核完仍有阻断项时，不输出复核 prompt，改为输出 root-cause expert 的 prompt（需求、PLAN、三轮发现、每轮修复引出的新发现），返回 `root_cause: true`；`--force` 无效。
- AC2 某一轮所有派出的 reviewer 都没有新的阻断项 → `converged: true`，下一步就是 meta-review，不再派复核。
- AC3 每一条发现（含修复范围外的）最终都出现在 REPORT §10 / 完成总结里，一条不少（测试比对条目总数）。
- AC4 root-cause 结论由 hook 从 expert 原话里解析（`ROOT-CAUSE VERDICT: SOUND | WRONG-APPROACH`），模型不能自己写。SOUND → 本地 commit、剩余项进 REPORT、`push_ready: false`；WRONG-APPROACH → 自动退回 PLAN，一个 run 只能退一次；第二次仍不收敛 → 和 SOUND 一样处理并结束。
- AC5 REVIEW 的 spec-compliance 同样在第 3 轮后走根因复盘。
- AC6 `over_budget_reasons` 不再被读取；旧 run.json 里有这个字段不报错。
- 上线后验证：接下来 5 个 full/bugfix run，Gate-2 轮数 100% ≤ 3（重新设计后最多再 3 轮），中位数 ≤ 2；根因复盘次数、两种结论各占多少、重新设计次数单独统计。

### N4 发现台账

- **生成**：`evidence/findings-ledger.json` 由 hook 捕获的 reviewer 回答生成，挂在现有的 `GATE2_FINDINGS` 绑定上。原来是「模型写记录，工具比对」，改为「工具生成记录，模型只补充修复说明和测试 nodeid」。
- **合并**：同一文件、相邻行、同一类问题的发现合并成一个条目。reviewer 可以回答「不是同一个问题」，使条目拆开。
- **状态**：`open → fixed → resolved` 或 `reopened`。`resolved` 只能来自 `_gate2_recheck_errors` 已经校验过的 RESOLVED 回答。
- **路由**：按 N2 的规则派发。注意，reviewer 是并行跑的，所以少派 reviewer 主要省 token，不省墙钟时间。墙钟时间的收益来自 N1 和 N3 减少的轮数。

### N5 REVIEW 用同一套

spec-compliance 判定「AC 未满足」时，同样适用 N1 的基线和反向变异，以及 N3 的终止规则。

## 4. 验证与局限

- **样本只有 2 个 run，且 `run_5d894e22` 被空快照 bug 放大过。** 所以实现 N1 之前，先做一次只读回放：
  - 在 `run_5d894e22` 第一轮的树上，用「HEAD 差分 + AC 例子 + 真实命令样本」做语料跑一遍。
  - 看它能否在第一轮就标出第 6–8 轮才找到的退化（#21/25、#52、#57、#58）。
  - 标不出来，N1 的 HEAD 差分部分就砍掉，只保留反向变异。
- **N2、N3、N4 的价值不依赖样本量**：它们修的是已经核实的判定不一致、没有终止条件和手工记录。可以先做。
- **验收**：用 `pipeline_run_profile.py` 在之后 5 个 run 上测量以下指标：
  - Gate-2 平均轮数；
  - 修复引出的阻断发现占比；
  - DELIVER 时长；
  - 记录类模型时间；
  - 每轮派出的 reviewer 数。

## 5. 实施顺序

1. **Run 1（full）：N2 + N4。** 统一阻断判定、台账生成与合并、按改动路由、非阻断项记进 REPORT §10。（run_925edb0e）
2. **Run 2（full）：N3（含 REVIEW 的同一轮数上限）。** 规则和验收标准见 §3「N3 规则定稿」。终止规则：一轮复核没有新的阻断发现就收敛；第 3 轮仍未收敛就自动做根因复盘，替代 `over_budget_reasons`。先于 N1，因为墙钟时间的收益主要来自轮数（§3 N4「路由」），而 N2 + N4 不减轮数；`run_d8762bc8` 的 7 轮 Gate-2 只有 N3 能截住。N3 和 Run 1 改同一段 recheck 代码（`artifact_cli.py` / `pipeline_validator.py`），所以等 Run 1 落到 main 后再开，不并行。
3. **N1 回放（只读，research profile）→ Run 3（full）：N1。** 基线冻结、HEAD 差分 probe、反向变异。
4. **Run 4（full）：N5。** REVIEW 接入同一套引擎。

## 6. 风险

| 风险 | 对策 |
|---|---|
| HEAD 差分语料覆盖不到真正的缺陷形状 | 语料包含真实使用样本，reviewer 的每个反例都自动追加进去；先用 §4 的回放校准 |
| 有意改变的行为被差分判成退化 | PLAN 里逐条声明有意改变；未声明的差异就是阻断项 |
| 非阻断项写进 REPORT 后没人看 | 由工具写进 REPORT §10，同时列在完成总结的遗留项里，和代码在同一个 commit；不进 SwarmAI ToDo 列表 |
| 终止规则让一个本来能收敛的循环提前停下 | 第 3 轮后先做根因复盘；方案根上错了会自动重设计一次，重新拿到 3 轮额度。剩余项和理由全部写进 REPORT，push_ready 为 false，push 前还有一道检查 |
| 合并条目时把两个不同的问题并成一个 | 合并结果写在 prompt 里，reviewer 可以要求拆开 |

## 7. 明确不做

- 不减少首轮 reviewer，不改评审标准和阻断阈值。
- 不做读者清单（已被证伪）。
- 不在本方案里做并行 session 的隔离。
- 不新增 reviewer 角色。
