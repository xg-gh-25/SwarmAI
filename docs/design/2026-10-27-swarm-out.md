# Swarm Out

## 0. 一句话和定位

**Swarm Out 让一个人把 Pipeline Run 派到自己 AWS 账户里的 Hive 上执行：Run 的上下文从
Brain Hub 准备，执行和记录在云上，代码和经验经本机核对后回到本机的 main 和 Brain。** Mac 合上以后，已经派出去
的 Run 和排在 Hive 上的定时 Run 照常跑完；回来时在 Swarm Out tab 看结果、回答它的问题、验收。

它不是一套新的执行体系，是两份已有设计的落地延伸：

| 已有设计 | 它定了什么 | Swarm Out 怎么用 |
|---|---|---|
| `pipeline-run-conductor-v1.md` | 本机 Conductor：request、dispatch 日志、Local Worker、park/resume、Slack、定时 | 原样用。Hive 就是一台跑着同一套 Conductor 的 SwarmAI |
| 同上 §13.1 | 远程执行的方向是**联邦式 Hive**：每台 Hive 自己的 Conductor 建 Run、驱动 Run、保存日志；Host 发请求、只读它的流；代码以 branch 回来由 Host 落地；不建中心租约服务 | 本设计就是 §13.1 的那份"own design"。Host 落地用 §5.7 的 Importer（ff-only + `check_no_revert`），不用 `landing.py`：它绑在一个本机 Run 的 engine 上，导入的 Run 在 Host 上没有 engine |
| `pipeline-human-loop-v2.md` | 问题和审批是 item，`submit_human_input` 一条写入路径，消息流投影 | Hive 上的 Run 的 item 由 Host 转发回答 |
| `project-agent-delivery-os-hld.md` | Brain → Project Agent → Run → Trace → Evolution 的总体分工 | Swarm Out 是它的个人版切片：一个人、一个 Host、几台 Hive |

## 2. Use cases

| # | 谁、在哪 | 做什么 | 结束时 |
|---|---|---|---|
| U1 | XG 在 Swarm Out tab | 说一个任务；Swarm 用本机完整大脑澄清，出确认卡；点"派出去" | Run 跑在某台 Hive 的空槽上，dashboard"在跑"多一行 |
| U2 | XG 在普通 chat tab | "派到 Swarm Out"：这段对话就是澄清结果，出确认卡 | 回执留在原 tab，Run 进 Swarm Out |
| U3 | XG 在 Slack | 私信"swarm out：…"，线程里出确认卡 | 进度和结论回到同一线程 |
| U4 | XG 建定时任务 | "每天 9 点在 Hive 上跑 github-trending" | 定时器在 Hive 上，Mac 合上也会触发 |
| U5 | XG 合上 Mac 又回来 | 打开 Swarm Out | 第一行是"离开期间完成 N 个，M 个等你"；记录和代码已经拉回本机 |
| U6 | XG 点开一行 | 大浮层打开那个远程 session：看实时、回答问题、补一句话、停止 | 回答后 Run 在 Hive 上接着跑 |
| U7 | Run 结束 | 达标的代码自动落到本机 main；经验经本机判官进 Brain | push 仍等 XG 说 |

首批任务（把整条流串起来）：SwarmAI 自己的 bugfix（公开 repo，代码回流）、一份调研报告（`research`，非 git 产出回流）、一个 Hive 上的定时任务（合盖验收）。

## 3. 前提和不做

**前提**

- **F1. 一个大脑，一个写入者。** 只有 Host 写 MEMORY、EVOLUTION、DDD。Hive 读一份只读快照，学到的东西作为记录交回 Host（HLD §6.1；P8）。
- **F2. 同一套 Pipeline。** Hive 上的 Run 和本机 Run 是同一个 Pipeline、同样的检查，不做远程弱化版（HLD §6.6）。
- **F3. Hive 不碰用户的 repo 和 GitHub。** 代码以 git bundle 交回，由 Host 的 Importer ff-only 进 main（§5.7）；Hive 上没有 GitHub 写凭据（STEERING #5 的 push 闸门不变）。
- **F4. Swarm Out 不让前端拿到 Hive 密码。** 新路径全部由 Host 后端带凭据代理。已有的 Settings 显示密码另行处理（§14）。
- **F5. 任何 repo、任何项目（P7）。** 不认 SwarmAI 的 repo 或项目名；首批用 SwarmAI 只是因为它是公开 repo。
- **F6. 只有 owner 能派。** 和 Conductor V1 §7.1 相同。
- **F7. 信任和本机后台 Run 相同（usable P5）。** Hive 上的 agent 自己写测试报告、自己调 `land`，和本机后台 Run 一样不防 agent 作恶；校验和只用来发现损坏，不证明没被伪造。Hive 和 Host 之间额外守住两件事：别的 Hive 读不到、写不了这台 Hive 的东西（§9）；进本机 main 的 tree 就是 Hive 上审过、测过的那个 tree（§5.7）。

**不做（这一版）**

- 中心租约服务、跨 Hive 接管（HLD §7 旧稿）。Hive 死了，它的 Run 由人重新派（Conductor V1 §13.1 已接受这个代价）。
- 需要 Midway 的内部项目：Hive 没有 Midway 身份，准入直接拒绝。等 Cloud Desktop Hive（另起 spike）。
- Hive 上的私有记忆：Hive 永远拿不到 MEMORY / USER / EVOLUTION / STEERING / TOOLS / KNOWLEDGE。
- Native 后台任务：后台跑的一律是 Pipeline Run（usable §3.3.1、Conductor V1 §3）。调研、内容任务走 `research`。
- 组织级 Trace store、Offline Flow Eval（HLD §8、§11）。
- Windows（Conductor V1 P8）。
- Hive 前端的 `?session=` 深链：远程 session 只在 app 里的浮层看（§5.8），不做浏览器入口。

## 4. 架构

可视化的架构图和流程图：`docs/design/2026-10-27-swarm-out-diagrams.html`（浅色、深色都能看）。

```text
 Host（XG 的 Mac）                                         AWS（XG 的账户）
 ┌───────────────────────────────────────────┐
 │ 入口：Swarm Out chat · 普通 chat · Slack     │
 │        └─ pipeline-v1 draft --placement hive │
 │ 确认卡（只有人点才提交）                       │
 │ Host Conductor ──── submit ─────────────────┼──► S3 briefs/<hive>/<digest> ← Context Pack + 代码 bundle
 │   placement = hive:<instance>                │        │
 │   dispatch 日志（只记 Host 侧事实）            │──► HTTPS POST /api/conductor/requests（Hive）
 │                                             │        ▼
 │ Swarm Out dashboard ◄── 只读 Hive 的消息流 ──┼──  Hive Conductor（同一份代码，N 个 Worker 槽）
 │ 远程 session 浮层   ◄── 代理 messages/events ┼──    └─ Worker（headless SessionUnit）跑 Pipeline
 │ 回答 / 补话 / 停止  ──► submit_human_input ──┼──►    └─ 达标 → 落到这个 Run 的 clone
 │                                             │        │ 终态
 │ Record Importer ◄── 按游标拉 ────────────────┼──  S3 records/<hive>/<run_id>/  ← 封存记录（put-only）
 │   ├─ 代码：tree 核对 → ff-only 进 main        │
 │   ├─ 经验：reflect.json → 本机判官和路由      │
 │   └─ Trace / 审计 → Conductor Store           │
 └───────────────────────────────────────────┘
```

**谁拥有哪个事实**（扩展 Conductor V1 §4.2，不改它已有的行）：

| 事实 | 拥有者 | 读者 |
|---|---|---|
| Swarm Out request（含 Context Pack 摘要、placement） | Host Conductor Store `requests/` | dashboard、Slack、Importer |
| Host 侧 dispatch：`hive_sent` → `hive_accepted` → `imported` / `revalidation_required` / `import_rejected` | Host Conductor `events.jsonl`（新事件种类，§6.2） | dashboard |
| Hive 上的 dispatch、Run 日志、items、消息流 | **那台 Hive**（它自己的 Conductor Store 和 run store） | Host 只读 |
| 封存记录（Run 日志、REPORT、`run_audit.json`、transcript、代码 bundle、`reflect.json`） | Hive 写入 S3，写一次不改 | Host Importer |
| 代码进本机 main | Host Importer（ff-only + `check_no_revert`，§5.7） | Run 的 import 事件 |
| 经验进 Brain | Host 的 REFLECT 判官和路由（单一写入者），新增导入入口（§5.7） | Brain Hub |
| Trace | **不存**，读时 join（§5.9） | dashboard、popover |

## 5. 组件

### 5.1 Swarm Out tab（已有，接数据）

- 左侧 dashboard 改读 `GET /api/conductor/requests`（Conductor V1 §9 已定义），加 Hive 维度：每台 Hive 的槽位和健康来自 `GET /api/conductor/capacity`，Host 汇总各 Hive 的 capacity。
- **它就是 Conductor V1 §9 的 board**，列一样（等你、在跑、排队、24 小时内结束）。Pipelines overlay 保留 History 和 Activity；board 只做一份（见决策 D3）。
- 右侧 chat 不变。Swarm Out 会话的 agent 用 `pipeline-v1 draft` 建草稿，和普通 tab 用的是同一个命令；Swarm Out 只是默认 `--placement hive`。

### 5.2 入口和澄清

- **澄清在 Host 上做，用完整大脑**（DDD、MEMORY、本机状态）。Hive 只有只读的公开大脑，做不了澄清。
- `pipeline-v1 draft` 增加 `--placement hive[:<instance>]`。草稿在 Host 上完成三件事，都在人点"派出去"之前：
  1. **准入**（Conductor V1 §5.3 的规则 + 远程规则，§5.4）。不能派的当场说原因，并给出路：本机跑，或只派公开那部分。
  2. **Project Agent 决定走法**：读 Brain 的 `project-agent.yaml`，按 `profile_rules` 选 profile，`placements` 不含 `hive` 就拒绝。没有 Brain 的任务只能是 `research`，记为"通用 · 无 Brain"。
  3. **打 Context Pack**（§5.3）。
- 确认卡显示：标题、需求、Brain 和版本、Project Agent 和命中的规则、profile、目标 Hive（或"自动选"）、Context 摘要、预计耗时（`estimation_learner`，给区间）。只有人点才提交（Conductor V1 §6.3）。

### 5.3 Context Pack：Brain + Project Agent + 任务上下文

一个 Run 在 Hive 上读的全部输入，打成一个按内容寻址的包，放进 S3 `briefs/<hive-name>/<digest>/`（前缀带目标 Hive 的名字，只有那台 Hive 读得到，§9）：

| 内容 | 来源 | 说明 |
|---|---|---|
| DDD 快照 | Conductor V1 §5.2 的快照（显式 manifest 拷贝） | Hive 上用 `pipeline-v1 create --ddd-root` 读它，和本机后台 Run 同一机制 |
| 公开 context | 5 个公开文件（SWARMAI / IDENTITY / SOUL / AGENT / SELF） | 只读；私有 6 个文件永远不进包 |
| Project Agent | 解析后的 `project-agent.yaml` + 它的 digest + 命中的规则 | 记录"为什么走这个 profile" |
| 任务 | requirement（原文）、title、验收、范围 | 来自确认卡 |
| 召回切片 | `recall_ddd(goal, project, purpose)` 的结果：doc、section、score | 只给 Context popover 显示"澄清时依据了什么"，Hive 不读；Hive 上的 Pipeline 自己在快照里召回 |
| 绑定 | 项目的 `bindings.yaml`，每个 repo 的 `worktree` 改写成 Hive 上的路径（§5.5），`clone` 保留 | Host 路径在 Hive 上解析不到（§1） |
| 代码 | 每个 repo 的 `clone` 地址、`base_commit`，以及 **origin 上没有的提交的 git bundle** | Host 的 main 通常领先 origin（不常 push），Hive 从 origin 拿不到这些提交 |

- **Brain 和发布包解耦。** worker 角色的 Hive 不装 `release.sh` 打进 seed 的 DDD，workspace 的 `Projects/` 是空的，只读每个 Run 的快照。这样 Brain 改了不用重新发版，每个 Run 读哪个版本也是确定的，Hive 上也不会同时存在两份 DDD。
- 包的 manifest 记在 Host request 里（§6.1），每个文件带 digest；Hive 读包时校验 digest，不符就拒绝这个 request（发现损坏，F7）。

### 5.4 Placement 和准入

新 placement `hive:<instance>`，同 Conductor V1 §5.3 一样在提交时和派发时各查一次，违反就拒绝、带上规则名，从不悄悄换 placement：

- Project Agent 的 `placements` 含 `hive`（没有 Brain 的 `research` 任务除外）；
- 每个 repo 在 `bindings.yaml` 里有 `clone` 地址，且 Hive 能匿名拉到（首批只支持公开 repo；私有 repo 用只读 deploy key 是后续）；
- 任务不需要 Midway、本机数据、本机 MCP、或以 XG 身份对外发消息（判断依据：Project Agent 的 `validations` 和 repo 的 `bindings.yaml`；判断不了就拒绝，不派过去再失败）；
- 目标 Hive 健康（`/health` 正常且应用层鉴权通过）。demo 那台现在鉴权不同步，会显示"暂停分配"；
- "自动选"= 有空槽的健康 Hive 里，排队最短的一台；全满就进 Host 队列等，不超额。

### 5.5 Hive 的 worker 角色

同一个发布包，`SWARMAI_ROLE=worker`（新环境变量，provisioner 写进 user_data）。和参考实例（explorer、demo）的区别：

| | 参考实例 | worker |
|---|---|---|
| DDD | 发布包 seed | 每个 Run 的快照（§5.3）；workspace 的 `Projects/` 为空 |
| 项目解析 | workspace 的 `Projects/*` | `--ddd-root` 同时决定 DDD 读取、`has_ddd_docs` 和 repo 绑定（读快照里改写过的 `bindings.yaml`）。**这是新代码**：今天 `--ddd-root` 只是 Conductor V1 §5.2 的提议，项目解析也还读 workspace（§1） |
| 认知写入（cultivation、distill、evolution、DailyActivity 蒸馏） | 照常 | **全部关闭** |
| REFLECT | 照常写 DDD / Library / proposal | **只导出**：`reflect_job` 新增 worker 模式，每条 lesson 的路由结果记成 `exported`，正文进 `artifacts/reflect.json`，不调 `apply_to_ddd`、不写 Library、不写 proposal。**这是新代码**，不是现有的 `kept_in_run` 兜底 |
| Conductor Worker 槽 | 1（Conductor V1 默认） | N，启动时由 `spawn_budget` 算出，上限 `MAX_CONCURRENT_STREAMS`；不给交互 chat 保留 stream（worker 上没人聊天）。**这改了 Conductor V1 P2 的"固定 1 个、不是设置"**，只在 worker 角色生效。另一种做法是每台 Hive 只开 1 个槽、多开几台；你要的是"按机型给 N 个"，所以选 N，代价是 Worker 之间抢同一台机器的 CPU，由 S-R2 实测定 N |
| repo | 无 | 共享缓存 `/opt/swarmai/repos/cache/<repo>`（从 `clone` 拉，导入 Context Pack 的 bundle）；**每个 Run 一个自己的 clone** `/opt/swarmai/repos/runs/<run_id>/<repo>`（`git clone --reference` 缓存，checkout 到 Run 的 base），这个 clone 就是 Run 的 integration root |
| 落地 | — | agent 照常 `pipeline-v1 land`，落到**这个 Run 自己的 clone** 的 main，不推送。Run 之间不共享 main，所以 `_sync_moved_bases` 不会把别的 Run 的提交带进来 |

### 5.6 Host ↔ Hive：联邦协议

全部是 Host 主动调 Hive 的 HTTPS（经 Caddy + `hive_auth`，凭据由 Host 后端从 `routers/hive.py` 取）。Hive 不主动连 Host，所以 Mac 合上不影响 Hive。

| 方向 | 调用 | 幂等 |
|---|---|---|
| 派发 | `POST /api/conductor/requests`，body 是 request + `brief_digest`；Hive 先从 S3 读包、校验、写进自己的 Conductor Store，再返回 `accepted` | `request_id` 作幂等键；重复提交返回同一结果 |
| 读状态 | `GET /api/conductor/requests[/<id>]`、`GET /api/conductor/capacity` | 只读 |
| 读消息流 | `GET /api/conductor/stream`（SSE，带游标续读） | 游标 |
| 回答 / 补话 | `POST /api/conductor/runs/<id>/input` → Hive 的 `submit_human_input`（human-loop v2 §4.3），surface 记为新的 `host_relay`，带上原始 surface（overlay / slack）和 actor；Slack 按钮的 nonce 在 Host 上验证消费后才转发 | item id + round |
| 定时任务 | `POST /api/conductor/schedules`（新路由）在 Hive 上建 `pipeline_submit` job；`PUT` 换模板引用的快照 | job id |
| 取消 | `POST /api/conductor/requests/<id>/cancel` | 同 Conductor V1 |
| 远程 session 浮层 | Host 新路由 `/api/swarm-out/hives/<id>/sessions/<sid>/{messages,events}`，后端代理到 Hive 的 `/api/chat/...`；`/api/chat/events` 推送所有 session，代理只转发这个 `<sid>` 的事件 | 只读 |

Conductor V1 把 human-only 路由定为"loopback、前面不加 gate"（P5）。在 Hive 上不用另加：hive 模式下 `hive_auth` 已经拦所有 `/api/*`，loopback 也拦（§1），所以 Conductor 路由天然要凭据。Worker agent 能不能读到这份凭据见 §9。

### 5.7 封存记录和导入

**Hive 写记录。** Run 到终态时，Hive 往 `s3://swarmai-hive-…/records/<hive-name>/<run_id>/<attempt:04d>-<try:02d>/` 写一份（`try` 只在写到一半重写时加一）。只在终态写：Run 等人时 Hive 活着，Host 直接读它的 API；Hive 死了，等人的 Run 也续不了，parked 记录没有读者。

```text
manifest.json   run_id · request_id · schedule_occurrence | null · attempt
                brief_digest · base_commits · landed_commits · landed_trees
                reviewed_trees（LG-1 核对过的、审过测过的 tree）· lg_results
                hive_release · files[] {path, sha256, bytes} · created_at
run/            Run 日志、projection、REPORT.md、run_audit.json
transcript/     Worker 会话 transcript（jsonl）
code/<repo>.bundle   base..landed 的 git bundle（只有代码 Run 有）
reflect.json    导出的经验（worker 模式，§5.5）
```

- **写一次**：每个文件用条件写（`If-None-Match: *`），bucket policy 拒绝不带 `s3:if-none-match` 的 PutObject，所以同一路径不能被覆盖。manifest 最后写；Hive 重启后发现某个前缀已有部分文件、没有 manifest，就把 `try` 加一重写，不覆盖。
- IAM 新加一条：`s3:PutObject` 只到 `records/${aws:PrincipalTag/HiveName}/*`，没有 Delete。

**Host 导入。** Host Conductor 有一个 Importer，在 daemon 启动、Swarm Out 打开、以及 Mac 醒着时每 10 分钟，按 S3 前缀和游标（`attempt` 和 `try` 补零，按字典序列出；同一 attempt 只认带 manifest 的最大 `try`）找新 manifest：

1. **核对**：每个文件的 sha256；`brief_digest`、`base_commits` 等于 Host 派出时记的值（定时 Run 对的是 Host 为这个定时任务记的模板 digest，base 必须是 Host repo 或 origin 上存在的提交）。不符记 `import_rejected(<原因>)`，进"等你"。这一步发现损坏和串号，不证明没被伪造（F7）。
2. **代码**：bundle 拉进一个临时 worktree，checkout `landed_commits`，确认它的 tree 等于 manifest 里的 `reviewed_trees`（就是 Hive 上 LG-1 核对过的那个 tree），再用 `check_no_revert` 检查没有撤销别人的改动，然后 **ff-only** 进本机 main。
   - **本机 main 没动过**（还在 base 上）、`lg_results` 全过、`run_audit` 的 Isolation 和 Quality 都是 PASS：自动落，不需要人，Autonomy 不扣分。
   - **本机 main 已经前进**：ff 不了。不在 Host 上悄悄 rebase（rebase 后的 tree 没人审过、没人测过，LG-1 就失去意义）。记 `revalidation_required`，Importer 向同一台 Hive 派一个 **follow-up Run**：profile `direct`，base 是本机现在的 main（带上新的 bundle），输入是原 Run 交付的提交，要求是"把这些提交 rebase 到新 base、重测、落地"；request 里记 `revalidates: <原 run_id>`，Trace 把两个 Run 串在一起。原 Run 在 Hive 上已经是终态，协议里没有给终态 Run 开新 Attempt 的路径，所以不复用它（HLD §6.5.2 的 revalidation 在 Run 内完成，要等 HLD 的 Phase 1b 协议切换，本设计不等）。follow-up Run 的记录再走一遍导入。
   - **其他情况**（检查没全过、Hive 已经没了、重测失败）：进"等你"，两个动作：在本机 tab 接手，或"仍然落地"（人工决策一次，Autonomy 记 WARN）。
3. **经验**：`reflect_job` 新增导入入口 `process_imported(reflect_json, project, run_id)`，把每条 lesson 交给本机同一个判官和路由（写 DDD、Library 或 proposal），结果写回 Host 侧的导入记录（F1）。今天 `process_run` 只接 RunEngine，没有这个入口（§1）。
4. **留档**：记录解到 Host 的 `~/.swarm-ai/state/conductor/imports/<run_id>/`，不放进 `Projects/<p>/.artifacts/runs/`：那个目录被 engine 当成本机 Run 扫描。Pipelines History 和 Run Audit 卡片要加一个读 `imports/` 的来源，这是一处读取方改动。
5. 写一条 Host dispatch 事件 `imported`（或 `revalidation_required`、`import_rejected`），幂等键 `(run_id, attempt)`。

S3 记录是 Hive 被停机或销毁后唯一留下的副本，Host 导入后不删（权限上也删不了）；保留期用 bucket lifecycle 管，默认 180 天。

### 5.8 远程 session 浮层

- 点 dashboard 任意一行，大浮层打开那个 Run 的 Worker 会话：用本机的 turn 渲染组件，数据来自 §5.6 的代理路由。
- **等你**：item 卡片和本机 human-loop 卡片同一个组件，回答走 `.../input`。
- **补话**：输入框文字作为 guidance（human-loop v2 §4.4），不是回答。
- **停止**：走取消。
- 顶部有 Judge tag。不做"在浏览器打开"（§3）。

### 5.9 Trace：读时 join，不另存

dashboard 每行的 trace tag 对应的数据都已经有拥有者，读的时候拼起来（Conductor V1 §4.2 的做法）：

| tag | 字段 | 来源 |
|---|---|---|
| Brain | 名字、版本（DDD digest）、用到的文档 | Host request 里的 Context Pack manifest |
| Agent | profile、命中规则、validations、placement、落地方式 | 同上（Project Agent digest + 规则） |
| Context | 目标、验收、范围、召回切片和分数、包大小、打包时间 | 同上 |
| Hive | 实例、槽位、Worker session、run_id | Hive dispatch（读流时缓存一份到 Host 的 `runs/<id>.json`，只作展示） |
| 时间 | 开始、结束、时长 | Hive dispatch 的 attempts；导入后读封存记录 |
| Token | 输入、输出、合计 | `run_audit.json` 的 token totals（缺计量就显示"未测"，不补零） |
| Report | 结果、交付物、轮数、回流到 Brain 的条目、路径 | REPORT.md + 本机 REFLECT 的结果 |
| Judge | 五维 PASS / WARN / BLOCK + 数字 | `run_audit.json`，加上 Host 导入这一步（自动导入不算人工；"仍然落地"算一次） |

前端 `mockData.ts` 里的 `RunTrace` 类型就是这张表的形状，接数据时换成 API 返回，不改组件。

### 5.10 Mac 合上时

| 情况 | Mac 合上时 | 打开后 |
|---|---|---|
| 已派出的 Run | Hive 照常跑完、写记录 | Importer 拉回、落地、沉淀 |
| Run 需要人 | Hive park，释放槽位 | Host 读到它在等你；回答后 Hive 续跑 |
| 定时 Run | 定时器在 Hive 自己的 Conductor 上（Conductor V1 §7.2 的 `pipeline_submit` job，经 §5.6 的 schedules 路由建在目标 Hive），照常触发；每次触发用 origin 最新代码 | 结果已在 S3，Importer 按定时任务的模板 digest 对上 |
| 新派一个任务 | **做不到**（澄清和确认卡都在 Host） | — |

定时任务的 Brain 快照归 Host 管：Host 为每个定时任务存一份模板 request（含 Context Pack digest）；Brain 变了，Host 在线时重新打包、上传，用 `PUT` 换掉 Hive 上 job 引用的快照。Host 一直不在线，定时 Run 就一直用上一份快照，dashboard 标出快照的日期。

最后一行是决策 D1 要定的。

## 6. 数据契约

### 6.1 Host request（扩展 Conductor V1 §5.1，只加字段）

```yaml
request:
  # Conductor V1 已有的字段全部保留
  placement: inline_local | background_local | hive        # 新增 hive
  hive:
    instance: <hive_instances.id> | auto
    resolved: <hive_instances.id>                           # 派发时写入
  brief:
    digest: sha256:...                                      # S3 briefs/<hive-name>/<digest>/manifest.json
    brain: { name: <project> | null, ddd_digest: sha256:... | null }
    agent: { digest: sha256:... | null, status: reviewed | draft | null,
             rule: <命中的 profile_rules[i].when> | default }
    recall: [ { doc, section, score } ]                     # 只记引用，不存正文
    code: [ { repo, clone, base_commit, bundle: <blob 路径> | null } ]
  schedule: { job_id, template_digest } | null            # 定时任务的模板（§5.10）
    size_bytes: <int>
    packed_at: <iso>
```

### 6.2 Host dispatch 事件（Host `events.jsonl` 新种类）

| 事件 | 含义 | 下一步 |
|---|---|---|
| `hive_sent` | 包已上传，请求已发出 | 等 `accepted` |
| `hive_accepted` | Hive 已写进自己的 Store | 之后 Hive 侧状态只读 Hive |
| `hive_unreachable` | 发送失败；可重试，同一 `request_id` | 重试或人工改派 |
| `imported` | 代码 ff 进本机 main、经验已交给本机判官 | 结束 |
| `revalidation_required` | 本机 main 已前进，已派 follow-up Run | 等 follow-up Run 的记录 |
| `import_rejected` | 核对没过，或检查没全过 | 等你 |

Hive 侧的 `queued` `running` `parked` 等状态**不复制**进 Host 日志（Conductor V1 §4.2：不复制 Pipeline 状态）。

### 6.3 Hive 记录 manifest

见 §5.7。`files[]` 的 sha256 覆盖每个文件；manifest 本身的 sha256 作为这条记录的 id。sha256 发现的是损坏和串号，不是伪造（F7）。

## 7. 主要流程

**U1：从 Swarm Out 派一个 bugfix**

1. XG 在 Swarm Out 说需求；agent 用 Brain Hub 召回 + 本机记忆复述，只问影响结果的问题。
2. agent 跑 `pipeline-v1 draft --placement hive`：准入（§5.4）、Project Agent 选 profile、打 Context Pack、上传 S3。
3. 确认卡；XG 点"派出去"→ Host Conductor `submit` → `hive_sent` → Hive 校验包、入队 → `hive_accepted`。
4. Hive 的 Worker 建 Run（`--ddd-root` 指向快照，integration root 是这个 Run 自己的 clone）、跑 Pipeline、自测、Gate-2 审查、`land` 落到这个 clone。
5. 终态写封存记录 → Host Importer 核对、确认 tree 就是审过测过的那个、ff-only 进本机 main、经验交给本机判官 → `imported`。dashboard 这一行移到"已结束"，Judge 五维全 PASS。如果这期间 XG 在本机提交过，走 `revalidation_required`：Hive 上跑一个 follow-up Run，在新 base 上重测再交回。
6. XG 说 push 才 push。

**U4：Hive 上的定时调研**：建定时任务时，Host 存一份模板 request、打包 Brain 快照、经 `POST /api/conductor/schedules` 在目标 Hive 上建 `pipeline_submit` job。每次触发是 Hive 本地的一次 submit。Host 打开后按 §5.7 导入，按模板 digest 对上；Brain 变了就换快照（§5.10）。

**U6：回答一个问题**：Hive Worker 遇到需要人决定的事 → item → park（释放槽位）。Host 读 Hive 的流，dashboard 出现在"等你"。XG 在浮层里点选项 → Host 以 `host_relay` 转发 `.../input` → Hive `submit_human_input` → `resume_pending` → 有空槽就续跑（Conductor V1 §5.1 的转移表，不改）。

## 8. 故障

| 故障 | 发现 | 处理 |
|---|---|---|
| 发送时 Hive 不通 | HTTP 错误 | `hive_unreachable`；同一 request_id 重试；不自动换 Hive（自动换会让人不知道它在哪跑） |
| Hive 收到请求但读不到包 / digest 不符 | Hive 校验 | 拒绝，带原因；Host 显示在"等你" |
| Hive 重启 | Hive 自己的 Conductor 恢复（Conductor V1 §8） | 和本机后台 Run 一样：新 Attempt |
| Hive 被停机或销毁 | Host 读不到流 | 已写的记录照样导入；没写完的 Run 显示"Hive 不可用"，由人重新派（不做接管，§3） |
| 记录写到一半 | manifest 是最后写的文件 | 没有 manifest 的前缀不导入；Hive 重启后把 `try` 加一重写，不覆盖（§5.7） |
| 导入时本机 main 已前进 | ff-only 失败 | `revalidation_required`，派 follow-up Run 在新 base 上重测（§5.7） |
| 记录损坏或串号 | sha256、digest 或 base 不符 | `import_rejected`，不落地、不沉淀。这挡不住一个被注入的 Worker 写出自洽的记录（F7），这一点和本机后台 Run 相同 |
| Bedrock 限流 | Worker 的 SessionUnit 重试 | 和本机相同；槽位数据要在 S-R2 实测 |

## 9. 安全和信任

- **Hive 是 XG 自己账户里的机器**，和 Host 同一个人。威胁主要来自它读的外部内容（网页、repo）：一个被注入的 Worker 能写出自洽的测试报告和记录。这和本机后台 Run 的风险相同（F7，usable P5），本设计不另加防护；它守的是下面这几条边界。
- **Hive 之间互相隔离。** 现在每台 Hive 能读整个桶（§1）。改成：发布包前缀所有 Hive 可读；`briefs/${aws:PrincipalTag/HiveName}/*` 只有那台 Hive 可读；`records/${aws:PrincipalTag/HiveName}/*` 只有那台 Hive 可写、谁都不能删、不能覆盖。参考实例因此读不到任何 Context Pack 和记录。
- 进 Hive 的只有：公开 context、按 manifest 选的 DDD 快照、任务原文、代码 bundle。私有 context 文件和本机 Knowledge 永远不进包（和 `release.sh` 的白名单同一个列表，抽成一个常量，两处共用）。
- **DDD 快照可能含内部信息**（SwarmAI 的 DDD 有内部 URL、客户名）。worker Hive 只服务 XG 本人，而且只有它自己读得到自己的 brief，可以接受。参考实例不跑 Swarm Out；它们今天从 live DDD 打 seed，是另一个问题（§14）。
- Hive 回来的一切都是数据：记录里的文字不会被当成指令；代码只以 ff-only 进 main，tree 必须是 Hive 上审过测过的那个，且经 `check_no_revert`；经验经本机判官才进 Brain（R32 B1–B4）。
- Swarm Out 不让前端拿到 Hive 密码（F4）。Hive 上没有 GitHub 写凭据、没有 Host 凭据。Hive 上的 Worker 能不能读到 `hive-auth.env`，S-R1 里查；读得到也只能调它自己这台 Hive 的 API，按 P5 接受。

## 10. 五维

| 维度 | 影响 | 守护 |
|---|---|---|
| Run Isolation | 每个 Run 在 Hive 上有自己的 clone、worktree 和 DDD 快照；Hive 之间读写隔离（§9） | 导入核对 base、digest 和 tree |
| Quality | 同一 Pipeline、同一检查（F2） | 进本机 main 的 tree 就是审过测过的 tree；main 前进就派 follow-up Run 重测，不在 Host 上悄悄 rebase |
| Autonomy | Mac 合上照跑；人只在"等你"和 push 时出现 | 达标且 main 没动过的 Run 自动导入；main 动过的自动派 follow-up Run 重测，也不需要人 |
| Speed | 并行数 = 各 Hive 槽位之和 | 槽位按实测（S-R2）定 |
| Token Cost | 远程 Run 的 Token 和本机同样计量 | 定时任务重叠就跳过（Conductor V1 §7.2） |

## 11. 需要 XG 拍板的决策

**D1. Mac 合上时，新任务能不能派？**

| 方案 | 做法 | 代价 |
|---|---|---|
| A（推荐，先做） | 只有已派出的和 Hive 上的定时 Run 在 Mac 合上时跑；新任务要 Mac 开着 | 合上后想到的任务要等开机 |
| B | 云上加一张 DynamoDB 认领表：Slack 或手机提交写一行，有空槽的 Hive 用条件写认领一次，之后那台 Hive 全权负责（不续租、不接管） | 澄清只能用 Hive 上的公开大脑；Slack 网关要搬到 Hive |
| C | 完整的中心协调服务（HLD §7 旧稿） | Conductor V1 已经拒绝过 |

你说过"肯定需要云上的 conductor"：在 A 里，每台 Hive 自己的 Conductor 就是云上的 conductor，定时和执行都在云上；Host 只负责澄清和派发。B 是"云上统一接单"，等 A 跑通、确实需要合盖派活时再加，不影响 A 的任何接口。

**D2. 远程执行的启动条件。** Conductor V1 §13.1 写的是"有证据证明一个 Worker 不够才做"。Swarm Out 的理由是"合上 Mac 也能跑"，不是本机容量。我按你的方向改这个条件，并在 Conductor V1 §13.1 补一句指向本设计。

**D3. 一个 board 还是两个。** Conductor V1 §9 在 Pipelines overlay 里有一个四列 board，和 Swarm Out dashboard 内容一样。推荐：**board 只在 Swarm Out**，overlay 保留 History、Activity、Schedules。不然同一份数据有两个入口，迟早不一致。

**D4. 非项目任务。** 推荐：没有 Brain 的任务只能走 `research`，lessons 进 Library 的 `pipeline-lessons/`（现有路径），不建"通用 Brain"。

**D5. 本机 main 前进时怎么办。** 推荐上面 §5.7 的做法：派一个 follow-up Run 在新 base 上重测再交回，代价是多一个 Run 的时间和 Token。另一种是在 Host 上 rebase 后直接落，快，但落进 main 的 tree 没人测过；第三种是每次都让你点一下，但你平时一直在本机提交，几乎每个 Run 都会变成"等你"。

**和上级设计不一致的地方**（都是有意的，列在这里方便你一并确认）：

| 上级设计 | 本设计 |
|---|---|
| Conductor V1 P1 只在本机；非目标"别的机器" | 加 `hive` placement（D2） |
| Conductor V1 P2 只有一个 Worker、固定 1 个槽 | worker 角色的 Hive 有 N 个槽（§5.5） |
| Conductor V1 非目标"Project Agents" | 准入和 profile 读 Project Agent（§5.2、§5.4） |
| Conductor V1 §5.2 "REFLECT 写进 Host 的 live DDD" | Hive 上只导出，Host 导入后由本机判官写（§5.5、§5.7） |
| Conductor V1 §13.1 "用 `landing.py` 落地" | Host 用 Importer ff-only 落地（§0） |
| human-loop v2 §4.4 的 surface 列表 | 加 `host_relay`（§5.6） |
| Conductor V1 P6 "只有人选的 Run" | Importer 自动派 follow-up Run（§5.7）。它是人选的那个 Run 的延续，不是新的意图；request 记 `revalidates`，dashboard 显示在原 Run 下面 |

## 13. 验证计划

- **写入方和读取方**：每种新数据先定读者再写写者。Context Pack 的读者是 Hive Conductor（SO-3）和 trace popover（SO-1）；封存记录的读者是 Importer（SO-4）；导出的 `reflect.json` 的读者是 `process_imported`（SO-4）；`imports/` 的读者是 History 和 Run Audit 卡片（SO-4）；Host dispatch 新事件的读者是 dashboard 和 Importer。
- **最终测试集**（收尾时只跑这一组）：
  1. 普通 chat tab 的 tab 状态、落地、动态上限测试（`swarmOutTab.test.ts`、`landPromptInTab.test.ts`、`test_dynamic_tab_scaling.py`）——证明主工作区不受影响；
  2. Context Pack 的内容和 digest 测试——证明私有文件不出 Host；
  3. Importer 的核对、tree 一致、幂等、main 前进测试——证明损坏的记录和没审过的 tree 进不了 main 和 Brain；
  4. worker 角色的认知写入关闭测试（逐文件 hash）——证明不会长出第二个大脑；
  5. 两个 Run 并行落地的 bundle 隔离测试；
  6. 一次端到端：Host 派 → Hive 跑 → Host 离线 → 开机导入。
- **每期的审查**：SO-1 ux；SO-2 security（数据出 Host）；SO-3 integration + security（新的远程入口）；SO-4 correctness + security（不可信数据进 main 和 Brain）；SO-5 ux + security；SO-6 不需要。
- **每个修复做 mutation check**：撤掉修复，对应测试变红。
