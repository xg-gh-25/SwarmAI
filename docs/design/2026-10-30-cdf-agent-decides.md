# CDF：带着上下文的 agent 做判断，删掉在它之后二次评判的机制

## 0. 原则

XG 2026-10-30：**CDF 是 agent 自己的认知引擎。** 什么该沉淀、放到哪里、大小怎么处理，都由 agent 自己决定，不问人。沉淀的目的，是让 agent 之后能自主判断、交付得更好。硬约束只有一条：**不影响整个系统的性能。**

由此得出一条划分：

| 判断的性质 | 谁来判断 |
|---|---|
| **含义**：这是不是知识、类型和范围、去向、是新的还是已有的、要不要覆盖旧条目、这次纠正是不是旧错重犯 | **产出它的那个 agent**，它手里有完整上下文：对话中的 agent（S1），会后复盘（S7，fork 出来的会话），写 REFLECT 的 run agent（S3） |
| **来源和存储**：引用了谁的话、有没有外部内容、有没有密钥或注入、是否逐字重复、单条大小、每轮注入多少 | 确定性代码，只看事实，不判断含义 |

**不允许**一个更弱的判断者在 agent 之后推翻它的判断。更弱的判断者指：正则、关键词或 BM25 匹配、固定规则、看到的上下文比 agent 少的模型调用。**检索可以**，比如用 BM25 给 agent 找出可能相关的已有条目，前提是判断仍由 agent 来做。

## 2. 每轮注入文件的来源底线（保留，并改成只看事实）

MEMORY、EVOLUTION、STEERING、USER、TOOLS 每轮都会进 prompt，外部或注入的文字一旦写进去，就会进入之后的每一个判断。所以这五个文件保留一道**确定性的来源检查**。它只看事实，不判断含义：

- **"用户原话"的唯一定义**：单元带有 `user_quote`，并且代码逐字核对它是被引用的那条本会话 `user_message` 的子串。只是引用了一条用户消息、但没有逐字引文的，**不算**用户原话。这个定义对 K1、K2、K3 和覆盖一律适用（来自另一个 session 的提醒：否则一个单元可以引用真实的用户消息，却写出那条消息没说过的话）。
- **K1 一般规则**：单元要么有用户原话（按上面的定义），要么引用了本会话或本 run 的 `measured` 证据，并且 `cited_external` 为假。引用链按 45e308448 的 `lineage_external` 计算。
  - 不满足时，单元写进项目 DDD（按需召回，不进每轮 prompt），去向和原因记在 `ingestion_writes` 里。这是来源事实决定去向，和判官的 grounded 判断无关。
- **K2 用户自己的文件**（STEERING、USER、TOOLS）：必须有用户原话，测量证据不算。
  - **逐字核对挡不住的一条路（安全评审 2026-10-30，决策 D，XG 选定）**：逐字只证明引文在用户消息里，不证明它说的就是这条规则。被注入文字带偏的复盘，可以把一条植入的规则配上一句真实的"好的"。所以这三个文件在逐字核对之后，还要过一次**隔离核对**（`core/ingestion/user_check.py`）：模型只看到用户自己的消息和这条主张，看不到会话记录、工具输出和任何外部内容，判断"用户的话是否说了这条"。不成立，或核对没有回答，单元按"非用户原话"处理，进项目 DDD（按需召回），不丢。MEMORY、EVOLUTION 不走这一步，仍是 K1。
  - S1 和 S7 都适用这条规则，S7 的 scope=user 单元因此不再整条丢弃。
  - 证据索引里，非用户的事件不再标成"(user message)"（`s7_review.py:201`）。
- **K3 防止信任洗白**：agent 写入的条目，在 baseline 里按来源事实登记 trust：有用户原话的登记成 user，有测量证据的登记成 measured，引用外部内容的登记成 external，其余都登记成 `inferred`（45e308448 的 `unit_basis`）。**永远不默认登记成 user。**
- 密钥和注入扫描（`provenance.py:407-410`，`governed_edit.py:121`）、证据必须真实存在、带凭证的 URL，这几项都不变。

## 4. 性能（价值优先，只度量，不设上限）

- **聊天路径**：不新增任何调用。D12 删掉每条用户消息都要跑的正则，D14 只改排序。
- **每轮 prompt 的大小**：五个文件全部注入。它们在可缓存的 base prompt 里（SELF 的两段式构建），体量变大，增加的主要是 cache read 的成本，首 token 时间受的影响很小。
- **度量**：
  - 每次构建 prompt 时，记录这五个文件的 token 数；
  - 每天记录首 token 时间的中位数，以及 S7 的耗时和花费（usage 账本，第 0 步修好之后）。
- **体量真的影响到性能时**：首 token 时间或文件体量和基线相比明显上升，就由 agent 对这个文件做一次**合并整理**：用 same 和 overrides 合并近似条目、覆盖过期条目，产出的是声明，不是截断。不设任何会丢掉有效知识的上限。
- **后台**：
  - S7 改用会话本身的模型，又每个会话都复盘，后台的 token 花费会上升。这部分照规矩只记账，不设上限。
  - 删掉 S2 和判官，能抵消一部分。
  - 复盘走串行执行器和内存门控（`worker.py:994-1024`），不和聊天抢资源。
- **账本 bug 先修**：usage 账本把 fork 父会话累计的 opus 用量记到了每次 S7 复盘上（例如一次复盘记了 $121.67，它实际的 Sonnet 花费是 $0.13）。不修这个，成本对比做不了。
- **待核实**：fork 的上下文平均只有约 14K tokens，S7 看到的可能是压缩后的会话。在 D1 第二轮一并核实，需要的话放大证据索引。

## 5. 一次性处理（先备份 `ingestion.db`，迁移用 45e308448 已有的、带校验的备份）

- **已写入、但当时被改道的条目**（S7 61 条，S2 29 条，S3 3 条）：**不搬**。它们已经在 DDD 里，可以按需召回。搬回去需要撤回、重写、改指向，还会和之后的编辑、覆盖、撤回冲突，风险比收益大。今后新写入的走新规则。
- **积压**（额度推迟的 102 条、`unknown_domain` 的 61 条）：**不重跑**。它们是在没有关系声明的情况下抽出来的，重跑会全部变成 `new`，制造重复和过期的 gap。改为在库里标成 `discarded_backlog`，保留原记录，可以恢复。
- **trust 和标记**：用 45e308448 的 v9 迁移（先验证备份），按引用顺序做到不动点。trust 改按来源事实计算。
