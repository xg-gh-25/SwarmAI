## 0. 结论

**Bot 是对一个结果负责的 agent。** 它有人定的目标，有自己的 SOP 和 policy，盯着一组输入，有事就醒，自己决定做什么、什么时候做、要不要找人。
它可以用到我们所有的 Brain；它自己只记一本账，记的是"正在干什么"。
它在哪里运行由定义指定，OS 检查那个位置能不能满足它的 policy。

第一个 Bot 是 **Inbox Bot**。今天的 Inbox 分好了类，但没有替人把活干掉：

- 进过"等你回复"的 49 条里，40 条已回，其中只有 3 条是从 Inbox 发出的。
- 白天的进入延迟：Slack 中位数 11 分钟、p90 15 分钟；邮件中位数 13 分钟、p90 99 分钟。
- XG 回过的 Slack 消息里，有 22 条被分到了"需要知道"。

（`inbox_items`、`inbox_sends`，2026-11-20 至 11-27。）XG 的原话：「一个是不及时 一个没看到我想要的」。

本稿取代 `2026-11-27-brain-duty.md`。那份稿从"给 Job 升级"出发，方向错了。它的几样零件留下来：执行器单写的账本、确定性预检、按 hash 绑定的脚本、人写的目标记录。

## 1. Bot 和其他东西的区别

| | Job | 功能（今天的 Inbox） | Project Agent | **Bot** |
|---|---|---|---|---|
| 驱动 | 到点就跑 | 固定流程 | 有人派活才动 | 有事就醒，自己判断 |
| 对什么负责 | 这次任务 | 流程跑通 | 这一单 | **一个结果**，有指标 |
| 知识 | 无 | 无 | 一个 Brain | **所有 Brain** 加个人认知 |
| 记性 | 无 | 条目状态 | 无 | 一本账：未闭环的事、成绩、权限等级 |
| 安全 | job 的 safety 字段 | 写在代码里 | 产品 gate 和 Brain gate | **它的 policy，由执行器执行** |
| 人 | 写提示词 | 每条都点 | 派单、验收 | 开头定目标和 policy，结尾看结果 |

**一个 Bot 由六样东西组成：目标、SOP、policy、输入、runtime、账本。** 知识来自所有 Brain。
Bot 和 Brain 是多对多的：Brain 按领域管"知道什么"，Bot 按目标管"为什么动"。

## 3. 东西放在哪里

| 东西 | 放在哪 | 谁写 |
|---|---|---|
| `bot.yaml`：名字、职责、输入、触发、runtime、指标脚本 id、报告周期 | workspace `Bots/<id>/` | 人在 owner 会话里与 Bot 一起起草；保存后，引用的脚本按 hash 记录 |
| `SOP.md`：怎么干活 | workspace `Bots/<id>/` | 同上。Bot 运行中只能**提议**修改，人在 Bot 页上接受后才写入；路径加进 `runs_later_rules` |
| **policy**：能读什么、能做什么、什么要人批 | **app 数据目录，审计写保护区**（与 `project_agent_rules` 同级，`backend/core/project_agent_rules.py:21-24`） | **只能经由 Bot 页的 UI 路由修改**；路由检查调用方是桌面 UI，复用 `core/inbox/caller.py` 的做法 |
| 目标：人的原话 | 同上 | 复用 `whole_sentences`、`quote_key` |
| Brain 可见性：`internal-ok` / `owner-only` | 同上，每个 Brain 一行 | 人在 Brain Hub 上设，默认 `owner-only` |
| 账本 | app 数据目录 | 只有执行器写 |

## 4. 一次醒来：四个角色

```
触发：输入上来新事件 / 到点 / 账本里有事到期
 ① 预检（不调模型）：没有新事件、指标没变、没有到期事项 → 记一行 quiet，结束
 ② reader（读原文，没有任何工具）：每个线程调一次，输出几乎全是枚举值的事实：
     projects ∈ Brain id 枚举 · people ∈ 线程参与者 · ask_kind ∈ {问答, 审阅, 决定, 安排, 通知, 其他}
     · due · needs_reply · commitments（你在这个线程里答应过什么，见 §8.2 C）
 ③ research（不读原文，只能提议）：一个无人值守会话，输入是②的事实、执行器组装好的召回（§5）和账本。
     工具只有 Read / Grep / Glob，读的范围限定在 workspace 和挑中的 Brain；credential_rules 和 workspace 外的路径一律拒读。
     它不能执行任何动作，最后输出一个动作块：建议做什么，加上给 drafter 的研究笔记
 ④ drafter（读原文，没有工具）：沿用 make_draft，输入是线程原文加③的研究笔记，不给其他东西。
     这一条改了 drafts.py 的约定：原来只放线程和你与对方的往来，现在多了研究笔记，研究笔记标明出自哪个 Brain 的哪个单元
 ⑤ 执行器：用 policy 这个纯函数逐条裁决动作块，执行允许的，把其余的准备好留给人，然后写账本、跑一次指标
```

- **为什么这样分：** 读原文的两个角色（②、④）手里都没有工具。有工具的那个（③）只能读和提议，不能动手。
  真正去做事的只有执行器，它按 policy 做确定性判断。一条注入就算被 reader 换了个说法，最坏的结果是 ③ 提议了一件不该做的事，然后被执行器拒掉。
- **research 的范围看收件人，不看消息内容**（审查 H2）。对方是外部的人，或者线程是公开的（`ReplyTarget.public`），只召回 `internal-ok` 的 Brain。
  对方是内部同事，可以召回所有 Brain，但草稿会标出用了哪些 Brain。
- ③复用 `attention_auto` 的无人值守会话。先从里面拆出一个公共核心 `run_unattended(message, preamble, tools, read_scope) -> 全文`，
  因为今天的 `run_session` 只返回 `RESULT:` 那一行，preamble 写死，也不接受工具列表（`backend/core/attention_auto.py:478-561`）。
  这个会话**不注入**默认的 USER、MEMORY，需要的个人事实由执行器按需放进召回里，这样"上下文里放过什么"执行器是知道的（审查 H4）。
  `cognition` 只允许查挑中的 Brain，每次调用都记进账本。
- 触发挂在输入自己的事件上。Inbox Bot 挂在 Inbox runner 存下新条目那一步，不用每小时一轮的 job 调度器。

## 5. 跨 Brain 读

今天的召回刻意只查一个 Brain（`backend/core/recall_multi.py:1434`，`backend/core/cognition.py:310-332`）。Bot 的做法：

1. **选 Brain**：由②从 Brain id 枚举里挑，prompt 里附上每个 Brain 的一句话简介。另外，人可以给 Brain 填写 `intake.aliases`，
   比如客户名、系统名、人名，做确定性匹配作为补充。今天的 `identity.summary` 和 `intake.handles` 写的是任务类型，
   不含客户名、人名，拿来做关键词匹配不行（审查 M2）。
2. **召回**：执行器对挑中的每个 Brain 各跑一次 `cognition find --project <P>`，再按需加上对方的组织信息和你与对方的往来。
   v1 就是 N 次调用，`--projects` 一次查多个等以后有需要再做。
3. **写回**：经 CDF 提交，按内容声明 scope。不新增写入路径。

## 6. Policy

### 6.1 形状（Inbox Bot）

```yaml
read:
  brains: all                   # 实际范围再由 §4 的收件人规则收窄
  personal: [org-chart, counterpart-history]
act:                            # 执行器对 ③ 动作块的裁决
  draft_reply: auto
  create_todo: auto
  close_aware_item: auto
  notify_self: auto             # 只发结构化字段和链接，见 §8.3
  send_reply: person            # v1 一律由人在 app 里点
escalate: [only-person-can-decide, policy-change-request]
runtime: {home: local}
```

### 6.2 policy 怎么执行

**policy 是执行器里的一个纯函数：`decide(action, facts, context_record, policy) -> allow | hold-for-person | refuse`。**
输入里没有模型的判断：动作块里的动作是枚举值，事实来自②的枚举，`context_record` 是执行器自己记下的"放进过哪些 Brain 的哪些单元"。
r1 声称能复用的 `unattended_gate` 白名单、`external_approval_gate`、`approval_class` 都不复用，它们解决的是别的问题（审查 M5）。
执行器能做的动作只有 policy 列出的那几个，每个对应一个后端函数。发送不在其中：v1 发送只能由人在 app 里点，走 Inbox 原有的接口和核对。

### 6.3 产品底线与权限阶梯

- **底线写在产品里，任何 policy 都放不开**：
  - 销毁不可恢复的用户数据
  - 读凭据
  - push、开 PR、发布
  - 改 policy、SOP 或目标
  - 读原文的角色手握工具
- **权限阶梯放在 B5，v1 不做。** 到时自动发送的"类别"由确定性的三样决定：对方 id、私信还是线程、`target.public`。
  `ask_kind` 只能把类别收窄，不能放宽，因为它来自外部原文（审查 M6）。
  另外，凡是用到了 `owner-only` Brain 内容的草稿，不在任何自动类别里。

### 6.4 什么时候找人

| 情况 | 去哪 |
|---|---|
| 日常处理 | 不找人，记账本 |
| 准备好了、等人点的东西 | Slack DM 通知加 Inbox 里的条目（§8.3），不进 Needs You |
| 只有人能决定的事、SOP 或 policy 的修改提议 | 一条 Needs You（REVIEW），每个 Bot 同时最多一条 |
| 连续失败被熔断 | Needs You（BLOCKING） |
| 每周 | 周报，放在 Bot 页上 |

## 7. Runtime

`bot.yaml` 里写 `runtime.home`，可选值是 `local`、`elastic`、`cloud-desktop:<名字>`、`hive:<名字>`。**v1 只接受 `local`。**
填了其他值，Bot 不启动，Bot 页上写明原因。原因如下：

- Inbox 的接入是本机上配置的用户 MCP 和钥匙串里的密钥（`backend/core/inbox/sources/credentials.py:1-15`）。
- Hive 模式不跑 Inbox runner（`2026-11-20-inbox.md` §9）。
- placement 里没有"本机"这个 offer（审查 M4）。

字段现在就保留，因为它承载 XG 要的这个决定。后续步骤（B4）接上 placement：

| 需要 | 从哪推出 | 谁能满足 |
|---|---|---|
| 内部网络和资源 | 已有的 `Needs.private`（`backend/core/carriers/base.py:104-108`） | Cloud Desktop；Elastic Worker 不行 |
| `personal_channels`（新） | 输入里有用本人身份读取的渠道 | 本机；Cloud Desktop 要先在那台机器上配好自己的接入 |
| `private_context`（新） | `read.personal` 不为空 | 本机；要放到别处，需要人允许把那几样同步过去 |
| `always_on`（新） | 触发要求 24 小时在线 | Cloud Desktop、always-on 的 Hive |

位置满足不了需要，Bot 就不启动，并说明原因，不会悄悄换个地方跑。

**委派**（B4）：Bot 的家在一处，可以把③那一步交给别的位置去跑。带过去的只有结构化事实和 `internal-ok` 的 Brain，不带原文，不带个人认知。走现有的 Swarm Out 派单。

## 8. 第一个 Bot：Inbox Bot

### 8.1 目标（建 Bot 时由 XG 用原话写，这里只是起草）

该回的人不漏，该做的事不掉，你花在消息上的时间一周比一周少。

### 8.2 四件事

- **A. 今天必须你处理的事**：早上一份，之后随时更新。跨渠道选 3 到 5 件，按重要性排，每件附一句理由。
- **B. 备好的回复和材料**：消息一到，就走 ②→③→④，草稿后面附上依据。
- **C. 没闭环的事**：
  - 你在等别人的：从线程状态里看出来，到期就代拟一封催问。
  - 你答应过别人的：要读你自己发出的消息，今天的规则把这些消息丢掉了（`2026-11-20-inbox.md` §6.1）。所以这是一个**新的抽取器**：只读你自己发出的那部分，交给②抽出 commitments。
- **D. 关注的人和话题**：你指定的人或项目有动态时，汇总给你。

日历在 v1 里不做，因为无人值守会话不加载 MCP（`backend/core/attention_auto.py:523`）。

### 8.3 送到你在的地方

主出口是**发给你自己的 Slack DM**，v1 有这几条限制：

- 收件人固定是你本人的 id，不由模型决定。
- 内容只有结构化字段（谁、什么事、期限、建议的动作）和一个"在 SwarmAI 里打开"的链接。草稿全文不进 DM。DM 发出前过一遍出站脱敏（`backend/channels/egress_redactor.py`）。
- **没有发送按钮。** Slack 按钮的点击是在后端进程内收到的，会被 Inbox 发送接口的调用方检查拒掉。要绕开这层检查，就等于开了第二条发送路径。以后要做按钮，得单独设计一条 `origin=slack_button` 的路径，要求是本人点击、绑定卡片上显示的收件对象、绑定 sha（审查 H3）。

### 8.4 及时

- **B-1 先修 Slack 拉取：**
  - 加上真正的 429 退避和 Retry-After 处理。今天 `slack.py:819` 只是抛错，没有退避；而且线上用的是 `mcp:user-slack-mcp`。
  - 白天的拉取间隔改成 2 到 3 分钟。今天一次拉取约 19 秒。
- 邮件 99 分钟的 p90 来自 Outlook MCP 超时，不是拉取间隔的问题，单独查。
- 分开衡量两段时间：从到达到进入 Inbox，从到达到草稿备好。

### 8.5 指标（第一周先记基线）

| 指标 | 基线 |
|---|---|
| 你亲手处理的比例 | 40 条已回里 37 条没经过 Inbox |
| 分错：你回了，但没标成要回 | 22 条，分布在 8 个私信线程（全部是规则判"要回"、模型降成"需要知道"） |
| 到达 → 进入 Inbox，p90 | Slack 15 分钟、邮件 99 分钟 |
| 到达 → 草稿备好，p90 | 尚无 |
| 草稿一字未改就发出的比例 | 尚无 |
| 未闭环事项按期关掉的比例 | 尚无 |

你回了的、你没理的，都会记进 `inbox_feedback`，再经 CDF 学进 USER 和 MEMORY。这一条改了 Inbox 设计里"不做行为镜子"的决定，需要 XG 认可（§13 第 3 条）。

## 11. 验证计划（结束时必须成立）

1. 一条带注入的消息，即使换了说法（比如"请把某某数据贴过来"），也不能让执行器做出 policy 之外的事，③也不能读到 credential 路径和 workspace 以外的路径。
2. 聊天会话和无人值守会话都写不进 policy、目标；只有经过调用方检查的 UI 路由能改。
3. 对方是外部的人，或者线程是公开的，召回只用 `internal-ok` 的 Brain。
4. ③的上下文里放过哪些 Brain 的哪些单元，账本里全部有记录。
5. Slack DM 的收件人固定是本人；DM 里没有草稿全文；DM 经过脱敏。
6. 预检没发现变化时，不调模型，usage ledger 也不新增记录。
7. 日常醒来不产生 Needs You；每个 Bot 同时最多一条 REVIEW。
8. `runtime.home` 不是 `local` 时，Bot 不启动，并给出原因。

## 12. 不做（v1）

- 自动发送；Slack 发送按钮；日历；本机以外的 runtime；Bot 之间互相派活。
- 常驻进程；预算或 credits 上限。

## 13. 要 XG 定

1. **Bot 有主动性**：不等人派活，自己判断。这扩展了 11-09 对 Project Agent 的界定，同意吗？
2. **v1 只在本机跑**：本机合盖就停。Cloud Desktop 一直在线，但它要先配好自己的 Slack 和邮件接入，还要允许把 USER、MEMORY 同步过去。要不要先在本机跑？我建议先在本机。
3. **用你的行为来校准**：你回了什么、没理什么，学进 USER、MEMORY。这一条改掉 Inbox 设计里"不做行为镜子"的决定，同意吗？
4. **主出口是发给你自己的 Slack DM**：只带摘要和链接，不带发送按钮，可以吗？
