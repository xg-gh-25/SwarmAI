# Swarm Out 派单中心

**XG 2026-10-30：**
- Swarm Out 是派单中心，Host 是指挥中心，Hive 是执行方。
- 能接的才接。比如现在的 Hive 没有内部开发环境，内部代码改动就直接拒收，而不是派出去才发现做不了。以后 Cloud Desktop 进了执行机池，这类单子就能接了。
- 派单中心不只负责派出去，还要收结果、验收、管理结果落地：run 的 reflect、文件产出、代码 bundle、run 的情况、token 花费、失败信息、阻断信号等。
- 当产品来做，但不要过度设计。

**本文和 `2026-10-30-run-spec.md`（r4）怎么分：** 派单这一段（派工单、执行方式、Hive 上的工作区）在 run-spec。本文讲两头：接单（§2），收单（§3–§6）。收回的各条通道都已经有了：
- 结果记录 `swarm_out_results`
- Hive 上的记录 `hive_records`
- 文件 `hive_files`
- 代码 `hive_return` 和 ReturnPanel
- 教训 `hive_lessons`
- 花费：usage ledger

本文把这些串成一张单子从头到尾的流程，只补缺的几处。

**r2：** 一轮零上下文前提审查之后改的。HIGH 三条，MED 八条，按原因归成五组，一次改完：
- **r1 设计多了，删掉：**
  - 机型能力表、`hive_instances.kind`、`platform:macos`、ToDo 回写。
  - 原因：现在每个内部 Brain 都已经被现有准入拒了两次（placements 不含 `hive`，clone 也不是 Hive 能拉的地址）；机型表眼下一个实际情况都拦不住。
  - Cloud Desktop 进池也不只是"加一个机型"：每条 Host→Hive 的路径都默认对方是 EC2、CloudFront、S3。所以这件事等第二种执行机真来了再设计。
- **"需要内网"的信号漏得太多：**
  - r1 只看 Brain 绑定的仓库里有没有 `kind: internal`，可内部需求大多不在那里：General 下的任务提到 code.amazon.com、Sentral 或 Athena，或者 clone 地址是 `git.amazon.com`。
  - r1 还拿 Brain 绑定的全部仓库来算，而不是这一单实际用到的仓库，结果把 AIDLC 公开仓库上的只读任务也拒了。改法见 §2.2。
- **跨文档的两处冲突：**
  - 交付物目录 `Hive/work/.../out/` 会被 `hive_files.safe_rel` 拒掉（`Hive/` 开头的路径一律不收），文档永远回不来。
  - Hive 在会话收尾时写 `closed` 记录、回收工作区，比验收早得多，"不通过之后补做"会落在一个已删的工作区里。
  
  这两处都改了，run-spec r4 跟着改（§5、§6）。
- **状态和存储没落到实处：**
  - 派发记录只追加不更新；结果记录每次检查都按一份固定的键重建，存在里面的验收结论会被冲掉。
  - "下一步"在补做时会出现不止一个。
  - 几种情况永远等不到了结：手工落地的代码、不想收的教训、永远不会来的教训、30 天后被清掉的记录。
  - 改法：单独的存储、明确的优先级、明确的结束状态（§1、§6）。
- **改代码的单子，验收和审 diff 重复了：** ReturnPanel 本身就是"审 diff → 批准落地或拒绝"。所以改代码的单子，验收结论直接取落地的结果，不再单独点一次（§4）。

## 1. 一张单子从头到尾

```
接单 ─拒收─▶ ✕ 拒收（什么都没发，§2）
  │
派单 ─失败─▶ ✕ 没派出去        ┄ 可能已派出（Hive 没报会话，按原样显示）
  │
执行中（在跑 / 等你回答）
  │                       ┄ Hive 不在了，没有结果（结束）
已收回（§3）
  │
验收（§4）
  │
落地（§5）
  │
已了结（§6）
```

- **状态从记录推出来。** 来源包括：派发记录、Hive 报的状态、结果记录、ReturnPanel 的状态、教训计数，再加一个新的小存储 `state/swarm-out/settle/<dispatch>.json`，只存三样东西：
  - `verdict`：回答类和文档类单子的验收结论；
  - `lessons_declined`：你说"这些教训不要了"；
  - `settled_at`：了结时间。

  这份文件不叫 `closed`，避免和 Hive 那边的记录类型同名；也不放进结果记录，因为结果记录每次检查都会重建。
- **每张卡片只显示一件"下一步"。** 优先级固定：

  等你回答 > 执行中 > 待验收 > 待审代码 > 已了结

  - 补做会在同一个会话里开一个新的 turn。新 turn 一开始，旧的验收结论就作废。结论绑定在它判断的那一次结果上，记下当时的 `ended_at` 和 turn 数。
- **两个结束状态写明白：**
  - **可能已派出**：Hive 没报会话，按现有方式显示。
  - **Hive 不在了，没有结果**：Hive 停了或被删了，结果没取到。现有逻辑只在 Hive 运行时才去检查，所以这一单不会再有结果，按结束处理。
- **"等你"一栏改成显示所有等你做的事：** Hive 的提问，加上待验收、待审代码，以及 3 天内要清理的单子。

## 2. 接单：能接才接，拒收在问你和派出之前

### 2.1 顺序

```
路由 → 选 mode → 跑 spec（现有准入 + §2.2 的内网判断）→ 有拒收：拒收卡片，结束
                                                      → 没有：问澄清问题 → 派
```

现在的问题是 skill 先问你问题，再跑 `spec`。改成先跑 `spec`，再问你问题：一个注定要拒收的单子，不该先问你三个问题。

### 2.2 "需要内网"：从这一单实际用到的东西推出来（确定性）

现有准入已经能拒：
- mode 不能在 Hive 上跑（placements）；
- clone 地址不是 Hive 能拉的地址，比如 `brazil ws create ...`；
- 定义是草稿或被改过；
- 没有验收；
- 没有空闲的 Hive。

新增一条 **需要私有网络**。下面任何一项命中就算，各项是"或"的关系：

| 来源 | 判断 |
|---|---|
| 这一单**用到的仓库**：mode 的 `repos`；没写 `repos` 时，用 Brain 绑定的全部仓库 | `bindings.yaml` 里 `kind: internal`，或者 clone 地址的主机在私有主机名单里 |
| 任务原文和验收句子里的地址 | URL 或主机名在私有主机名单里，例如 code.amazon.com、w.amazon.com |
| mode 用到的 skill | SKILL.md 的 frontmatter 写了 `network: private`。这是产品新增的通用字段，和已有的 `platform: desktop` 同一种用法 |
| 本机 agent 写进 spec 的 `needs_private` 理由 | agent 读出了表里抓不到的内部依赖（比如"要查 Sentral"），可以加一条拒收理由，但**不能去掉**表里已经命中的拒收 |

- **私有主机名单**是用户自己的设置，写在 Swarm Out 设置的 `private_hosts` 里，产品只提供这个机制。这台机器上首次的默认值是 `*.amazon.com`、`*.a2z.com`、`*.amazon.dev`。
- **执行机能不能上私有网络：** 现在所有 Hive 都上不了，结论写死。以后有了能上私有网络的执行机，复用 `hive_instances.hive_type` 这一列来区分，到时候一起设计它的传输方式。

### 2.3 拒收卡片和拒收记录

- 卡片和派发卡片是同一个组件，状态显示"✕ 拒收"，写三件事：
  - **为什么**：命中的是哪一条，比如"IVTHub-Service 是 Amazon 内部仓库，需要私有网络，现在的 Hive 都上不了"。
  - **什么都没发**：Brain 没有同步，也没有联系任何 Hive。
  - **可以怎么做**：在本机 chat tab 里做，卡片上有一个按钮，把任务原文放进一个新的 chat tab。
- 拒收单独记在 `state/swarm-out/refusals.jsonl`，**不写进派发记录**。原因：派发记录里一行没有会话，表示"可能已派出"；而且 `/runs`、usage 同步这些读取方都要求有 `hive_id`。
- Swarm Out 的历史里加一行："拒收 N 次 · 其中需要私有网络的 M 次"。什么时候值得把能上私有网络的执行机加进池子，看这个数。

## 3. 收回：回单里有什么

| 回单项 | 来源 | 单子上怎么显示 |
|---|---|---|
| 结局、失败信息 | `summarize` 的 `ended`、`error`（已有） | 状态栏；失败时显示红色的原因条 |
| 检查 | 派工单上的检查和实际 Bash 调用的比对（已有） | 跑了 / 报错 / 没看到 / 跑了但没有结果。不再说"没跑"：在循环、脚本里跑的检查 Host 认不出来，说"没跑"就是假话（2026-10-31 改，见 `2026-10-31-swarm-out-agent-owns-its-runs.md` §2.7） |
| 阻断信号 | Brain gate 拦截计数和完整性问题、保留动作的问询（批了 / 拒了 / 没答）、Hive 的提问（已有） | 没答的进"等你"，其余列在验收清单里 |
| 执行方式 | 声明的和实际的（run-spec §4.2） | 不一致时标出 |
| pipeline | profile、状态、landing、审计（已有） | 一行。REPORT 见下一行 |
| pipeline 的 REPORT | **新增**：会话创建的 run 结束时，Hive 后端把它的 `REPORT.md` 作为一个文件记录封进回单。现在只有 agent 自己列出的文件才会回来 | 文件行 |
| 花费 | usage ledger（已有，`spend_of`） | 一行；历史里按结局汇总（已有，`tallyRuns`）。拒收和可能已派出的单子没有会话，花费按 0 记，注明"本机写 spec 的花费不计入" |
| 文件 | `hive_files` 自动放进 Brain 的 `deliverables/hive/`（已有）。交付物目录见 run-spec r4 §4.3：改成 `Outputs/<dispatch>/`，`safe_rel` 收得下 | 文件行，可以点开 |
| 代码 | `hive_bundle`，本机取回到 `refs/hive/`（已有） | ReturnPanel |
| 教训 | `hive_lessons`（已有） | LessonsAccept |

## 4. 验收：按交付物分两种，不重复

**机器核对清单**（确定性，所有单子都显示，只列出来，不阻止任何操作）：
- 结局是 `completed`；
- 检查跑了且没报错（"没看到"单独列）；
- 交付物在：
  - 回答：最后一 turn 有回复；
  - 文档：至少回来一个文件；
  - 提交：有 bundle；
- 没有没答的提问或问询；
- 没有完整性问题；
- 执行方式和声明的一致。

**验收结论：**
- **交付物是提交的单子：结论直接取落地的结果，不再单独点一次。** ReturnPanel 本来就是"审 diff → 批准落地或拒绝"，受保护的路径单独批（已有）：
  - 落地了 = 通过；
  - 拒绝了 = 不通过；
  - 合不上或改动太大，需要手工落地的，新增一个"我已经手工落地"按钮 = 通过。
  
  审 diff 的卡片旁边，显示派工单上的验收句子和机器核对清单。
- **交付物是回答或文档的单子：** 卡片把验收句子放在交回来的东西旁边，你点"通过"或"不通过"，不通过时附一句话。结论写进 `settle/<dispatch>.json`，并绑定这次结果的 `ended_at`。
- **不用模型判官下结论**（P5）：这一句只有你能判断。

**不通过之后：**
- **补做**：把你的那句话作为新消息，发到同一个 Hive 会话。Hive tab 已经能通过 Host 的代理发送；工作区还在，因为回收只在了结时发生（§6）。
- **放弃**：直接了结，结局记为"放弃"。

**Slack 派的单子：** Slack 回复里只说"已收回，到 Swarm Out 里验收"。Slack 不做验收按钮。

## 5. 落地

| 产出 | 落到哪 | 谁批 |
|---|---|---|
| 代码 | 本机 main（`hive_return.land`，已有） | 你，在 ReturnPanel 上；这一步同时就是验收 |
| 文件 | 收回时已经放进 Brain 的 `deliverables/hive/`（已有），只是放着，不进认知 | 不用批 |
| 教训 | 到了就进本机 CDF → Brain（CDF 设计 D13，2026-10-30 起；原来的"收下教训"按钮已删） | 没人批。r2 写的"不收"按钮作废：没有可收的步骤，也就没有可不收的 |

## 6. 了结

**三个条件都满足时自动了结：**
1. **结论定了：** 通过、不通过后放弃、放弃，或者"Hive 不在了，没有结果"。
2. **代码处理完了：** 落地了、被拒了、"已手工落地"，或者没有代码。
3. **教训都到了：** 满足下面任何一种：
   - Hive 的记录已经 `closed`，而且交回的教训都已经交给本机 CDF（没有 `pending`）；这一单没有记录（老 Hive，教训走老路）时只看后一半；
   - Hive 停了或被删了。

你也可以手动了结，结局记为"放弃"。

**了结时：**
- **回收 Hive 上的工作区：** 新增一个 Host→Hive 的接口 `POST /api/hive/work/{dispatch}/release`。Hive 收到后：
  - 会话还在跑，或者最后一个 bundle 还没被 Host 取走，就拒绝，下次了结检查时再试；
  - 否则删掉 `Outputs/<dispatch>/` 和 `Hive/work/<dispatch>/`，只删这两处。
  
  会话分支 `hive/<dispatch>` 在代码落地或被拒之后才删。Hive 不在了，就跳过回收，单子照样了结。
- **Hive 那边的兜底：** 一直没了结的单子，工作区按已有的 `RETENTION_DAYS`（30 天）回收，和 Hive 上的记录一样。
- **Host 这边的提醒：** Host 的 `sweep_host` 会删掉 30 天没动过的记录，到那时 bundle 就落不了地了。所以第 27 天起，在"等你"一栏提醒"这单 3 天后清理"。
- 卡片移进历史。历史按结局统计，已有。

## 7. 不做什么

- 不用模型判官下验收结论。
- 不做执行机机型和能力表：等第二种执行机真来了，连同它的传输方式一起设计。
- 不按工具链细分（cargo、npm、Brazil）：工具链由 `setup` 装，装失败就是 run 失败，原因看得见。
- 不自动重试；不排队；不把一个单子拆给多台机器。
- 不回写 ToDo：不在这次的范围里。

## 8. 验证计划

**谁读新写的东西：**
- `refusals.jsonl`：拒收卡片、历史里的那一行。
- `settle/<dispatch>.json`：状态推导、"等你"一栏、了结判断。
- `release` 接口：了结。
- REPORT 文件记录：回单、文件行。
- `private_hosts` 和 `network: private`：`spec` 的拒收。

**最终测试集：**
1. 需要私有网络（每一行来源各一个用例）：`kind: internal` 的仓库；`git.amazon.com` 的 clone 地址；General 下任务原文里有 code.amazon.com；skill 带 `network: private`；agent 写的理由能加上拒收、去不掉拒收。都在问问题、同步 Brain 之前被拒，拒收写进 `refusals.jsonl`，不写进派发记录，`/runs` 照常能用。AIDLC 只用公开仓库的 mode 不被拒。
2. 下一步：给定各种记录的组合，"下一步"只有一个，并且符合优先级；新 turn 一开始，旧的验收结论作废；"Hive 不在了"和"可能已派出"各有自己的结束状态。
3. 机器核对的每一条，各一个用例（2026-10-31 起不再有"没跑"，只有"没看到"）。
4. 改代码的单子：落地了 = 通过，拒绝了 = 不通过，"已手工落地" = 通过；不存在第二个验收按钮。
5. 了结：三个条件各有一个"不满足就不了结"的用例；`release` 在会话还在跑或 bundle 没取走时拒绝；只删那两个目录；Hive 不在了也能了结。
6. 一份文档写进 `Outputs/<dispatch>/`，回到 Brain 的 `deliverables/hive/`；pipeline 的 REPORT 也回来。

**审查：**
- 内网判断和拒收：correctness 审。
- 了结和 `release` 接口：correctness、security、operational 审（删除的范围）。

## 9. 分步落地（接在 run-spec r4 之后，同一个 requirement 里排任务）

1. skill 改成先跑 spec；加内网判断；拒收卡片和 `refusals.jsonl`。不变量 1。
2. 回单补齐：REPORT 文件记录、`Outputs/` 目录、检查的"没看到"。不变量 3、6。
3. 状态推导和"下一步"，"等你"一栏的扩展。不变量 2。
4. 验收：回答和文档类用你的结论；改代码的取落地结果，加"已手工落地"。不变量 4。
5. 了结、`release` 接口、30 天的提醒。不变量 5。
