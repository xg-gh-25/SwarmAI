# CDF 提取的输入

## 0. 目标和约束

XG 2026-11-02：

- 知识质量在提取端把控，不靠审核兜底（EVOLUTION K007：改提取器读什么、按什么标准提取，不加审核层、不加逐条模型核对）；
- fork 整个 session 来复盘是偷懒的做法：把"读什么"这个设计问题交给了模型；
- 对准北极星，不带来性能问题，长期正确，系统化，不打补丁。

## 1. 现状（2026-11-02 实测）

**成本**：近 7 天 CDF 花了 $1489，占全部花费的 21%，其中 S7 占 97%。

- Opus 5.5 跑了 405 次，花 $1478，平均每次 $3.65。
- 钱几乎全花在写缓存上：7 天写入 1.73 亿 token，读缓存 3.3 亿，输出只有 433 万。
- 单次写缓存超过 50 万 token 的有 131 次，花了 $773。

**为什么写这么多**（`s7_review.review_session`）：

- **每个窗口都 fork 一次 session**：fork 带着整个 session 的历史。文件头写"fork 约 10K token"，这是 10-30 在一个压缩过的 session 上量的；1M 上下文的 session 基本不压缩，实际是几十万 token。
- **缓存从不命中**：复盘关掉了所有工具，提示前缀就和原 session 不一样；单次复盘读缓存约 0.1M token，写缓存却是 1–1.7M。
- **每安静一小时就复盘一次**：长 session 两天内被复盘 13–28 次，每次都重新付一遍"到目前为止的整个 session"。
- **记录不做任何过滤**：fork 之外，每个窗口还附带一份记录（`_record`，最多 40 万字符）。

**提取器读到的是什么**。这个 session 的记录（`messages` 表）共 103 万字符：

| 内容 | 占比 |
|---|---|
| 工具调用（命令摘要、输入正文 `display`、id） | 53% |
| thinking | 29% |
| 每次调用的结果（只是一行 `outcome`，记录里从来没有工具输出的正文） | 11% |
| 我对人说的话 | 3.4% |
| 每轮的文件改动卡片（`turn_changes`） | 2.4% |

用户消息原文和实测字段（退出码、通过和失败数）不在这份记录里，在 evidence 索引里，索引已经把它们全部列出。

**写出来的质量**（近 7 天）：

- 有用率 83%，目标 90%；General Brain 55%，GAP 75%。
- 写进 DDD 1893 条，其中被召回过的只有 6%。
- 健康检查自己的诊断：写的是"刚才发生了什么"，没有提炼成规则；把进度备忘当成缺口写。

**判断**：提取器读的东西 90% 以上是过程。它在过程里一边找结论一边写，于是写出大量"这次做了什么"。质量问题和成本问题是同一个根因：输入没有设计。

## 2. 设计：两件事

### ① 提取器只读承载知识的那一层

每个窗口送给提取器的内容：

| 读 | 来源 | 引用 |
|---|---|---|
| 人的消息原文 | evidence 索引（现有） | 可引用（user） |
| 我对人说的话：每段文字原文 | 记录里的 assistant text | 可引用（agent） |
| 实测结果：工具结果里的退出码、通过和失败数等 | 带实测字段的工具结果只保留这些字段，照常登记为 measured | 可引用（measured） |
| 每轮改了哪些文件：路径和状态 | `turn_changes` 卡片 | 可引用 |
| 每条消息用了哪些工具、各几次、失败几次（一行） | 由记录生成（`knowledge_view`） | 跟着这条消息 |
| 一轮怎么结束的（完成、被停下） | `turn_outcome` 的 ended / subtype | 跟着这条消息 |

不读：thinking；工具调用的命令摘要和输入正文；每次调用的结果行。

我做出的结论都在我说的话里，提取器从那里提取，不去过程里找。工具调用不再逐条列出，所以单独引用某一次工具调用的 id 会被拒；要引用，就引用我说出结论的那条消息。

**不 fork。**复盘是一次独立的调用，提示前缀固定（提示词加契约），所以每次复盘都能复用同一份前缀缓存。窗口之前的上下文来自两处：本 session 之前写下的单元（relations 已经在送），以及人在本 session 更早的消息（索引里已有）。

### ② 提取标准写在提取端

每个去处写明"满足什么才写"，由提取器自己判断写或不写，不留给下游审核。

| 去处 | 写的条件 |
|---|---|
| General Brain | 能用一句话写出脱离这个项目、这次事件仍然成立的规则；写不出就不写 |
| GAP | 一条只写一个问题，附具体的下一步；进度备忘不是缺口 |
| TIMELINE | 事件写做了什么，也写结果是什么 |
| 项目 DDD | 只写会改变以后在这个项目里做判断的内容：决定、模型、带识别信号的坑。"这次做了什么"属于 DailyActivity 和 git，不写进 DDD |
| EVOLUTION | 一类判断错误（2026-11-02 r4 已定） |

这些条件写进提示词契约（`contracts_v2.UNIT_RULES` / `_TYPE_QUESTIONS`），不另设机制。

### 删掉的东西

- fork 和它的退路：`fork=True`、`Unresumable` 那一支、`_drop_fork`；
- 记录里的 thinking、工具调用的命令和输入正文、每次调用的结果行；
- 实测：这个 session 的记录从 120 万字符降到 13 万（11%），fork（11MB 的完整 CLI 对话）整个去掉。窗口切分基本用不上了。

## 3. 北极星、性能和成本

- **质量**：提取器读的是结论和人的话，不再在过程里找东西，写出来的应该更像规则、更少流水账。是否如此，看各去处的有用率和 DDD 写入量，不在这里预设数字。
- **成本**：这个 session 的复盘输入从 120 万字符的记录加 11MB 的 fork，降到 13 万字符，而这还是整个 session 的量；每次复盘只读上次复盘之后的部分，还要更少。S7 每周估计从约 $1440 降到 $100–200。这是估计，上线后实测。
- **性能**：复盘在会后跑，不在聊天路径上。点名和筛选是确定性的字符串处理。

## 4. 风险

- **只在工具输出或命令里出现、我从没说出口的事实，不会被提取。** 我接受这个风险。R20 要求最终回复写出结论和验证结果；实测数字由索引的实测字段带着。这正是"质量在输入侧把控"：知识在说出口的那一刻成形，提取器不去过程里替我总结。
- **少了窗口之前的完整上下文。** 一句很短的纠正（比如"不对"），要靠它前面那段我说的话才看得懂；而我说的话一直在知识层里。

## 5. 否决的方案

| 方案 | 为什么不做 |
|---|---|
| fork 和只用记录做 A/B | fork 本身就是错的方向（XG） |
| 降低复盘频率 | 去掉 fork 之后，每段内容只被复盘一次，频率不再影响成本 |
| 复盘换成 Sonnet | 质量风险，而且省得少 |
| 截断工具输出 | 违反 R23，截短的过程仍然是噪声 |
| 给 General Brain 和 GAP 加审核 | K007：把条件写进提取端，不加审核层 |

## 6. 待核对（写代码之前）

- 现有的逐条模型核对：每轮注入的条目被用户原话覆盖时，会做一次隔离核对（`user_check.grounds`）。它防的是"借一句无关的用户原话拿掉用户自己的规则"，属于安全底线，不是质量审核，成本接近 0（121 次调用，$0）。保留，并在这里写明它和 K007 的区别。
- 健康评委每个去处抽 20 条打分，这是测量，不是关卡，保留。

## 7. 验证计划

**测试（先写，应当失败）**：

- 记录生成：不含 thinking、命令摘要、输入正文和结果行；含人的消息、我说的话、实测字段、文件改动的路径和状态、每条消息一行工具使用情况。
- 复盘不 fork：review 调用不带 resume / fork。
- 提示词里带着每个去处的写入条件。

**最终不变量**：人的每条消息都原文在场；我说的每段话都原文在场；实测字段照常登记；复盘调用里没有 fork。

**实现与验证**：`s7_review.knowledge_view`、`review_session` 不再 fork、`_cwd_of` 删除、提示词第 6 条写明各去处的写入条件。测试在 `tests/test_cdf_s7_review.py`；7 个 mutation 全部被抓到；用到 S7 的 25 个测试文件全部通过。

**上线后实测（7 天）**：S7 的成本和单次 token；各去处的有用率；DDD 写入量；C3。

**评审**：设计做一次零上下文的前提审查；代码改动请 correctness 评审。

## 8. r2：写入条件变成结构，窗口带上前一轮对话（2026-11-02）

r1 把各去处"满足什么才写"写在了提示词里，模型照不照做没有保证。r2 把能变成结构的条件变成结构；窗口开头缺的上下文，从输入侧补上。

**结构化**（`contracts_v2`）：

- **知识单元必须写 `applicability`**：什么时候适用，一个能认出来的触发条件。"这次做了什么"的流水账写不出适用场景，这一条就挡住了它。原来"pitfall 必须写 applicability"那条单独的规则因此多余，删掉。
- **缺口必须写 `proposed_next`**：具体的下一步。进度备忘写不出下一步，这一条就挡住了它。
- 事件已经要求写 `impact` 或 `outcome` 之一，不再加码：代码提交来的事件（S4）一律只有 `impact`。
- 各模型提取器回答时用的结构化 schema 是从契约生成的，所以这两个字段直接成了模型必须填写的字段，对 S1、S4、S6、S7 同时生效。pipeline 复盘的说明（`deliver.md`）和模板同步加了这两个字段；缺了它们的条目会被丢弃，并在 `dropped` 里写明原因。来自旧版本 Hive 的、缺这两个字段的经验会被拒，记为 refused，不会静默丢失。New Brain 的建脑流程有自己的条目契约，不在这次范围内。
- 加这两条之前量过（近 7 天）：S7 的缺口有 16/326 缺 `proposed_next`，S3 有 11/25 缺；S7 的知识单元有 39% 缺 `applicability`，S4 有 70% 缺。这些就是从今以后在提取那一刻就写不进来的内容。

**已经存下的数据不按新契约重新判**：

- pipeline 的复盘报告入队（`s3_run.enqueue_report`）改为逐条校验：契约后来不再接受的一条（比如部署前写好的报告）记为无效，其余照常入队。
- 落地前的 RF-1 到 RF-4 只检查报告是否为五段式（`prepare_lenient`），不会因为旧行缺新字段而让交付失败。REFLECT 本来就不应挡住落地。
- 队列里的单元按单元处理，一个失败不影响其他；改动时队列是空的。

**窗口前的上下文**（`s7_review._exchange_before`）：每个窗口都附上它之前的最后一轮对话，包括人的话和我那之后的回复。窗口开头的一句"不对"，因此能读到它否定的是什么。这段只作背景，不可引用。原来只在窗口里没有用户消息时才显示人的上一条消息，现在每个窗口都显示，并且带上我的回复。

**验证**：`tests/test_cdf_extraction_structure.py` 和 `tests/test_cdf_s7_review.py`。9 个 mutation 全部被抓到。构造单元的 40 个测试文件，加上用到 S7、REFLECT 和模板的 48 个测试文件，全部通过；只有一个例外 `test_model_answer_single_entry`：它报的是 `core/aws_account.py` 直接调用 Bedrock，那个文件这次没有改动，main 上本来就是这样。

## 9. 第二轮复用第一轮的缓存，候选条目只列一次（2026-11-02）

**为什么第二轮命不中缓存**（重启后的第一批 3 次复盘实测）：第二轮写缓存 4.7 万到 7.7 万 token，读缓存只有 592 token。

- CLI 的结构化输出是一个 `StructuredOutput` 工具，schema 就是这个工具的参数定义。
- 工具定义位于缓存前缀的最前面：两轮用两套 schema，前缀从第一段就分叉了，第二轮读不到第一轮的任何缓存。
- 同一种 schema 的调用之间共享的那段，正好是工具定义加系统提示（第一轮 2235 token，第二轮 592 token）。

**第二轮提示词本身的浪费**：

- 每条候选条目印了两遍：先一行"id + 前 200 字"，再整条原文；
- 同一条候选在多个单元下重复出现，3 次复盘里分别占 15%、15% 和 47%。

**改法**：

- `review_schema()`：两轮用同一个 schema，单元列表加上可选的 `relations`，每一轮的提示词说明这一轮填哪一部分。
- `relation_prompt`：每个单元只列出它相关候选的 id；所有候选集中在 "## Entries" 下各出现一次。id 那一行就是声明时要照抄的 "<id> | <首行>"，后面一行是首行之后的其余原文。条目仍然是完整的，去掉的只是重复。

**验证**：

- 4 个 mutation 全部被抓到：第二轮换回单独的 schema、条目重复列出、首行印两遍、把 relations 设为必填。
- 用同样 3 次复盘的真实单元重建第二轮提示：94K→60K、57K→36K、80K→38K 字符，分别少了 37%、37% 和 52%。
- 第二轮读到第一轮缓存后实际省了多少，上线后看账单。
