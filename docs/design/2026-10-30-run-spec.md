# Run Spec：一个 Intent 在本机定完怎么做，Hive 只执行

**XG 2026-10-30：**
- intent → run spec 在本机全部定好：路由到哪个 Brain 和 Project Agent、用 native 还是 pipeline、用哪个 profile，其他该准备的也都准备好，不留到 Hive 上再判断。
- profile 不该由 Project Agent 规定，而是按 intent 选。
- Hive 上改代码可以走 native。
- 要系统性的方案，不打补丁：Project Agent 没用对，就重构。

**r3（XG 2026-10-30："为什么不在派发时敲定，到了 Hive 再暴露是 shift-right"）：**
r2 让 Hive 上的偏离走审批来问人，等于承认 Hive 上还会有"换执行方式"这件事。逐个看会偏离的场景，发现每个都能前移，或者本来就不该改执行方式（§4.2）：
- **agent 不照做**：这是执行出了偏差，不是一个需要判断的问题。改成 Hive 后端在会话开始时，按 pin **自己建好 run**，agent 不再调用 create。pin 下的 create 一律拒绝，不问人。
- **direct 遇到歧义**：歧义要在派发时解决。本机只在"你的原话就是规格、读不出第二种意思"时才选 direct。Hive 上真遇到歧义，问你的是"要的到底是什么"，profile 不变。
- **做到一半发现风险更大**：风险判断前移到本机，派发前用本机的代码图看影响面。剩下的部分不改执行方式，由落地前的人审 diff 兜底，这一道本来就有，而且看的是真实改动。
- 准备仓库也一起前移：Hive 后端在会话开始前把仓库准备好，不再写成命令让 agent 自己跑（§4.3）。仓库准备不好，任务就不开始，派发卡片显示"没派出去"。

**r2：** 一轮零上下文前提审查之后改的。它找到 4 个 HIGH，按原因归成四组，一次改完：
- **r1 加了一层新机制（`escalate`、`floor`、`spec_digest`、迁移命令），作用对象却是几乎不起作用的字段。** 现在只有 SwarmAI 一个 Brain 能派到 Hive，其他 8 个都只在 chat tab 上。迁移规则会把 SwarmAI 的 `direct` 变成 `floor`，结果 Hive 上永远走不到 native。r2 改为直接删掉，见 §3。
- **Hive 上 native 没有隔离。** 同一台 Hive 上的会话共用一个仓库目录，`pick_hive` 又会把任务派给已经在跑的 Hive。r2 改为每个会话一个 worktree，见 §4.3。
- **pin 下的 create gate 不是确定性的控制，而且和 pipeline 自己的"放弃后重建"协议冲突。** r2 改为复用保留动作的审批，见 §4.2。
- **§4.3 号称复用 Hive 的提问通道，其实是新机制。** 本机到 Hive 没有更新 pin 的路径。r2 并入保留动作审批，见 §4.2。
- **`report → pipeline:research` 理由不成立。** native 会话的教训一样会回来（S2、S7），而 research 不产出提交，仓库里的文档带不回来。r2 改为 `report → native`。
- §1 里 P3、P4、P5 的说法有夸大，已改正。

上游设计：
- `2026-10-28-project-agent-flow.md`：本文取代它 §7 ② "mode 和 profile"那一行和 §14.2 里的 profile。
- `templates/project-agents/STANDARD.md`：本文删掉 `modes[].profile` 和 `modes[].profile_rules`。
- `2026-10-30-swarm-out-dispatch-card.md`。

## 1. 现在的问题（2026-10-30 读代码，经前提审查核实）

| # | 现象 | 位置 |
|---|---|---|
| P1 | 执行方式只有 pipeline 一种。项目段写死"用 pipeline 跑，profile X"，没有 native。pipeline skill 自己却写着"只在用户选了 pipeline 时用，普通改动走 native"（AGENT R1）。 | `core/task_spec.py:241`；`skills/s_autonomous-pipeline/SKILL.md` 的 description |
| P2 | Project Agent 规定流程的轻重。每个 mode 有起始 profile（`modes[].profile`），还有散文写的 `profile_rules` 往上调。但 profile 是任务形状的属性，有没有复现、是不是有界功能、改不改代码，对每个 Brain 都一样。现在每个 Brain 各写一遍，写法也不同：SwarmAI 的 code-change 是 `direct`，标准写的是 `bugfix`。 | `templates/project-agents/STANDARD.md:60,75,100`；`Projects/*/project-agent.yaml` |
| P3 | 选 profile 的理由算出来了（`profile_reason`），但派发记录没有存它，卡片和面板都看不到这次为什么这样选。 | `core/task_spec.py:90-124`；`core/swarm_out.py:363` |

**根因：** Project Agent 把两件不相干的事放在了一起：
- **这个 Brain 里有哪几类活：** 仓库、环境、检查、skill、交付、护栏。这是 Brain 自己的事。
- **这次要用多重的流程：** 这取决于这一个 intent。

后一件既不在 spec 里定，Hive 上也不约束，最后是 Hive 上的 agent 读一段文字自己决定的。

## 2. 目标形态

Run Spec 由四个决定组成，全部在本机定下来：

| 决定 | 回答什么 | 谁定 | 怎么带到 Hive |
|---|---|---|---|
| **① 路由** | 属于哪个 Brain（包括 General） | 确定性信号；没把握就问人（不变） | 派发记录、pin |
| **② 模式** | 在这个 Brain 里做哪一类活：仓库、setup、检查、skill、交付、能在哪跑、护栏 | Project Agent 的 mode，agent 对照 `when` 选（不变） | 派发记录、pin |
| **③ 执行方式** | `native`，或 `pipeline:<profile>` | **本机 agent 按这个 intent 选**，依据是产品统一的选法（§3）；选的理由记下来 | 派发记录、**pin**、项目段 |
| **④ 验收和交付物** | 做到什么算完成，交付的是一段回答、一份文档还是提交 | agent 按你的话写 | 派发记录、项目段 |

派出去之后，**Hive 不改执行方式**，也不再自己选（§4.2）：pipeline 的 run 由 Hive 后端按 pin 建好，仓库也由后端准备好。

**"确定性"的边界写清楚：** 选执行方式，和今天选 mode、选 profile 一样，是本机 agent 的判断，不是机器算出来的。产品做三件确定的事：
- 给出选法，所有 Brain 共用一份；
- 把选择和理由记下来，显示在卡片上；
- 在 Hive 上按钉住的选择建 run、准备仓库，agent 不再经手；跑完比对。

## 3. 执行方式：Project Agent 不再规定，按 intent 选

### 3.1 删掉什么

- `modes[].profile` 和 `modes[].profile_rules` 从 schema 和标准里删除。Project Agent 只管 Brain 自己的事。
- pin 里的死字段 `profile` 删掉，换成 `execution`（§4.2）。
- 不新增 `escalate` 或 `floor`。SwarmAI 唯一的一条 `profile_rule`（跨前后端、加 store、endpoint 或热路径 hook 时升到 full）讲的其实就是风险，下面的选法已经覆盖。Brain 自己要提醒的审查重点，本来就写在 `watches` 里。

### 3.2 选法（产品统一一份，写在 `s_swarm-out` skill 里，描述取自 `PROFILE_CAPS`）

| 这个 intent | 执行方式 | 为什么 |
|---|---|---|
| 你点名了（"走 pipeline full"、"直接改、不走 pipeline"） | 照你说的 | 你说了算 |
| 问一个问题、做调研、写一份报告或设计，交付物不进仓库 | `native` | 教训照样会回来：native 会话的 S2、S7 都会交回（`hive_lessons`）。research profile 不产出提交 |
| 交付物是仓库里的文档 | 按"改代码"处理 | 文档要以提交的形式带回来 |
| 运维、构建、读 CI | `native` | 对外发送、写生产库这类动作，靠保留动作和危险命令审批拦，pipeline 本来就拦不住它们 |
| 改代码，没有风险 | `native` | AGENT R1 的默认做法；XG 2026-10-30 定了 Hive 上也可以这样 |
| 改代码，有风险：跨模块、公共接口或数据形态、迁移、安全（R1 列的那几类） | pipeline，profile 看要什么样的审查：<br>有复现的缺陷 → `bugfix`（每次都过 Gate-0，带 current/expected/unchanged）<br>有界的新功能 → `full`<br>已知模式 → `trivial`<br>你的原话就是规格 → `direct` | Hive 无人值守，派发这一刻就是 R1 说的"问一次"：卡片上写明选了什么、为什么，你可以叫回来重派。**这是一条新规定，不是照搬 R1**：本机 R1 在没人回答时默认 native，Hive 上有风险的改动默认走 pipeline |

- 拿不准的时候不另外问你：选偏轻的那一种，把理由写上，卡片上你看得见。这是派发卡片设计 §1 里"问你的情况"之外的，不新增提问。
- 拿不准的只有 Brain、两个结果不同的 mode、验收这三样，这些照旧问你。

### 3.3 兼容

- schema 号不变。`normalize` 和 `validate` 不再要求、也不再读 `modes[].profile` 和 `profile_rules`。已有文件里留着的这两个字段会被忽略，表单上显示一条备注："这个字段不再起作用，可以删除"。文件不重写，revision 不变，所以 9 个 Brain 都**不需要重新确认**。
- **为什么不在文件里直接删掉这两个字段：** 旧版本的 Hive 用自己的 `validate` 检查同步过去的定义，它要求每个 mode 都有 profile。这两个字段要等所有 Hive 都升级后，才能从表单上删。
- 新的草稿生成器、表单、模板不再写这两个字段。

## 4. 本机定下来，Hive 只执行

### 4.1 本机，派发前

- `swarm_out spec` 收 `--execution native|pipeline:<profile>`，加 `--why "<一句理由>"`；`--profile` 删掉。spec 里带上 `execution`、`execution_why`。
- `swarm_out dispatch` 带同样的参数。本机按派发参数重新算 spec，这一点不变。派发记录存下 `execution` 和 `execution_why`，P3 的问题就补上了。
- 派发卡片加一行 **执行**，例如："pipeline · bugfix（有复现的缺陷，跨前后端）"，或者"native（一处改动，没有风险）"。

### 4.2 Hive，执行时

- **pin 带上 `execution: {how, profile}`。** 派发请求的 `project_agent` 字段一起带过去，`make_pin` 写进 pin，`_valid_pin` 要求有这个字段。
- **项目段按 `execution` 生成：**
  - native："在这个会话里直接做；完成前跑这些检查；在声明的分支上提交，不推送。"
  - pipeline："这个任务的 pipeline run 用 profile `X`。"
- **run 由 Hive 后端建，agent 不建：**
  - 钉的是 pipeline：会话的 session 行建好、pin 记下的同一时刻（`session_router` 把 `project_agent` 交给 `_published_turn` 的地方），Hive 后端用 `RunEngine.create` 建好这个 run：
    - `session_id` 是这个会话，`owner_source="host"`；
    - profile 是钉住的那个；
    - requirement 是派发的任务原文；
    - 仓库是 §4.3 准备好的工作副本。
  - 项目段只说"这个会话的 run 是 `<run_id>`，从 `status` 开始"。
  - 钉的是 native：不建 run。
  - **pin 下的 `pipeline-v1 create` 一律拒绝**，不问人，拒绝理由写明"这个会话的执行方式已经定了"。
  - 照实写清楚：agent 绕开命令行、直接调引擎，还是能建出 run。这属于故意绕过，结果比对会抓到。正常执行的路径上，没有任何一步需要 agent 自己选执行方式。
- **Hive 上不改执行方式。三个曾经可能偏离的场景，各自怎么处理：**

  | 场景 | 处理 |
  |---|---|
  | agent 不照项目段做 | 结构上消除：run 已经建好，create 被拒 |
  | direct 读出了第二种意思 | 前移：本机只在读不出第二种意思时选 direct；拿不准就选 trivial。Hive 上真遇到歧义，向你提一个关于意图的问题，profile 不变 |
  | native 做到一半发现动到了接口 | 前移：派发前，本机用代码图看 intent 指向的模块影响多大（`code_intel.impact`），作为风险判断的依据。剩下没看出来的部分不改执行方式，照原方式做完；落地前人审 diff，受保护的路径单独批，这一道本来就有 |

  pipeline 协议里"direct 遇到歧义就放弃、改用 trivial 重建"这一条，在 pin 下不适用：run 是后端建的，profile 是派发时定的。
- **结果比对（证据层）：** `/runs` 里已经有声明的执行方式和实际的执行方式（建没建 run、用的哪个 profile，`swarm_out_results.py:809,846`）。两者不一致时，卡片和面板标出"执行方式和声明的不同"。不新增字段。

### 4.3 仓库由 Hive 后端准备，每个会话一份工作副本

- **现在：** 任务说明里写着 clone、fetch bundle、`checkout -B` 这些命令，由 agent 在会话里自己跑（`task_repos.task_text`）。同一个仓库的所有会话共用 `Hive/repos/<host>/<path>`（P6）。所以：
  - checkout 有没有成功，要到 Hive 上才知道；
  - 并发的会话会互相踩；
  - 各会话的 bundle 会混进别的会话的提交。
- **改成：** 会话开始前，由 Hive 后端（接收派发的那一步）按声明的仓库做这些事：
  - `Hive/repos/...` 是共享的 clone，只做 clone 和 fetch，包括 fetch 本机发来的 bundle（`hive_repo_inbox`）；
  - 每个会话一份工作副本，用 `git worktree add Hive/work/<session>/<repo> <sha>` 建出来。
- **失败的处理：** clone 失败、sha 不在仓库里、超时，都算这个派发失败。会话不开始，派发返回原因，卡片显示"没派出去"。这样 checkout 晚才验证的问题，也一起前移了。
- **之后都用工作副本：** 项目段、setup、检查、bundle 都指向这份工作副本；pipeline run 从它建自己的 worktree。
- **回收：** 会话结束、取回之后，工作副本由 Hive 按记录回收，只在 `Hive/work/` 范围内删。
- **为什么这和"本机 daemon 准备仓库"不同：** 早先否掉的方案，是本机 daemon 准备仓库（缓存、clone、移动），五个 HIGH 都出在本机这一步。Hive 是一台专门用来执行的机器，仓库本来就在它上面准备，现在只是把同样的命令从 agent 手里拿到后端来做，变成确定的一步。

### 4.4 版本

- 一台 Hive 有没有这次的改动（pin 里的 `execution`、后端建 run、后端准备仓库、`Hive/work/`），看它上报的能力。做法和 Brain 同步报 `supported` 一样。
- 没有这些能力的 Hive，**派发时拒绝**，提示"先更新这台 Hive"。旧 Hive 不认识 `execution`，就只会照项目段的文字去做，钉住的选择得不到保证。

## 6. 不做什么

- **本机聊天不钉 Project Agent。** 本机 chat tab 照旧走 SwarmAI 自己的 guard 和 R1。把日常对话钉上 Project Agent，会改变每一次对话的行为，要单独设计。
- **不用一个"任务形状"枚举假装确定性。** r1 的形状加风险标记，本质上还是 agent 的判断，只是换成了一种看起来像算出来的写法。r2 直接说明这是判断，然后把判断记下来、显示出来、在 Hive 上执行、事后比对。
- **不加 spec digest。** 派发卡片是派发之后从记录生成的，中间没有确认步骤。本机重新算 spec，再加上 revision 比对，已经能保证"派出去的就是按这些参数算出来的"。

## 7. 验证计划（定在这里）

**谁读新写的东西：** `execution` 的读取方有：项目段、pin、后端建 run、create 的拒绝、派发卡片、结果比对，每一处都在 §5 里列了。每会话工作副本的读取方：任务说明、setup、检查、bundle、清理任务。

**最终测试集（必须一直成立的不变量）：**
1. `execution` 从 `spec` 经 dispatch、`_pin_request`、Hive 上的 `make_pin`，原样到达 pin，往返一次验证（P4 的回归）。
2. 钉的是 pipeline 时，会话开始就已经有这个 run（profile、requirement、owner 都对得上）；钉的是 native 时，没有 run。pin 下 agent 调 create 一律被拒；没有 pin 的会话不受影响。
3. 项目段：native 和 pipeline 各自生成正确的那一段；native 那段不出现"用 pipeline 跑"。
4. 旧定义：带 `profile` 和 `profile_rules` 的文件能读、能确认、能派发，revision 不变；不带这两个字段的文件也能通过校验。
5. 两个会话在同一台 Hive 上处理同一个仓库：各自有工作副本，各自的 bundle 只含各自的提交。仓库准备失败（sha 不在仓库里）时，派发返回失败，会话没有开始。
6. 声明 `pipeline:bugfix`、实际跑的是 `direct`（或者声明 native、实际建了 run）：卡片上标出不一致。
7. 没有这些能力的 Hive：派发被拒绝，并说明原因。

**审查：**
- 本文：前提审查已经做过一轮（r2 就是按它改的），不再做第二轮。实现时由测试来验证设计。
- 实现：
