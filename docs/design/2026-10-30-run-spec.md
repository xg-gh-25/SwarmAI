# Run Spec：一个 Intent 在本机定完怎么做，Hive 只执行

**XG 2026-10-30：**
- intent → run spec 在本机全部定好：路由到哪个 Brain 和 Project Agent、用 native 还是 pipeline、用哪个 profile，其他该准备的也都准备好，不留到 Hive 上再判断。
- profile 不该由 Project Agent 规定，而是按 intent 选。
- Hive 上改代码可以走 native。
- 要系统性的方案，不打补丁：Project Agent 没用对，就重构。

**r4.2（实现第 1–3 步时补的，不改方向）：**
- **交回什么也在本机定：** `spec` / `dispatch` 加 `--returns answer|document|commits`，和 `--execution` 一样由本机 agent 按 skill 的表选。只有 `commits` 让仓库可写，其余一律只读。`admit` 拒绝不一致的组合：会落地代码的 profile 必须是 `commits`，`pipeline:research` 不能是 `commits`，没有仓库的 Brain 不能是 `commits`。项目段的交付说明按 `returns` 写，不再看 mode 名或 profile。
- **工作区准备是一个单独的请求：** Host 先调 Hive 的 `POST /api/hive/work`（会话开始之前，有自己的挂起保护 `PREPARE_TIMEOUT_S`，第一次 clone 一个大仓库要几分钟是正常的），拿回 Hive 实际准备好的工作区，再按它写任务说明、带着 `work_id` 开会话。`work_id` 就是 dispatch id，由 Host 先生成。Hive 的 chat 入口只接受一个已准备好、还没开始过的 `work_id`，并在会话有 id 时把它绑上。开会话失败（拒绝、出错）时 Host 通知 Hive 回收；"可能已在跑"时不回收。
- **能力检查：** Hive 的 `admission-state` 带 `work_orders: true`。没有这一项的 Hive，在同步 Brain 之前就拒绝派发，提示先更新。
- **Hive 后端跑 git 时不执行 agent 写的任何配置（实现中按 security 审查改了布局）。** §4.3 原来让各会话做共享 clone 的 git worktree。但 worktree 共用共享 clone 的 `.git`：agent 能在里面写配置，甚至放一个 `commondir` 把 git 引向它自己写的配置。这样 daemon 下一次 fetch 或签出时，就会执行 agent 配置的命令，绕过 agent 的 gate。"使用前重写配置"不是边界，因为 agent 可以在重写和使用之间再改一次。实现改成下面这样：
  - daemon 只在自己的 bare mirror（`<数据目录>/hive/mirrors/`，不在工作区）里 fetch，agent 从不在那里工作；
  - 每个任务的仓库是 daemon 在会话开始前从 mirror 新建的一份独立 clone（`--reference` 共享对象），签出的时候这份 clone 的配置是 daemon 刚写的；
  - 工作单存在 `<数据目录>/hive/orders/`，agent 改不到；
  - 纵深防御：最小环境变量；会执行命令的配置项在命令行上固定死；不读全局和系统配置；关掉 hook；mirror 里出现 `commondir`、`gitdir`、`alternates` 或链接就拒绝。
  - 会话分支 `hive/<dispatch>` 在任务自己的 clone 里，回收时随 clone 一起删掉。它的提交在每轮结束时已经封进 run record，Host 是从那里取回的。
  - 代价：后端 clone 不用全局配置里的凭据，需要凭据的私有仓库现在本来就被拒收（派单中心 §2.2）。
- 一个工作单只能开一个会话：chat 入口原子地认领工作单（`.claim` 独占创建），第二个请求被拒绝。
- 回收清理按"最后一次有改动"计时，不按准备时间：任务 clone 的 HEAD、index、reflog，以及 outputs 目录的修改时间都算，正在用的单子不会被清掉。
- **远端不可达时：** 本机发来的是整条分支的 bundle（本机分支没有跟踪远端时就是这样），后端直接从 bundle clone。
- 回收时直接删掉这份工作单的目录和记录，不跑 git。
- **后端建 run（第 4 步）：**
  - run id 由 Host 按 dispatch id 定（`run_` + dispatch id 的前 8 位十六进制），所以项目段里能写明"这个会话的 run 是哪个、从 `status` 开始"。
  - pin 带上 `execution`（how、profile、run_id、requirement），Hive 把工作单里可写的 clone 作为 run 的仓库根。
  - Hive 在记下 pin 的同一步、会话第一条消息到模型之前建好 run：owner 是这个会话，`owner_source="host"`。建不出来，会话不开始。
  - requirement 就是任务原文。超过 run 能收的长度（`REQUIREMENT_MAX`）时：`direct` 在本机就拒收，其他 profile 不带 requirement，由 run 自己写。
  - General（不属于任何 Brain）的任务不能走 pipeline，因为 run 要归属到一个 Brain 的项目，`admit` 会拒绝。
  - pin 下的 `pipeline-v1 create` 一律拒绝：执行方式是派发时定的，pipeline 会话的 run 已经建好，native 会话本来就没有 run。只提到 CLI、并不执行它的命令（grep、echo）不受影响。

  - 没有仓库的任务只有这个目录；
  - 工作区在 Host 了结这单时回收（r4.1：原来写的是 Hive 收尾时回收，那样会先于验收）。

## 2. 目标形态

Run Spec 由四个决定组成，全部在本机定下来：

| 决定 | 回答什么 | 谁定 | 怎么带到 Hive |
|---|---|---|---|
| **① 路由** | 属于哪个 Brain（包括 General） | 确定性信号；没把握就问人（不变） | 派发记录、pin |
| **② 模式** | 在这个 Brain 里做哪一类活：仓库、setup、检查、skill、交付、能在哪跑、护栏 | Project Agent 的 mode，agent 对照 `when` 选（不变） | 派发记录、pin |
| **③ 执行方式** | `native`，或 `pipeline:<profile>` | **本机 agent 按这个 intent 选**，依据是产品统一的选法（§3）；选的理由记下来 | 派发记录、**pin**、项目段 |
| **④ 验收和交付物** | 做到什么算完成，交付的是一段回答、一份文档还是提交 | agent 按你的话写 | 派发记录、项目段 |

派出去之后，**Hive 不改执行方式**，也不再自己选（§4.2）：pipeline 的 run 由 Hive 后端按 pin 建好，仓库也由后端准备好。

### 2.1 Host 是指挥中心：Run Spec 就是一张派工单

**Host（本机）是唯一下命令的地方。** 判断都在 Host 上做完，写进派工单：
- 属于哪个 Brain、哪个 mode；
- 用什么执行方式；
- 每个仓库怎么用；
- 交回什么。

**Hive 是执行方，分两半，各干一件事：**

| 谁 | 做什么 | 不做什么 |
|---|---|---|
| **Hive 后端** | 把派工单落成实物：准备工作区（§4.3）、钉 pin、按执行方式建 run（§4.2）。按单子交回结果：bundle、文件、教训、记录。Host 了结这单时按它的通知回收工作区 | 不做任何判断 |
| **Hive 上的 agent** | 在已经摆好的工作区里，按已经定下的执行方式干活，跑单子上的检查 | 不选执行方式，不建 run，不 clone、不 checkout，不自己决定交回什么 |

派工单的结构（派发记录里存的就是它，卡片显示的也是它）：

```
work_order:
  who:     {brain, mode, revision}                         # 路由 + Project Agent
  how:     {execution: native | pipeline:<profile>, why}   # §3
  where:   repos: [{name, url, sha, ref, access: read|write}]   # §4.3，access 由交付物定
           out: true                                       # 不进仓库的交付物放这里
  checks:  {setup: [...], validations: [...]}              # 来自 mode
  returns: {deliverable: answer|document|commits, delivery: bundle}
  limits:  {reserved: [...], gates: [...], skills: [...]}  # 来自 Project Agent
  done:    {acceptance}
  task:    <原话 + 范围说明>
```

**落不成实物就是派发失败。** clone 不了、sha 不在仓库里、Brain 同步不上、run 建不出来，任何一项失败，会话都不开始。派发返回原因，Host 上的卡片显示"没派出去"。不会出现 Hive 跑到一半才发现单子做不到的情况。

**"确定性"的边界写清楚：** 选执行方式，和今天选 mode、选 profile 一样，是本机 agent 的判断，不是机器算出来的。产品做三件确定的事：
- 给出选法，所有 Brain 共用一份；
- 把选择和理由记下来，显示在卡片上；
- 在 Hive 上按钉住的选择建 run、准备仓库，agent 不再经手；跑完比对。

## 3. 执行方式：Project Agent 不再规定，按 intent 选

### 3.1 删掉什么

- `modes[].profile` 和 `modes[].profile_rules` 从 schema 和标准里删除。Project Agent 只管 Brain 自己的事。
- pin 里的死字段 `profile` 删掉，换成 `execution`（§4.2）。
- 不新增 `escalate` 或 `floor`。SwarmAI 唯一的一条 `profile_rule`（跨前后端、加 store、endpoint 或热路径 hook 时升到 full）讲的其实就是风险，下面的选法已经覆盖。Brain 自己要提醒的审查重点，本来就写在 `watches` 里。

### 3.2 选法（产品统一一份，写在 `s_swarm-out` skill 里，描述取自 `PROFILE_CAPS`）

| 这个 intent | 执行方式 | 为什么 |
|---|---|---|
| 你点名了（"走 pipeline full"、"直接改、不走 pipeline"） | 照你说的 | 你说了算 |
| 问一个问题、做调研、写一份报告或设计，交付物不进仓库 | `native` | 教训照样会回来：native 会话的 S2、S7 都会交回（`hive_lessons`）。research profile 不产出提交 |
| 交付物是仓库里的文档 | 按"改代码"处理 | 文档要以提交的形式带回来 |
| 运维、构建、读 CI | `native` | 对外发送、写生产库这类动作，靠保留动作和危险命令审批拦，pipeline 本来就拦不住它们 |
| 改代码，没有风险 | `native` | AGENT R1 的默认做法；XG 2026-10-30 定了 Hive 上也可以这样 |
| 改代码，有风险：跨模块、公共接口或数据形态、迁移、安全（R1 列的那几类） | pipeline，profile 看要什么样的审查：<br>有复现的缺陷 → `bugfix`（每次都过 Gate-0，带 current/expected/unchanged）<br>有界的新功能 → `full`<br>已知模式 → `trivial`<br>你的原话就是规格 → `direct` | Hive 无人值守，派发这一刻就是 R1 说的"问一次"：卡片上写明选了什么、为什么，你可以叫回来重派。**这是一条新规定，不是照搬 R1**：本机 R1 在没人回答时默认 native，Hive 上有风险的改动默认走 pipeline |

- 拿不准的时候不另外问你：选偏轻的那一种，把理由写上，卡片上你看得见。这是派发卡片设计 §1 里"问你的情况"之外的，不新增提问。
- 拿不准的只有 Brain、两个结果不同的 mode、验收这三样，这些照旧问你。

### 3.3 兼容

- schema 号不变。`normalize` 和 `validate` 不再要求、也不再读 `modes[].profile` 和 `profile_rules`。已有文件里留着的这两个字段会被忽略，表单上显示一条备注："这个字段不再起作用，可以删除"。文件不重写，revision 不变，所以 9 个 Brain 都**不需要重新确认**。
- **为什么不在文件里直接删掉这两个字段：** 旧版本的 Hive 用自己的 `validate` 检查同步过去的定义，它要求每个 mode 都有 profile。这两个字段要等所有 Hive 都升级后，才能从表单上删。
- 新的草稿生成器、表单、模板不再写这两个字段。

## 4. 本机定下来，Hive 只执行

### 4.1 本机，派发前

- `swarm_out spec` 收 `--execution native|pipeline:<profile>`，加 `--why "<一句理由>"`；`--profile` 删掉。spec 里带上 `execution`、`execution_why`。
- `swarm_out dispatch` 带同样的参数。本机按派发参数重新算 spec，这一点不变。派发记录存下 `execution` 和 `execution_why`，P3 的问题就补上了。
- 派发卡片加一行 **执行**，例如："pipeline · bugfix（有复现的缺陷，跨前后端）"，或者"native（一处改动，没有风险）"。

### 4.2 Hive，执行时

- **pin 带上 `execution: {how, profile}`。** 派发请求的 `project_agent` 字段一起带过去，`make_pin` 写进 pin，`_valid_pin` 要求有这个字段。
- **项目段按 `execution` 生成：**
  - native："在这个会话里直接做；完成前跑这些检查；在声明的分支上提交，不推送。"
  - pipeline："这个任务的 pipeline run 用 profile `X`。"
- **run 由 Hive 后端建，agent 不建：**
  - 钉的是 pipeline：会话的 session 行建好、pin 记下的同一时刻（`session_router` 把 `project_agent` 交给 `_published_turn` 的地方），Hive 后端用 `RunEngine.create` 建好这个 run：
    - `session_id` 是这个会话，`owner_source="host"`；
    - profile 是钉住的那个；
    - requirement 是派发的任务原文；
    - 仓库是 §4.3 准备好的工作副本。
  - 项目段只说"这个会话的 run 是 `<run_id>`，从 `status` 开始"。
  - 钉的是 native：不建 run。
  - **pin 下的 `pipeline-v1 create` 一律拒绝**，不问人，拒绝理由写明"这个会话的执行方式已经定了"。
  - 照实写清楚：agent 绕开命令行、直接调引擎，还是能建出 run。这属于故意绕过，结果比对会抓到。正常执行的路径上，没有任何一步需要 agent 自己选执行方式。
- **Hive 上不改执行方式。三个曾经可能偏离的场景，各自怎么处理：**

  | 场景 | 处理 |
  |---|---|
  | agent 不照项目段做 | 结构上消除：run 已经建好，create 被拒 |
  | direct 读出了第二种意思 | 前移：本机只在读不出第二种意思时选 direct；拿不准就选 trivial。Hive 上真遇到歧义，向你提一个关于意图的问题，profile 不变 |
  | native 做到一半发现动到了接口 | 前移：派发前，本机用代码图看 intent 指向的模块影响多大（`code_intel.impact`），作为风险判断的依据。剩下没看出来的部分不改执行方式，照原方式做完；落地前人审 diff，受保护的路径单独批，这一道本来就有 |

  pipeline 协议里"direct 遇到歧义就放弃、改用 trivial 重建"这一条，在 pin 下不适用：run 是后端建的，profile 是派发时定的。
- **结果比对（证据层）：** `/runs` 里已经有声明的执行方式和实际的执行方式（建没建 run、用的哪个 profile，`swarm_out_results.py:809,846`）。两者不一致时，卡片和面板标出"执行方式和声明的不同"。不新增字段。

### 4.3 工作区：按任务类型安排，由 Hive 后端准备

**现在的问题：** 任务说明里写着 clone、fetch bundle、`checkout -B` 这些命令，由 agent 在会话里自己跑（`task_repos.task_text`）。同一个仓库的所有会话共用 `Hive/repos/<host>/<path>`（P6），所以：
- checkout 成没成功，要到 Hive 上才知道；
- 并发的会话会互相踩；
- 各会话的 bundle 会混进别的会话的提交。

而且现在只考虑了改代码的任务。

**一个会话的工作区（Hive 后端在会话开始前建好）：**

```
Hive/repos/<host>/<path>/            共享的 clone：只做 clone 和 fetch（包括本机发来的 bundle），谁都不在这里干活
Hive/work/<dispatch>/
    repos/<name>/                    这个会话的 worktree，每个仓库一个
Outputs/<dispatch>/                  不进仓库的交付物（报告、数据、图）
```

交付物目录不放在 `Hive/` 下面：取回文件时，`hive_files.safe_rel` 拒收所有以 `Hive/` 开头的路径（`hive_files.py:62`），那是 bridge 的内部区域。

**每个仓库只读还是可写，由 Host 在派工单上定，依据是交付物：** 交付物是提交的仓库为 `write`，其余为 `read`。

| 任务类型（例子） | 执行方式 | 仓库 | worktree | 交回什么 |
|---|---|---|---|---|
| 问答、调研，不涉及仓库（General Brain，Library 知识） | native | 无 | 没有，只有 `Outputs/<dispatch>/` | 回答；`Outputs/<dispatch>/` 里的文件回到 Brain 的 `deliverables/hive/` |
| 读代码出报告（比如"dive deep 最近的改动"） | native | `read` | `git worktree add --detach repos/<name> <sha>` | 报告文件。没有 bundle：只读的仓库不打包，就算误提交了也不会带回 |
| 运维、构建、读 CI | native | `read` | 同上，detached | 结论；构建产物要交回的，放进 `Outputs/<dispatch>/` |
| 仓库里的文档（设计文档、README） | 按改代码选（§3.2） | `write` | 同下 | 同下 |
| 改代码，native | native | `write` | `git worktree add -b hive/<dispatch> repos/<name> <sha>` | bundle `sha..hive/<dispatch>` |
| 改代码，pipeline | pipeline:`<profile>` | `write` | 同上。后端建 run 时 `repo_roots` 指向这个 worktree，run 从会话分支分出自己的 worktree，落地落回会话分支（`engine._create_worktree` 要求主检出在一个分支上，会话分支正好满足） | bundle `sha..hive/<dispatch>`，和 native 一样 |
| 跨多个仓库 | 按上面规则 | 每个仓库各自 `read` 或 `write` | 每个仓库各自一个 | 每个可写仓库各一个 bundle |

**为什么这样安排：**
- **一套规则，所有任务类型都适用。** pipeline 在 Hive 上的位置，和它在本机的位置一样：本机上 run 从主检出分出来、落回主检出；Hive 上会话分支就是这个会话的"主检出"。native 和 pipeline 的交回都是同一个 `sha..hive/<dispatch>`，bundle 和本机取回、人审落地都不用为执行方式写两套。
- **共享 clone 不被任何会话改动。** 会话之间只共享对象库：worktree 共用 `.git` 的对象，磁盘上增加的只是检出的文件。
- **只读就是真的只读。** 不打包，不交回。派工单说只读的仓库，Hive 上即使有人提交，也带不出来。
- **会话分支只在 Hive 本地，不推送**（Hive 没有推送凭据，不变）。名字用 dispatch id，同一个会话后续的几轮还在这个分支上继续，只审、只落上次落地之后的新提交（`hive_return` 已有）。

**准备的步骤（Hive 后端，接收派发时，在会话开始之前）：**
1. 对每个仓库：共享 clone 不存在就 clone，存在就 fetch；本机发来了 bundle（`hive_repo_inbox`）就再 fetch 它。
2. 确认 `sha` 在共享 clone 里，不在就算派发失败。
3. 按 `access` 建 worktree，`Outputs/<dispatch>/` 一定建。
4. 写一份工作区清单 `Hive/work/<dispatch>/order.json`，记下每个仓库的路径、access、sha、分支。项目段、setup、检查、`repo_facts`、bundle 和回收都读这一份，不各自去拼路径。
5. 任何一步失败：删掉已经建了一半的 `Hive/work/<dispatch>/`（只在这个目录里删），派发返回原因。

**回收：** 只在 Host 了结这单的时候回收（派单中心设计 `2026-10-30-dispatch-center.md` §6），不在 Hive 写下 `closed` 记录时回收。`closed` 在会话收尾后十分钟左右就写下了，比验收早得多，如果那时回收，"不通过之后补做"就没有工作区可用了。

Host 了结时调用 `POST /api/hive/work/{dispatch}/release`，Hive 后端：
- 会话还在跑，或者最后一个 bundle 还没被取走，就拒绝这次回收；
- 否则 `git worktree remove` 这个会话的每个 worktree，删掉 `Hive/work/<dispatch>/` 和 `Outputs/<dispatch>/`，只删这两处；
- 从来没被了结的单子，按已有的 `RETENTION_DAYS`（30 天）兜底回收。

会话分支 `hive/<dispatch>` 保留到它的提交落地或被拒绝，所以以后还能对照。

**项目段里写什么：** 只写派工单上已经定下的事。例如：

```
Workspace (prepared for this task):
- repos/swarmai: swarmai at a680d1a0, read-only
- Outputs/<dispatch>/: put documents and other deliverables here
```

可写的仓库写成："repos/swarmai: swarmai at a680d1a0 on branch hive/so_…; commit here, do not push"。项目段里不再出现 clone、checkout 这类命令。

**为什么这和"本机 daemon 准备仓库"不同：** 早先否掉的是由本机 daemon 准备仓库（缓存、clone、移动），五个 HIGH 都出在本机这一步。Hive 本来就是执行机，仓库本来就在它上面准备。这里只是把 agent 手里的那几条命令拿给 Hive 后端来做，变成确定的一步。

### 4.4 版本

- 一台 Hive 有没有这次的改动（pin 里的 `execution`、后端建 run、后端准备仓库、`Hive/work/`），看它上报的能力。做法和 Brain 同步报 `supported` 一样。

## 6. 不做什么

- **本机聊天不钉 Project Agent。** 本机 chat tab 照旧走 SwarmAI 自己的 guard 和 R1。把日常对话钉上 Project Agent，会改变每一次对话的行为，要单独设计。
- **不用一个"任务形状"枚举假装确定性。** r1 的形状加风险标记，本质上还是 agent 的判断，只是换成了一种看起来像算出来的写法。r2 直接说明这是判断，然后把判断记下来、显示出来、在 Hive 上执行、事后比对。
- **不加 spec digest。** 派发卡片是派发之后从记录生成的，中间没有确认步骤。本机重新算 spec，再加上 revision 比对，已经能保证"派出去的就是按这些参数算出来的"。

## 7. 验证计划（定在这里）

**谁读新写的东西：** `execution` 的读取方有：项目段、pin、后端建 run、create 的拒绝、派发卡片、结果比对，每一处都在 §5 里列了。每会话工作副本的读取方：任务说明、setup、检查、bundle、清理任务。

**最终测试集（必须一直成立的不变量）：**
1. `execution` 从 `spec` 经 dispatch、`_pin_request`、Hive 上的 `make_pin`，原样到达 pin，往返一次验证（P4 的回归）。
2. 钉的是 pipeline 时，会话开始就已经有这个 run（profile、requirement、owner 都对得上）；钉的是 native 时，没有 run。pin 下 agent 调 create 一律被拒；没有 pin 的会话不受影响。
3. 项目段：native 和 pipeline 各自生成正确的那一段；native 那段不出现"用 pipeline 跑"。
4. 旧定义：带 `profile` 和 `profile_rules` 的文件能读、能确认、能派发，revision 不变；不带这两个字段的文件也能通过校验。
5. 工作区：
   - 两个会话在同一台 Hive 上处理同一个仓库：各自有 worktree，共享 clone 的 HEAD 和分支不变，各自的 bundle 只含各自的提交；
   - 只读仓库是 detached 的，不出 bundle；
   - pipeline run 落回会话分支，bundle 和 native 的形状一样；
   - 没有仓库的任务只有 `Outputs/<dispatch>/`；那里的文档能回到 Brain；
   - 准备失败（sha 不在仓库里）时派发返回失败，会话没有开始，`Hive/work/<dispatch>/` 不留下；
   - 回收只在 Host 了结时发生，只删 `Hive/work/<dispatch>/` 和 `Outputs/<dispatch>/`；会话还在跑或 bundle 没被取走时拒绝；会话分支保留。
6. 声明 `pipeline:bugfix`、实际跑的是 `direct`（或者声明 native、实际建了 run）：卡片上标出不一致。
7. 没有这些能力的 Hive：派发被拒绝，并说明原因。
