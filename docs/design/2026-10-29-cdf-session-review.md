# CDF 会后复盘

本文是 CDF（`2026-10-26-swarm-cognitive-distillation-flow.md`）r16.15 的完整设计。CDF 主文档 §5.13 只保留摘要并指向本文。复盘之后的流程（判断卡、目的地规则、污染、配额、单一写入口、Flow）沿用 CDF 主文档，本文不重复。

## 1. 要解决的问题

CDF 现在靠 S2 主提取沉淀会话里的判断：会话结束后，另一个模型分窗重读整段聊天记录，从文字里还原当时做了什么判断。这样做有三个问题：

1. **信息丢了一半。** 做判断的那一刻，Agent 知道考虑过哪些方案、为什么放弃、依据是什么。事后重读只能看到留在文字里的痕迹，"为什么"和"放弃了什么"最容易丢，而这正是最有价值的部分。
2. **成本最高。** S2 主提取每天读入 200 万到 400 万 token（CDF §12），读的大多是工具输出。
3. **复杂度大多是它带来的。** 分窗、窗口重叠、跨窗口看不到上下文、每个窗口登记证据，都是因为要重读很长的记录。

## 2. 目标和边界（用户 2026-10-29 确定）

- **用户无感。** 不在用户的回合里做任何额外的事，不让用户等，不打断。
- **不频繁。** 只有两个保底触发：任务结束、用户立规矩或纠正。不做测试红变绿这类针对编程的触发。
- **不只是代码。** research、写文档、做 deck、做 mockup、brainstorm 同样重要。触发条件、提示和去向都不能偏向代码库。
- **Agent 也要成长。** Agent 自己的认知（它怎么判断、哪里错、什么做法可靠），只要有价值就进 EVOLUTION 和 MEMORY。Agent 不只是替人记事，它是一个要自我进化的个体。
- **不过度设计。** 能复用的都复用：S2 的后台任务队列、提取器的扁平 schema、SDK 自带的会话恢复和结构化输出、现有的检测 hook。

## 3. 总体方案

```
会话进行中（用户回合里什么都不加）
  ├─ 用户说"记住这个" ──────────► S1 当场入队并回显（不变）
  └─ hook 只记信号：用户消息数、工具调用数、写过的文件、立规矩或纠正

会话空闲 10 分钟或关闭，且有实质内容
  └─► 排一条复盘任务（ingestion_s2_jobs，kind=review）

后台任务线程（串行，主机忙时等待，先看内存预算）
  ├─ 能恢复：SDK resume + fork_session，无工具，output_format = 扁平单元 schema
  │          问事后回顾四问 ──► S7 单元 ──► inbox ──► 判断卡 ─► 写入（不变）
  └─ 不能恢复：退回 S2 主提取（现有做法）

每个会话照跑：S2 用户原话那一遍（只读用户写的字）
抽样 10% 的会话：S2 主提取全量跑一遍，用来测复盘漏了多少
```

## 4. 哪些信息由复盘负责，哪些由别的来源负责

判断标准只有一条：**这条信息在什么时候、由谁掌握得最完整。**

| 信息 | 七类 | 负责的来源 | 理由 |
|---|---|---|---|
| 决定和取舍 | decision | **复盘（S7）** | 只有做决定的上下文里有被放弃的方案和原因 |
| 走错了、被纠正 | correction、pitfall | **复盘**；用户原话部分同时由 S2 用户原话那一遍负责 | 复盘知道错在哪；原话是最可信的证据 |
| 验证有效的做法、流程 | guideline、process | **复盘** | 任务结束时才知道哪些做法真的有效 |
| 心智模型 | model | **复盘** | 查清机制的上下文里才有完整解释 |
| 遗留和待办 | Gap | **复盘** | Agent 知道还差什么 |
| 产出的报告、定稿、读到的有用资料 | Reference | **复盘**；S6、Library 照旧 | 复盘知道哪份东西以后用得上 |
| 用户的规矩、偏好、品味 | USER、STEERING 类 | **S2 用户原话那一遍**（每个会话）；复盘可以补上下文 | 用户自己的话是唯一能进每轮注入文件的证据 |
| 原则 | principle | 不由单次复盘产出；由多条同向的 decision 强化得来（CDF §5.8），或 S5 跨会话挖掘 | 单次会话里写原则容易拔高 |
| 关键事件 | Event | S4（commit）、S3（run） | 已经有确定性来源 |
| Agent 当时没意识到重要的东西、跨会话的模式 | 任意 | S2 主提取抽样、S5 | 只有事后横向看才看得见 |

## 5. 触发

### 5.1 会话里只记信号

不改变用户回合里的任何行为。现有 hook 已经在数的东西，存进会话的复盘计数：

| 信号 | 来源 |
|---|---|
| 用户消息数 | 消息库（已登记的 `user` 事件） |
| 工具调用数 | 现有的 PostToolUse 计数（`create_session_checkpoint` 的 `_tool_count`） |
| 写过的文件（任何路径） | 现有的 `create_file_tracker` |
| 用户立规矩或纠正 | 现有的 UserPromptSubmit 检测器（纠正检测、high-signal 检测），只记下消息 id |

纠正检测器现在会把用户原话整句自动提交成一条 correction。**这一步去掉**：没有上下文的原话写不成离开会话也读得懂的单元。改由复盘来写，原话同时由 S2 用户原话那一遍处理。

### 5.2 什么时候排复盘

从上次复盘的位置（水位，见 §6.3）到现在，满足任意一条，就算"有实质内容"：
- 至少 3 条用户消息；
- 至少 10 次工具调用；
- 写过至少 1 个文件，任何路径都算，包括文档、deck、mockup、报告；
- 有用户立规矩或纠正的信号。

有实质内容后，会话**空闲满 10 分钟**，或者**会话关闭**（现有的会话结束 hook），就排一条复盘任务。一两句的闲聊不复盘。

**Save to Memory 按钮**：立刻排一条复盘任务，不等空闲，也不看门槛（用户明确要求）。

## 6. 复盘任务

### 6.1 运行位置

- 复用 `ingestion_s2_jobs` 和 `S2JobExecutor`（CDF §12 r16.13）。任务表加一列 `kind`（`review` 或 `s2`），schema 放进还没发布的 v7。
- 同一个线程串行执行，不用聊天的线程池。开始前同时看 `ingestion_admission("session")` 和 `ResourceMonitor.spawn_budget()`，主机忙或内存不够就等，不和聊天抢资源。
- 同一个会话同时最多一条任务；运行中又被请求时，跑完再补一次（沿用 `again`）。失败的处理沿用现有规则：退避重试，3 次后标为 failed 并带原因。

### 6.2 恢复会话

- 用 Claude Agent SDK 的 `resume=<sdk_session_id>` 加 `fork_session=True` 打开会话的一个分叉。分叉里的上下文就是 Agent 当时的上下文；原会话的记录一个字都不改，用户的标签页里也看不到这个分叉。
- `allowed_tools=[]`：复盘只想不做。
- `output_format={"type": "json_schema", "schema": flat_unit_schema(允许的 kind)}`，复用提取器同一份 schema（CDF §5.4 r16.14）。结果从 `structured_output` 取，不解析文本。
- 输出上限和超时沿用提取器的预算：16,000 token、300 秒。
- **恢复不了**（找不到 SDK 会话 id、CLI 的会话记录已经不在、恢复报错），就把这条任务改成 `kind=s2`，退回 S2 主提取。

### 6.3 水位

- 每条复盘记下它复盘到哪条消息为止（水位）。下次只看水位之后的新内容是否达到门槛；复盘提示里也只要求总结水位之后的部分，前面已经复盘过。
- 会话被压缩过：分叉里的上下文是压缩后的。复盘照跑；压缩前、水位之后的那一段，再额外排一条 S2 主提取兜底。

### 6.4 产出

- 单元记为 **S7**（会后复盘）。`extraction_attempts.source` 的 CHECK 在 v7 里加上 `S7`。每次复盘记一条 attempt：产出数、无效单元及原因、token。
- 单元交给 `api_v2.enqueue_unit`。之后的判断卡、目的地、配额、写入全部照旧。
- 证据：服务端把这个会话到水位为止的全部内容登记成证据根（复用 S2 的 `window_roots`），作为这次复盘的读取集。复盘不能自报读过什么（CDF §9 防止有选择地引用）。

## 7. 复盘提示

提示里的规则和表格从 `contracts_v2` 生成（`UNIT_RULES`、`SCOPE_RULE`、七类），不另写一份。

**第一步：四问（事后回顾，After-Action Review）**，找出值得记的东西：
1. 本来打算怎样？
2. 实际发生了什么？
3. 两者为什么不一样？答案是 pitfall 或 correction。
4. 下次怎么做？答案是 guideline 或 process。做过的取舍写成 decision，没做完的写成 Gap。

只问"学到了什么"，得到的多半是流水账；四问逼着 Agent 去看预期和实际的差别，经验正是从这里来的。

**第二步：每张卡过三道关**，过不了就不写：
1. 换一个任务还用得上吗？
2. 一个能干、但没参与这次会话的人，不看这条会犯错或走弯路吗？
3. 能指出凭据吗？用户的话、命令或测试的结果、文档段落、commit 都算。

**第三步：写成"情境—判断—理由—证据"**：

| 段 | 字段 | 要求 |
|---|---|---|
| 情境 | `applicability` | 认得出的触发条件，例如"在 worktree 里跑 pytest 时"，不是"开发时" |
| 判断 | `what`；流程类加 `how` | 一句能照做的话 |
| 理由 | `why`；decision 加 `rejected_alternatives` | 为什么，放弃了什么、为什么放弃 |
| 证据 | `evidence` | 凭据的锚点 |

**第四步：用一个问题认出类型**：
- correction：之前哪里做错了？
- pitfall：什么条件下会出错？
- decision：选了哪个、放弃了哪些、为什么？
- guideline：什么做法验证过有效？
- process：哪串步骤的顺序有讲究？
- model：系统为什么是这样？
- principle：单次复盘不写。

**按任务类型各给一个例子**：
- **research**：哪些来源可靠、哪些不可靠、为什么；结论和依据；还没查清的（Gap）。报告本身作为 Reference。
- **文档和 deck**：用户对结构、篇幅、语气的反馈说明了什么；哪种写法被接受、哪种被改掉。定稿作为 Reference。
- **mockup 和设计**：每一轮改了什么、为什么；被否掉的方向和原因。
- **brainstorm**：选定和放弃的想法及原因；还没想清楚的问题；值得以后再拿出来的想法。
- **代码**：根因、修法、被否掉的方案；只有不显然的才写。

**专门问 Agent 自己**（`scope=agent`）：这次我判断错在哪？用户为什么要纠正我？我哪种做法可靠、哪种不可靠？

**有用户立规矩或纠正的信号时**，提示里点明是哪几条消息，要求把它们写成离开上下文也读得懂的单元。

**反例**：操作琐事；没验证的猜测；复述已经注入的记忆；任务局部状态；"我做了 X"的流水账。

## 8. 去向

| 单元 | 去向 |
|---|---|
| 会话属于某个项目时的项目知识（决定、坑、做法、模型、待办） | 那个项目的 DDD（带 `taint: external`）。项目可以不管任何代码仓库 |
| 不属于任何项目的通用知识 | Knowledge |
| Reference（报告、定稿、资料） | Knowledge / Library |
| `scope=agent` 的 Agent 自身认知，满足 §9 | EVOLUTION、MEMORY |
| `scope=agent` 但不满足 §9 | `_common/agent.md`（和 CDF §5.5 S3 被污染的 agent 纠正同一个去处） |
| 用户的规矩和偏好 | 由 S2 用户原话那一遍写进 USER、STEERING；复盘写的同类单元按污染规则改投 DDD |

## 9. Agent 自身认知进 EVOLUTION 和 MEMORY（修改 CDF §9 的一条已确认规则）

- **原规则**：血统里有 `external` 根就算被污染，被污染的单元不进每轮注入的文件。Agent 的会话几乎都读过工具输出，所以它自己的经验实际上永远进不来。
- **新规则**：S7 中 `scope=agent` 的 Cognition（correction、pitfall、guideline、process、model），满足下面两条就可以进 EVOLUTION 和 MEMORY：
  1. 证据里至少有一个 `user` 根（用户的话、用户的纠正）或 `measured` 根（命令和测试的结构化结果、review 结论）；
  2. 卡 1 的蕴含检查确认，这条经验由这些根支撑，而不是由读到的外部文字支撑。外部内容可以作为背景，不能作为唯一依据。
- **剩下的风险**：网页里写着"以后都要这样做"，Agent 照做了，又恰好有一个测试结果能当证据，这条就有可能被写进来。防护：
  - 蕴含检查；
  - EVOLUTION 和 MEMORY 原有的每日配额；
  - 每条写入都能在 Flow 里查到、撤回（CDF §13 墓碑）。

  这是为了让 Agent 能成长而接受的风险，记入 CDF §17 由用户确认。安全基线 B5 的要求（不可信文字不能变成长期指令）由第 2 条和配额兜住，不再是"一律不进"。

## 10. 对现有来源的改动

| 来源 | 改动 |
|---|---|
| S1 | 不变。用户说"记住这个"时当场入队并回显 |
| 纠正检测器 | 去掉自动提交，只给会话记信号 |
| S2 用户原话那一遍 | 不变，每个会话照跑 |
| S2 主提取 | 只在两种情况跑：复盘不了的会话（门槛同 §5.2）；按会话 id 哈希确定性抽样 10%，测漏记率 |
| Save to Memory | 改为立刻排一条复盘 |
| 会话结束 hook | 改为"满足门槛就排复盘"，不再直接排 S2 |
| S3 到 S6 | 不变 |

## 11. 成本和资源

- **每次复盘**：输入大约等于这个会话当前的上下文大小，上限是模型的上下文窗口，压缩后会更小。空闲 10 分钟后提示缓存多半已经过期，所以按全价计。输出预计 2,000 到 4,000 token。
- **和现在比**：一个会话复盘一次，输入大约是这个会话一个上下文窗口；S2 主提取要读完整段记录，长会话远超一个窗口。按 CDF §12 的会话规模估，整体成本预计持平或更低。实测值从 `ingestion_llm_usage` 的 S7 行读，预演报告里给出。
- **内存**：每次复盘起一个 CLI 子进程，同时最多一个，开始前看 `spawn_budget()`。
- **聊天热路径**：只多了 §5.1 的计数（内存里加一，复用现有 hook），不做 I/O。复盘任务在聊天之外的线程上运行。

## 12. 怎么知道它管用

全部放进 Flow 健康区，按天统计：
- **漏记率（主指标）**：抽样会话里，S2 主提取找到、但复盘没有覆盖的有价值单元占多少；"覆盖"由卡 1 的比对判定。**按会话类型分开报**：有代码改动 / 写过非代码文件 / 只有对话。
- **复盘的产出和质量**：每次复盘的单元数；判断卡通过的比例；被拒原因的分布；产出为零的复盘占多少。
- **Agent 自身认知**：每周进入 EVOLUTION 和 MEMORY 的 `scope=agent` 单元数，以及被用户撤回的比例。
- **成本**：每次复盘的输入和输出 token；恢复失败、退回 S2 的比例。

## 13. 实施步骤

0. **先验证**（半天，不写产品代码）：在 dev backend 上确认一个已关闭的会话能用 `resume` 加 `fork_session` 恢复；`output_format` 能拿到 `structured_output`；原会话的记录没被改动；看一次复盘的 token 和耗时。任何一条不成立，回到本文修改方案。
1. **任务和触发**：`ingestion_s2_jobs.kind`、水位、§5 的信号计数和门槛、空闲 10 分钟检测、会话结束 hook 和 Save to Memory 改为排复盘。
2. **复盘执行**：分叉恢复、结构化输出、S7 source（v7 的 CHECK）、证据登记、恢复不了时退回 S2。
3. **复盘提示**：从契约生成；按任务类型的例子；用户信号的点名。
4. **去向和 §9 新规则**：`scope=agent` 的条件、蕴含检查的输入、Flow 里的撤回入口。
5. **S2 改为兜底**：主提取只在 §10 的两种情况跑；10% 抽样；按会话类型分开统计漏记率。
6. **去掉纠正检测器的自动提交。**

每一步都写测试并做 mutation 检查（撤掉修复，测试必须变红）。第 1 步要量出 hook 计数的耗时。

## 14. 不做

- 不在用户回合里提醒，不拦截回合结束。
- 不做针对编程的触发（例如测试红变绿）。
- 不在 AGENT.md 里加"记得随时记录"一类的规则。
- 不改判断卡的格式（CDF §14.1 第 4 项，上线后按数据再做）。

## 15. 待验证的假设

| 假设 | 不成立时 |
|---|---|
| 已关闭的会话还能用 SDK 恢复（CLI 的会话记录还在，SDK 会话 id 已持久化） | 这类会话退回 S2 主提取；如果比例很高，重新考虑在会话还活着、空闲时复盘 |
| `fork_session` 不改原会话的记录 | 改用只读副本恢复 |
| 一次复盘的成本不高于同一个会话的 S2 主提取 | 复盘时用 `resume_session_at` 只加载水位之后的部分（会丢掉前面的上下文，需要权衡） |
| 10 分钟的空闲是"任务结束"的合理信号 | 按实测的复盘产出调整空闲时长 |

## 16. 实现说明（2026-10-29，实现时定下的细节，覆盖上文的对应说法）

- **信号不在聊天路径上计数**（取代 §5.1）：复盘任务开始时，从消息库里读水位之后的记录现算：用户消息数、工具调用数（assistant 消息里的 `tool_use` 块）、写过的文件（`Write`、`Edit`、`MultiEdit`、`NotebookEdit` 调用）、用户立规矩或纠正（用现有检测器的同一组正则重新匹配用户消息）。聊天路径上一行代码都不加。
- **空闲 10 分钟**（实现 §5.2）：现有的 `LifecycleManager._fire_idle_hooks` 在会话空闲 120 秒后触发会话结束 hook，每次空闲只触发一次。hook 把任务的 `next_attempt_at` 设为"现在 + 8 分钟"；用户又说话、再次空闲时，再往后推。执行线程只认领到点的任务。按钮立刻到点。
- **SDK 会话 id**：`HookContext` 增加 `sdk_session_id`，由 `_build_hook_context` 从 `SessionUnit._sdk_session_id` 填入，排任务时存进任务行。按钮从 router 取（活着的会话取 unit 上的，否则取持久化的那份）。没有 id 的任务直接退回 S2 主提取。
- **恢复的工作目录**：从 CLI 自己的会话记录里读。`leak_transcript.find_transcript` 定位文件，取记录里的 `cwd` 字段；找不到就当作恢复不了。
- **运行方式**：在执行线程里用 `asyncio.run` 调 SDK 的 `query()`，参数为 `resume`、`fork_session=True`、`tools=[]`（`--tools ""`，真正不给工具；`allowed_tools=[]` 在这个 SDK 里等于全部允许）、`output_format`、`cwd`、`max_turns=1`、`strict_mcp_config=True`、`setting_sources=[]`。CLI 路径和环境变量复用后台任务的 `jobs.executor._resolve_claude_cli` 和 `_build_cli_env`。超时 300 秒。
- **证据索引**（补上 §6.4 的缺口）：分叉里的聊天记录看不到证据编号。复盘提示末尾附一份索引：水位之后每条用户消息的锚点和开头 120 个字，以及每个 measured 根的锚点、字段名和值。证据清单 = 索引里的锚点。复盘的读取集 = 这个会话的全部用户根，加上水位之后所有窗口登记的根（`window_roots`）。
- **每次任务做什么**：先跑 S2 用户原话那一遍（每个会话都跑）；再复盘；恢复不了就跑 S2 主提取；会话 id 哈希落在 10% 里，再额外跑一遍 S2 主提取（测量用）。
- **§9 新规则的实现**：在 `pipeline_v2` 里，路由之前判断。S7、`scope=agent`、类型属于 correction、pitfall、guideline、process、model 的 Cognition：如果它引用的根里至少有一个 `user` 或 `measured` 根，就用现有的蕴含判断卡，拿这些根的原文（用户写的字、measured 字段的值）去判断；判为蕴含，这个单元按不污染路由；否则照旧按污染处理。判断卡不可用时推迟（和 S1 一致）。
- **度量**：每次复盘的 attempt 在 `evidence_range` 里记会话类型（有代码改动 / 写过非代码文件 / 只有对话）、是否抽样、各项信号的数值，token 记在 `ingestion_llm_usage` 的 S7 行。漏记率的计算和 Flow 里的展示放到第一次批量评测时做。
- **分叉的会话记录**：每次复盘会在 CLI 的会话目录里留下分叉自己的记录文件。复盘结束后删掉这个文件，原会话的文件不动。
- **measured 证据的边界**：库里只存 measured 根的哈希，不存值。所以 §9 的蕴含检查只能拿用户原话去比，只有 measured 证据的 Agent 经验暂时留在 DDD，进不了 EVOLUTION 和 MEMORY。复盘提示里的证据索引能显示 measured 的值，因为值可以从这一段聊天记录里读回来。
- **恢复不了的会话**：退回 S2 主提取时，读的是整个会话，不只是水位之后的部分；重复的单元照常由写入端判为已存在。
