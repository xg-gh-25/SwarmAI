# CDF 重构：谁有上下文谁判断

日期 2026-10-29 · 状态：诊断 + 方案，待用户决定

## 1. 结论

CDF 的问题不在某一张卡的阈值，而在三处结构：

1. **权力倒置。** 主线来源 S7 是 Agent 带着会话上下文复盘自己，它已经给出了类型、scope 和依据。之后一个零上下文的判官（卡 1）重新判类型、scope、形状、项目和 7 项质量，并且有否决权。知道得多的一方提议，知道得少的一方决定。
2. **信任按会话算，不按单元算。** 会话里读过任何外部内容，S7 的全部单元就带污染，进不了每轮注入的文件。为了让用户的话还能进 STEERING/USER，又加了一遍"只读用户原话"的 S2 提取，两遍抽同一句话，产生重复，也产生编造。被污染的单元再改投进 `Knowledge/Learned/_common`，那里没有读者。
3. **为了 v1 的问题建的机制，v2 不再需要。** 原设计（2026-10-26 §0）要解决的是"每个写入者当场自己判断、自己写"，所以让所有来源只提议、统一判官决定。v1 的来源是正则 hook，确实不可信；v2 的主线来源是 Agent 自己，这套"不信任来源"的机制变成了主要的误差来源。

保留得住的部分：唯一写入者 + 写入日志 + 恢复、inbox 和提取审计、配额、注入选择、使用统计、S7 分叉复盘、S1 当场提交。

## 2. 证据（2026-10-29，线上 cutover 后约 5 小时）

规模：`core/ingestion` 12,147 行，CDF 测试 51 个文件 10,504 行，设计文档 2,189 行；契约模型 35 个，卡 1 的形状 10 种，目的地 8 类，卡 1 到卡 3b 每个单元 2–5 次模型调用。

一个零上下文的审阅者按 Principle 1 看了全部 64 条写入和 114 条去重后的拒绝：写入的只有 23 条（36%）值得留；拒绝的有 32 条本该写入。把每类错误归到产生它的机制：

| 现象 | 条数 | 产生它的机制 |
|---|---|---|
| 写入的认知单元落在提取者声明之外的位置 | 29 条里 16 条 | 卡 1 重判形状 + 污染改投 `_common` |
| 用户的决定、具体要求被判"推测" | 16 条该留 | 卡 1 看不到这是用户说的（`SOURCE_CONTEXT` 只有类型和 scope） |
| 写清原因和修法的单元被丢 | 14 条该留 | 卡 0 按 600 字符丢弃（原子性本该由判断决定） |
| 同一条教训写进多个文件 | 11 条重复 | 两遍提取抽同一句话 + 查重只看目标那一个 store |
| 条目被另一个文件里的条目"取代"、不再注入 | 线上 2 条（含纠正 C069） | 卡 3 跨文件判 refine/replace，writer 只能改目标文件，关系却生效 |
| 编出用户没说过的做法（进了 EVOLUTION） | 3 条 | S2 原话那一遍改写用户的话，没人核对依据 |
| 用户的规矩和偏好写进 STEERING/USER | 0 条 | 上面两条的合力：能进的那一遍被判推测，复盘那一遍带污染 |
| 写进 `_common` 的条目被读到 | 16 条里 0 次 | 改投目的地没有读者 |

## 3. 新设计

原则：**谁掌握上下文，谁做判断；下游只做下游能可靠判断的事。**

### 3.1 去向由提取者的声明确定性算出

主线来源（S7、S1、S3）的单元已经自带 kind、type、scope（`user` + user_kind / `agent` / `world` / `project:X`）；提取 schema 为 project 单元加一个 `topic` 字段（取值沿用 `DDD_MATRIX` 的 topic），原来由卡 1 填。去向是这几个字段的纯函数，沿用现有的表：

| 单元 | 去向 |
|---|---|
| scope=user | STEERING（preference）/ USER（profile）/ TOOLS（environment）的 system appendix |
| scope=agent | EVOLUTION（correction 进 Corrections，其余进 Competence） |
| scope=world | MEMORY，按 type 分节 |
| scope=project:X | X 的 DDD，按 `DDD_MATRIX[topic][type]` |
| gap | X 的 IMPROVEMENT § What to Watch For |
| event | TIMELINE |
| reference | Knowledge 对应目录 |

X 必须是已有项目（大小写、空格不敏感地匹配）。来源声明的项目（S3 的 Brain、Hive 课、S1 指定的项目）优先；会话所在的项目不是声明，不覆盖单元自己的 scope。scope 里的名字匹配不上已有项目时（回放里是“CDF”“Hive Session Tab”“SwarmWS”这类子系统名），退回会话所在项目；也没有就拒绝（`unknown_project`），不再造 `repos/<x>.md` 这样的新文件。只有 gap 和 project 认知单元需要项目；event、reference 的去向和项目无关，scope 写什么都不因项目被拒。卡 1 的形状、`reroute_to`、改投映射全部删除。

### 3.2 信任看单元自己的依据，用户文件另加会话污染这道确定性门

- 单元引用了用户消息或实测结果，并且这份原文支持它（一次判断，见 3.3），单元是 **grounded**。
- 单元没有引用任何会话原文时（如 S5 的指标单元，依据是它自己登记的实测根），只有在没有任何外部内容到达它、并且它的依据强度是 `measured` 时才算有依据。
- MEMORY、EVOLUTION 只收有依据的单元。
- STEERING、USER、TOOLS 另加一道确定性的门：单元必须没有被会话污染、强度是 `user_explicit`，并且依据里有用户的话。这一道不听模型：复盘单元是在读过外部内容的上下文里产生的，它是被哪段输入塑造的无法得知，判官说"用户的话支持它"也不能证明它没被注入（选择性引用）。所以用户自己的文件只从 S1 和 S2 原话那一遍来，那两条通道碰不到外部内容。
- 不可能通过的单元（没有原文、也没有可用的实测强度；或去用户文件却带污染）在调模型之前就拒绝，不花一次核验。
- inferred 的 project 单元照常进项目 DDD（标 `taint`，和现在一样）。inferred 的 agent/world 单元（Agent 从自己的工作和工具输出里学到的教训，回放里是最有价值的一类）进会话所在项目的 DDD，标改投来源和 `taint`：按需召回，不进每轮注入。没有会话项目就不写，记为 `not_grounded`。inferred 的 user 单元一律不写。
- 删除 `_common` 改投和它的三个文件的写入路径。已写进去的内容不搬（原设计 §13），Library recall 仍能找到。后果：Hive 交回的 world 课（引用的是 Hive 的文档，没有本机会话原文）不再有去处，记 `not_grounded`。

> 初稿写的是"会话级污染不再决定信任，只留在审计里"、"S2 原话那一遍退出主线"。实现时安全测试抓到：这样被注入的工具输出可以经复盘写进 STEERING。已改为上面的规则：污染对用户文件仍是确定性的门，对其他文件由单元自己的依据决定。

### 3.3 一次核验代替卡 1、蕴含、卡 3、卡 3b

每个单元一次模型调用。输入：单元；它引用的用户原话和实测结果（`<GROUNDING_DATA>` 围栏，作为数据）；查重命中（下一节）。判官回答四件事：

1. **grounded**：依据原文是否支持单元的每个具体说法（做法、原因、日期、项目）。不支持的说法让单元变成 inferred；回答里列出了不支持的说法，就按不 grounded 处理，不看它的布尔值。
2. **durable**：离开这个会话仍然成立、仍然有用吗？对眼前一件事的一次性指示、进度和状态不是。
3. **relation**：和每条命中的关系：`same`（已有）、`adds`（同一主题，补充了新东西）、`contradicts`（矛盾）、`unrelated`。
4. **self_contained**：不看会话能读懂吗？

确定性动作：

| 结果 | 动作 |
|---|---|
| 不 durable 或不 self_contained | 拒绝 |
| 有 `same` 命中 | reinforce 那一条，不写新的 |
| 有 `contradicts` 命中，且命中在目标文件里 | 写新条目，旧条目标 `supersedes` |
| 有 `contradicts` 命中，但在别的文件 | 写新条目，只记关系，不隐藏旧条目 |
| `adds` 或无命中 | 写新条目（`adds` 记 `derived_from`） |

不再就地改写旧条目（删除卡 3b 和它的蕴含检查）：改写是最容易丢内容、也最难核对的一步，新条目加关系就够用。

### 3.4 查重看所有认知文件

查重语料：每轮注入的文件、目标文件、单元所在项目（scope 声明的，或来源给定的，如会话所属项目）的 DDD。不含 `Knowledge/Learned/_common`、`repos`、`domains`：那里没有读者，里面带污染的旧副本还会把可信的新单元判成"已有"挡掉。BM25 取前 8 条交给 3.3。和写入不同，查重不需要分信任层：命中只用来判断"是否已知"，跨文件的命中不会被改写或隐藏。

### 3.5 卡 0 只做确定性的安全检查

注入扫描、带凭证的 URL、条目里的 HTML 注释标记。删掉按字符数判原子性。渲染后超过目标 store 整天配额的单元（永远写不进去）由写入前的配额检查拒绝（`too_large_for_store`），不再每天推迟。项目 DDD 不进每轮注入，不设每日配额（AGENT R22 同步修改）：回放里一个重度会话一天就把 20KB 用完，32 条被推到第二天。

### 3.6 来源

| 来源 | 角色 |
|---|---|
| S7 复盘 | 主线：会话空闲约 10 分钟时，在 Agent 自己的上下文里复盘，负责七类认知（user 单元除外，归 S2 原话）、gap、reference |
| S1 | 主线：用户说"记住"时当场提交 |
| S3 | 主线：pipeline run 的 REFLECT |
| S2 原话 | 每个会话都跑，在复盘之前跑，交出它抽到的全部单元：它是用户文件唯一的可信通道，也是用户说过的具体要求的主要来源（回放里只按 user 单元限定范围，丢掉 32 条该留的里的 12 条，复盘没有补上）。和复盘重复的由查重处理 |
| S2 主提取 | 副线：会话恢复不了时兜底；10% 抽样用来测复盘漏了多少 |
| S4、S5、S6 | 不变 |

删除 `high_signal_capture`（它的读者 distillation 已删除）。会话中的纠正检测器保留，它给复盘打信号。

## 4. 会删掉什么

- 卡 1 的形状、复核、`reroute_to` 和改投映射；卡 3 的 per-hit 关系表；卡 3b、它的蕴含检查和就地改写。
- `_common` / `repos` / `domains` 的改投写入路径。
- 卡 0 的长度规则；`high_signal_capture`。复盘交出的 user 单元在 15 条上限之前丢掉（`owned_by_user_pass`），不占其他单元的位置。
- v1 引擎和它的契约（按上线计划本来就要删，这次一起删）。

预计删除的代码远多于新增的：新增的是 3.1 的路由函数、3.3 的核验卡和它的提示、3.2 的信任计算，单元的写入接口（destination + action + relations）不变，writer 不动。

## 5. 方案比较

| | 做什么 | 代价 | 风险 |
|---|---|---|---|
| **A 重构（推荐）** | 本文 | 删多加少；改 pipeline_v2、contracts、prompts、card3、两个来源 | 提取者的分类变成权威：它分错就直接放错。用已有项目匹配、grounded 核验兜住；复盘本身就是 Agent 在完整上下文里的判断，是现有信息最全的一方 |
| B 在原架构上补 | 给卡 1 补来源和原话、换掉卡 0 的数字、扩查重、给两遍提取划分工、禁止跨文件改写 | 改动小 | 倒置的权力、会话级信任、没人读的改投都还在；每处补丁都要和其他卡片配合，今天这类错误会换个形式再出现 |
| C 去掉判官 | 提取者直接写，只做确定性查重 | 最省 | 没人核对依据：今天 8 条错误里有 3 条是编造，会直接进每轮注入的文件 |

## 6. 验证

**不变式测试**：去向是声明的纯函数（含未知项目拒绝）；每轮文件只收 grounded；判官的提示带 `<GROUNDING_DATA>` 且剥掉伪造的围栏标签；跨文件的 `contradicts` 不产生 `supersedes`；卡 0 不按长度拒绝；带污染的单元进不了用户文件，模型怎么说都不行；复盘交出的 user 单元被丢掉；没有依据的 agent/world 教训进会话项目的 DDD 并标 taint；项目 DDD 没有每日配额。每条修复撤掉要变红。

**验收回放**（判定价值）：cutover 前的受管文件快照 + 今天全部 S7、S3 的候选 + `data.db` 副本，按入队顺序逐个走新流程并写入副本，和线上一样有先后、有查重。以审阅者的标签为标准答案：

- 32 条"本该写入"至少 22 条写入；8 条"错误"至多 2 条写入；
- 同一教训的重复不超过 3 组；
- 写进每轮注入文件的条目，人工逐条看，没有编造。

跑两次，两次都满足才上线。

**结果（2026-10-30，177 条带标签单元，真实判官）**：

| | 第一次 | 第二次 | 门槛 |
|---|---|---|---|
| 32 条本该写入 | 25 写入，5 条以 reinforce 落在已有条目上 | 27 写入，4 条 reinforce | ≥22 |
| 8 条错误 | 4（其中 3 条是写入时为真、后来被另一个 run 修好的 gap，见 §8） | 4（同上） | ≤2；不计 §8 的为 1 |
| 重复组 | 3 | 1 | ≤3 |
| 判官回答的命中对不上检索结果 | 0 / 175 | 0 / 175 | 0 |

回放中途抓到并修掉两处：数据围栏用 NFKC 折叠全角字符，把 STEERING 追加区锚点里的“（）”改成“()”，24/173 的判断丢了查重关系（STEERING 写进三条同义偏好）；判官抄回 64 位锚点时抄错几位。现在命中以 `h1`、`h2` 编号给判官，按编号映射回锚点。

回放假设：这批会话的作业都没有记下会话所在项目（绑定状态只在 daemon 内存里），回放按 SwarmAI 补上。上线后要核对新作业是否带上了项目，否则会话项目的兜底在线上不起作用。

**迁移**：新流程替换 `run_unit_v2` 里卡 1 到卡 3b 那一段，worker 和 writer 的接口不变。回放通过后删除旧代码。线上 worker 现在卡在一次 Bedrock 调用上（`3fd647183` 已修，未部署），队列里有 142 个候选；重构合入后再 build、重启，让积压的候选按新流程判。

## 7. 现在就该做、和重构无关的两件事

- 删掉 EVOLUTION 里那条写反了的 `ln -s` 条目（每轮注入）。
- 让线上两条跨文件的 `supersedes` 失效，纠正 C069 和那条 MEMORY pitfall 重新可见。

## 8. 回放发现、没在这次解决的：gap 没有关闭的路径

验收回放里 4 条“错误”写入（同一天里已修好的 gap）不是写的时候就过时了：它们来自早上一个 run 的 deferred finding，写入时是真的；两小时后另一个 run 修好了，产生一条 event。CDF 现在没有任何机制让后来的单元关闭一条已写的 gap，跨文件关系又只记 `derived_from`、不隐藏旧条目，所以 IMPROVEMENT 里的 gap 一旦写入就永远是“未解决”，以后的会话召回到它会被误导。

要解决的是 gap 的生命周期，不是核验：核验时让判官为命中的 gap 回答“这个单元是否报告它已解决”（新关系 `resolves`），写入时记关系；召回和 `knowledge find` 显示 gap 时带上“已由 <单元> 解决”。读的一侧（召回、`knowledge find`、Brain Hub）要先设计好再动写的一侧，单独做。回放的“错误”计数把这 4 条单列。
