# 知识到达判断

## 0. 目标和约束

两个问题（XG 2026-11-02）：C10"知识有没有被用上"量不出来；EVOLUTION 涨到每轮 24K token，没有上限，早晚会炸。

五条约束：对准北极星；不带来性能问题；MEMORY、EVOLUTION 不无限膨胀，但不靠截断；长期正确（含义由带上下文的 agent 判断，代码只核对事实，条目不因时间离开）；系统化，不打补丁。再加一条：**只为线上真实发生过的问题加机制。**

## 1. 现状（2026-11-02 实测）

**C10 量不出来。**

- C10（`health.py:749-754`）统计写入满 14 天、且 14 天内被读过（`read_by_agent`）或被引用过的条目。CDF 第一条写入是 10-29，要到 11-12 才有条目满 14 天，所以现在是 `no_data`。
- 到期了也不准。过去 3 天，对 Brain / Knowledge 文件执行读取命令的次数：Bash（sed、cat、grep 等）131 次，Read 12 次，`cognition get` 24 次。用量观察器只挂了 Read 和 Grep（`hook_builder.py:688-696`），**大约四分之三的读取记不到**。

**EVOLUTION 只进不出。**

- 每轮注入的 token 数（`prompt_metrics`）：10-30 18.1K → 11-02 24.3K。首 token 时间中位数同期 8.7s → 6.2s，**目前还没有性能问题**，但照这个速度一个月后会到 60K 以上。
- CDF 写入 EVOLUTION 37 条：**30 条是第一次出现的教训**，7 条是重犯写成的新条目。22 次重犯声明，全部指向每轮注入的文件。
- 根因一：**"一件事"的粒度是一次事故，不是一类判断错误。** 纠正大多写"这次在哪个界面、哪个 API 上错了"。类别相同、事故不同，`same` 对不上，就各写一条。按类别重读 CDF 时代的 35 条，大约能并成 15 类（比如交还给人 C068 / C091 / C092；回复语言 C079 / C081；复用已有组件 C078 / C084 / C094；断言状态前先观察 C085 / C093）。
- 根因二：**没有离开的门。** `overrides.check` 只解析项目 DDD 的条目（`overrides.py:140-141`），MEMORY、EVOLUTION、General Brain 的条目覆盖不了。10-30 约定的"靠 same / overrides 保持精简"只通了一半：same 能加强，没有条目能离开。
- 体量里有一大块是历史：旧的手写块 `CLASS B` 30.3KB（全文件 41%），`Governance Candidates` 里已升级规则的说明 6.3KB。

**体量的度量已经有了，只是没摆到我面前。** `prompt_metrics` 每轮都记五个每轮注入文件的 token 数，10-30 设计约定"明显上升时由 agent 按声明合并"，但这个数不在我的 prompt 里，所以从来没有人去合并。

## 2. 设计：四个改动，一行显示

**① Bash 读取也要记到（治 C10）。**

- 用量观察器的 matcher 从 `Read|Grep` 改成 `Read|Grep|Bash`。
- 钩子本身只做一件便宜的事：看命令里有没有一个 token 指向 `Projects/*/` 或 `Knowledge/` 下的受管文件，按 cwd 和命令开头的 `cd <目录>` 解析。没有就直接返回；有就交给 io 线程池。
- 线程池里：stdout 里完整出现的单元，以及 `grep -n` 形式的 `路径:行号:` 行对应到的单元，记 `read_by_agent`。这和 Read 现在的记法一致，C10 不用改。
- 实测 721KB 的输出扫一遍大约 40ms，在线程池里跑，不在聊天路径上。

**② 每轮注入的文件也能覆盖（治"只进不出"）。**

- `overrides.check` 的解析范围扩到 MEMORY、EVOLUTION 和 General Brain 里由 CDF 写入的条目（带 `cand:` 标记）。规则不变：id 加首行对得上、说得比旧条目晚、不是人手写的。STEERING、USER、TOOLS 归用户所有，不动。
- 配套改一个条件：`withdrawn.restates`（`withdrawn.py:92-97`）现在会拒收"内容出现在被覆盖条目里"的单元，哪怕当前有效的条目也说了这段话。覆盖一旦用在 EVOLUTION 上，"写整条当前教训再覆盖旧的"之后的每次重述都会被误拒。所以改为：当前有效条目也说了，就不拒收，交给关系判断走 `same`。线上已有 11 个单元因"withdrawn"被拒，这一条同样适用于 DDD。

**③ 一件事 = 一类判断错误（治"按事故增长"）。**

S7（会后复盘）的提示词，对去往 EVOLUTION 的纠正和 Competence 规定：

- 条目写的是**我在哪种判断上会出错**（规则、识别信号、适用范围），不是事故经过。
- 已有一类覆盖了这次：什么都没多就声明 `same`；多了新的一面，就写这一类的整条当前教训，并声明 `overrides` 旧的。这正是提示词已有的规则（`s7_review.py:390-392`），有了 ② 才能在每轮注入的文件上生效。
- 只在某个项目里成立的细节（API 名、界面组件、文件名），作为另一个单元写进那个项目 DDD 的 IMPROVEMENT，由 `[DDD:]` 召回送到。
- 含义全部由 S7 判断，代码只核对 id 和首行。

**④ 第一次整理，由我在会话里做一次。**

改写是含义判断，由掌握上下文的 agent 来做，不做成自动机制。

- **EVOLUTION**：旧手写块和 CDF 时代同一类的条目，改写成按类别的教训，原文逐字进 archive 分片（`cognition find --in evolution` 会读所有分片）。已升级规则的说明搬进 archive。只在 SwarmAI 里成立的细节，进 SwarmAI DDD 的 IMPROVEMENT。
- **MEMORY**：长篇 COE 叙述改写成一条教训，完整复盘放进 `Knowledge/Archives/`，条目里写指向它的路径。
- **写入**：通过 `governed_edit`，带 actor 和原因（MEMORY、EVOLUTION 归 agent 所有，AGENT R21）。
- **安全**：先备份 `.context/` 和 `ingestion.db`，并确认备份可用。
- **核对**：整理前的每个 C / K 编号整理后都能找到；搬走的原文和备份逐字一致；记下前后的 token 数。

**⑤ 一行显示：把每轮注入文件的体量放进北极星。**

北极星的 headline 每轮都在我的 prompt 里。CDF 那一行加上 EVOLUTION 和 MEMORY 的当前 token 数，以及 7 天前的值（读 `prompt_metrics`，北极星已经按这个方式在读其他数）。这样 10-30 约定的"明显上升时由 agent 按声明合并"就有了触发者：就是每轮都看得到这个数的我。合并照 ③ 的规则来，用声明，不截断。

## 3. 增长上界（如实说）

每轮注入的体量 ≈ 当前有效的判断类别数 × 每条教训的长度。

- 同一类错再犯，只加强或改写那一条（③ + ②）；
- 只在一个项目里成立的细节，不进每轮注入的文件（③）；
- 体量每轮在我面前，上升时由我按声明合并（⑤）。

剩下的增长只有一个来源：**真正新的判断错误类别**。这不是硬上限，也不该是，因为硬上限意味着砍掉还在承重的教训。但新类别不停地出现，本身就是北极星在变差，而且每轮都看得见。

## 4. 性能

聊天路径只多一个 PostToolUse 过滤（解析 Bash 命令的 token，微秒级），匹配在 io 线程池里。不新增模型调用。整理之后每轮 prompt 变小，首 token 时间和缓存读取成本只会下降。

## 5. 北极星怎么因此变好

- 每轮注入的内容更少、更密，每条都是跨项目成立的判断，不被事故细节和重复条目稀释。
- 同一类错只有一条，重犯会加强或改写这一条，而不是在旁边再加一条。
- C10 能量出真实的读取，写了却从没被读过的目的地会直接显示出来（比如 DDD 4 天写入 1531 条）。

## 6. 否决的方案

| 方案 | 为什么不做 |
|---|---|
| 恢复体积上限，超了就归档 | 违反价值优先和 STEERING #2，按数字砍掉还在承重的知识 |
| 按时间把旧纠正移出每轮注入 | 违反"条目不因时间离开" |
| 自动合并或去重阀（r2、r3） | 改写是含义判断，自动模型看不到当初的对话（C046）；只判重的版本，是在为"③ 不起作用"预先造机制。体量已经量着，⑤ 把它摆到我面前就够了 |
| `merges` 声明和 `merged` 状态（r2） | 问题出在 `restates` 少一个条件，改条件就够了 |
| S7 自报"哪条知识影响了决定"（r2） | 模型自报，没法证伪 |
| C11、C12、重犯归环、`repeats` 先写、"犯过 N 次"渲染、升级和修复的专门出口（r3） | 线上没发生过它们要防的问题：被拒时丢掉 repeats 0 次，same 写成新条目 1 次，22 次重犯全部指向每轮注入的文件。升级或修复之后要让条目离开，有了 ② 直接声明覆盖即可 |

## 7. 为什么从 r3 删到 r4

r1 的前提审查找出了真问题，但 r2、r3 对每一条发现都加了一个机制，加到了 13 个、再到 7 个。AGENT § Iterative Refinement 写着这个信号："为了回应一份已经审过一次的设计的发现，在加新的状态、标志或模式。"r4 对每个机制只问一句：**它要防的问题在线上发生过吗？** 没发生过的都删了，等数据说需要时再加。

## 9. 实现与验证（2026-11-02）

**评审改变了 ② 的底线。** 第一轮安全评审证明，只看"单元去了哪个 store"挡不住两条路：靠"重犯"被放进 EVOLUTION 的推断单元，以及配一句真实但无关的用户原话的单元。所以 ② 的实际规则比 §2 写的更严：

- 每轮注入的条目只能被**同一个文件**的单元拿掉；新单元必须有用户原话或测量依据，并且不是作为重犯被放进来的；
- 被拿掉的条目如果原本是用户原话依据（没有记录的一律按用户原话处理），新单元也必须是用户原话；
- 只要新单元是用户原话依据，就再做一次隔离核对：问"用户的话是否替换了这一条"（复用 `user_check.grounds`，只在覆盖每轮注入的条目时才会多这一次调用）；
- General Brain 的条目，只能被写进同一份文档的单元拿掉，或者被以上述依据写进 MEMORY / EVOLUTION 的单元拿掉；
- `restates` 的例外只对"被覆盖"的记录生效：用户撤回的文字，不能从任何文件绕回来。

**不变量，逐条：**
