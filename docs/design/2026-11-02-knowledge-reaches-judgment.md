# 知识到达判断

## 0. 目标和五条约束

CDF 是 Swarm 自己的认知引擎，这份设计由 agent 自己决定（XG 2026-10-30 授权，2026-11-02 重申："这是你的认知系统"）。五条约束（XG 2026-11-02）：

1. **朝北极星**：被纠正的会话占比下降，重犯占比趋近于零，能看清错误出在哪一环。
2. **不带来性能问题**：聊天路径不新增模型调用，首 token 时间不变差。
3. **MEMORY、EVOLUTION 不无限膨胀**：增长要由结构决定，不能靠截断。
4. **长期正确**：含义由带上下文的 agent 判断，代码只核对事实；不设预算、不截断；条目不因时间离开；不让上下文更少的判断者改写上下文更多的判断者的结论。
5. **系统化**：从源头改形状，不在下游打补丁；能删就不加。

## 1. 现状（2026-11-02 实测，已按审查核对）

**EVOLUTION 的体量**（`prompt_metrics` 每轮记录的 token 数）：10-30 18.1K → 10-31 23.0K → 11-01 24.0K → 11-02 24.3K。首 token 时间中位数同期 8.7s → 6.2s，**目前还没有性能问题**；按现在的速度，一个月后会到 60K 以上。MEMORY 是 17.9K（10-31 整理过一次），7 天只写入 6 条。

**EVOLUTION 怎么涨的**（`ingestion.db`）：

- CDF 写入 37 条，其中 **30 条是第一次出现的教训**（21 条纠正、9 条 Competence），**7 条声明了 `repeats` 却作为新条目写入**（action=add）。另有 2 条重犯走了 `same`，正确地加强了已有条目。`_repeat_opens`（`pipeline_v2.py:620-650`）一次都没触发过。
- 根因：**EVOLUTION 里"一件事"的粒度是一次事故，不是一类判断错误。** 21 条纠正大多描述"这次在哪个界面、哪个 API 上错了"，而不是"我在哪种判断上会出错"。类别相同、事故不同的纠正，`same` 对不上，于是都成了新条目。按类别重读 CDF 时代的 35 条，大约能并成 15 类，例如：
  - 把我能做的事交还给人：C068 / C091 / C092
  - 回复语言：C079 / C081
  - 复用已有组件，不另造：C078 / C084 / C094
  - 断言系统状态前先观察：C085 / C093
- 体量构成：旧的手写块 `CLASS B` 30.3KB，占全文件 41%；`Governance Candidates` 里已升级规则的说明 6.3KB；CDF 时代的条目平均每条 785B。

**每轮注入的文件没有"离开"这扇门。**

- 10-30 设计约定：MEMORY、EVOLUTION 靠 agent 声明 same / adds / overrides 保持精简（`2026-10-30-cdf-agent-decides.md` §4，`prompt_metrics.py:5-10`）。
- 但 `overrides.check` 只通过 `addressing.matches(project, …)` 解析项目 DDD 的条目（`overrides.py:140-141`），MEMORY、EVOLUTION、General Brain 的条目解析不到。线上全部覆盖都落在 `Projects/…` 和 TIMELINE 上。
- 结果：same 能加强，但没有任何条目能离开，主文件只能变大。

**知识有没有到达判断，量不出来。**

- C10（`health.py:749-754`）只看写入满 14 天的条目，CDF 第一条写入是 10-29，所以是 `no_data`。
- 即使到期也不准。过去 3 天，对 Brain / Knowledge 文件执行读取命令的次数：Bash（sed、cat、grep 等）131 次，Read 12 次，`cognition get` 24 次，`cognition find` 55 次。用量观察器只挂了 Read 和 Grep（`hook_builder.py:688-696`），**大约四分之三的读取看不到**。
- 早期数据（未满 14 天）：DDD 4 天写入 1531 条，被召回 90 条，被打开 16 条。

## 2. 根因（四个）

| # | 根因 | 后果 |
|---|---|---|
| R1 | EVOLUTION 的"一件事"是事故，不是判断类别 | 条目跟着事故数涨（约八成的增长） |
| R2 | 每轮注入的文件和 General Brain 没有离开的门：覆盖解析不到 | 条目只进不出 |
| R3 | 重犯写成新条目；拒收路径会丢掉 `repeats` 记录（`pipeline_v2.py:753-754`、`:793-794` 先于 `_with_relations` 返回）；被覆盖条目的内容之后被重述时会被拒收，即使当前有效的条目也说了它（`withdrawn.py:92-97`） | 重犯也在涨，重犯率可能少算；"写整条当前说法再覆盖"这条路会误伤之后的重述 |
| R4 | 用量仪器看不到 Bash 读取 | "知识有没有到达"量不出、量不准 |

## 3. 设计

七个改动：B1–B5 治 R1–R3，A1–A2 治 R4。

### B. 每轮注入的文件：一类判断一条，按事件离开

**B1 EVOLUTION 的"一件事"是一类判断错误。** S7（会后复盘）的提示词对去往 EVOLUTION 的纠正和 Competence 明确规定：

- 条目写的是**我在哪种判断上会出错**（规则、识别信号、适用范围），不是这次事故的经过。
- 代码给 S7 看最接近的已有纠正（现有的 8 条，`s7_review.py:45`）。如果已有一类覆盖了这次：
  - 什么都没多出来，声明 `same`（加强那一条）；
  - 多出了新的一面，就把那一类的**整条当前教训**重写一遍，并声明 `overrides` 那一条。这是 S7 提示词已有的规则（`s7_review.py:390-392`："写整条当前说法，再声明覆盖"），这里只是让它在每轮注入的文件上也能生效（B2）。
- 这次事故里只在某个项目成立的细节（API 名、界面组件、文件名），作为另一个单元写进那个项目 DDD 的 IMPROVEMENT。那个项目活跃时，由 `[DDD:]` 召回送到。
- 含义全部由 S7 判断，代码只核对它点名的 id 和首行。**代码不从 `repeats` 推断任何覆盖。**
- **B1 只是提示词，靠的是复盘自觉。** 我的记录里写着：这种修法单靠自己守不住。所以 B1 必须有度量（B5），碎片化一旦出现就能看见。

**B2 给每轮注入的文件打开离开的门。** `overrides.check` 的解析范围扩到 MEMORY、EVOLUTION 和 General Brain 里由 CDF 写入的条目（带 `cand:` 标记）。规则不变：id 加首行对得上、说得比旧条目晚、不是人手写的。同样扩到 `override_closes`（`overrides.py:282-292`），让 B4 的关闭出口可用。STEERING、USER、TOOLS 归用户所有，这次不动。

**B3 重犯计数一次都不丢；有效条目说过的话不被当作"已撤回"。**

- `repeats` 在每个拒收或加强的返回之前就写进 `version_vector`。这样 `queries.read_corrections`（`queries.py:403-434`）不管单元最后是新增、加强、覆盖还是被拒，都能数到这一次重犯。
- `withdrawn.restates` 改一个条件：一个单元的内容出现在被撤回条目的原文里，**而且没有任何当前有效条目也说了它**，才按"用户拿掉的东西"拒收。如果当前有效条目说了，就不拒收，交给关系判断去走 `same`。这一条同样修好了 DDD 里"覆盖之后，新条目说过的内容反而被拒收"的问题。

**B4 按事件离开的出口。** 退出状态都用 `closed`，不用 `overridden`：`closed` 不拒收，之后又犯时，现有逻辑把"和已关闭条目相同"当作复发，重新写成新条目（`pipeline_v2.py:796-797`），教训自动回来。

- **升级成规则**：一条规则经 s_self-evolution 落地（AGENT、SOUL、STEERING 或某个 skill）后，落地它的那个会话在复盘时声明关闭它点名的 EVOLUTION 条目（"已升级为 …"）。哪一行能成为提案，仍按 governance miner 现有的规则：Checked 那一格由 agent 填了才算（`governance_miner.py:9-17`）。重犯次数只是证据。
- **结构性修复**：一个会话或 run 落地了让这类错不再发生的机制（钩子、门、测试、代码改动），它的复盘声明关闭这条教训，并把"这个机制为什么存在"写进那个机制所在项目的 DDD。

**B5 关系去重阀，加上碎片化度量。**

- **去重阀**：
  - 触发：`prompt_metrics` 记录到某个每轮注入文件的 token 数，达到它上次去重后体量的 1.25 倍。触发后照常继续，不截断任何东西。
  - 动作：CDF worker 排一个任务，在串行执行器和内存门控下跑。用会话本身的模型，把整份文件放进上下文。**它只能声明一种关系：`same`**，也就是"条目 A 说的 B 全都说了"。代码核对 id 和首行，关闭 A（`closed`，"内容在 B 中"），加强 B。
  - **它不写一个字的新内容，不改写、不合并、不覆盖。** 理由：它只看得到文件，看不到当初纠正发生的那段对话，掌握的上下文比写这条教训的 S7 少。让它改写，就是更弱的判断者改写更强判断者的结论（约束 4）；压缩时最容易丢的，正是用户当时纠正的那个细节（EVOLUTION C046：把沉淀的判断压成摘要）。判断"两段话是否一个包含另一个"，看文件就够了。
  - 去重阀没有可关的条目时，记录"没有重复"，并把基线更新为当前体量。真实的增长被接受，在 Health 里可见（P6：每一项都在承重时抬高警戒线，不砍有用的东西）。
- **碎片化度量**：CDF Health 每周对每个目的地抽样评审新条目（已有，`cdf.health`）。对 EVOLUTION 的抽样多问一句："这条是不是文件里已有某一类的又一次？"命中率作为"碎片化率"显示。它只度量，不自动处理；它告诉我 B1 有没有起作用。
- **C11 "每轮注入的文件按'类'增长"**：7 天内写进 MEMORY / EVOLUTION 的单元里，声明了 `same`、点名的是**当前有效**条目、却作为新条目落地的数量必须为 0。点名已关闭条目而重新写入的属于 B4 的复发，不算违规。

**增长上界（如实说）**：每轮注入的体量 ≈ 当前有效的判断类别数 × 每条教训的长度。

- 同一类错再犯，只加强或改写那一条（B1、B3）；
- 类别会因为升级成规则、结构性修复、被判为重复而离开（B4、B5）；
- 只在单个项目里成立的细节不进每轮注入的文件（B1）；
- 碎片化有度量（B5）。

剩下的增长只有一个来源：**真正新的判断错误类别**。这不是硬上限，也不该是，因为硬上限意味着砍掉还在承重的教训。但它把增长和北极星绑在了一起：新的错误类别一直在出现，就是北极星在变差，而且在 Health 上看得见，不会藏在一份越来越长的文件里。

### A. 知识有没有到达判断

**A1 Bash 也要看到。** 用量观察器的 matcher 加上 Bash。钩子本身只做一件便宜的事：命令里有没有一个 token 指向受管文件。解析时按 cwd 和命令开头的 `cd <目录>`，看能不能落到 `Projects/*/`、`Knowledge/` 下面。没有就直接返回；有就交给 io 线程池。

线程池里：对这些文件，stdout 里**完整出现**的单元、以及 `grep -n` 形式的 `路径:行号:` 行对应到的单元，记 `recall_injected`。Bash 的输出最多 30000 字符（实测），"是不是整份"判断不了，所以 Bash 只记"送到"。实测 721KB 的输出扫一遍大约 40ms，在线程池里跑，不在聊天路径上。

Read 是否整份读取，改为按 `tool_response.file` 的 `startLine`、`numLines`、`totalLines` 判断，不再按"没给 limit"判断。

**A2 北极星问的是"到达"，不是"用上"。**

- **"用上"不做。** 一个条目"影响了某个决定"，只能由模型自己报告，没办法证伪，而且只会往高报。北极星真正要的是两件事：该用的知识当时送到面前了吗？送到了还犯错吗？这两件都可以确定性地测。
- **C10 改名为"知识有没有到达我"**：满 14 天的按需条目（DDD、Knowledge、General Brain、TIMELINE 事件）里，至少有一条在写入后 14 天内被送到过。依据是 `recall_injected` 和 `read_by_agent`。北极星的详细输出按分组显示送到率，没满 14 天的显示"目前为止"并注明未到期。比例不设通过线，等有 4 周数据再定（P6）。pipeline 的 `knowledge_refs` 已在 Brain Eval 里统计（`brain_eval.py:195-210`），不再接一份。
- **重犯归到错误倒查的哪一环**：一条纠正声明 `repeats X` 时，代码看 X 当时有没有送到这个会话。
  - X 在每轮注入的文件里，就算送到。这是"送到了还错"（第三环），杠杆是升级成规则或机制（B4），不是再写一遍。
  - X 是按需条目、而这个会话没有它的送到记录，就是"没送到"（第二环），杠杆是修召回。
  - 北极星的详细输出加一行："重犯 k 次：教训当时在面前 j 次，不在 k−j 次"。
- **C12 "仪器看得到每一扇门"**：过去 7 天有会话的前提下，"送到"的每个来源（自动召回、`cognition find`、Read / Grep / get、Bash）各至少有一条记录，否则判失败，并指出是哪一扇门。这个检查判断的是测量本身有没有坏，像现在 Bash 看不到这种情况，就会判失败。

## 5. 第一次整理（一次性，由我在会话里做）

旧的手写块和 CDF 时代同一类的条目，需要**改写**成按类别的教训。改写是含义判断，所以由掌握上下文的 agent 来做：我在会话里做，不做成自动机制。

- **EVOLUTION**：
  - `CLASS B` 等旧手写块，以及 CDF 时代同一类的条目，改写成按类别的教训，原文逐字进 archive 分片（`cognition find --in evolution` 会读所有分片）；
  - `Governance Candidates` 里已升级规则的说明是历史，搬进 archive；
  - 只在 SwarmAI 里成立的细节，进 SwarmAI DDD 的 IMPROVEMENT。
- **MEMORY**：长篇 COE 叙述改写成一条教训，完整复盘作为文件放进 `Knowledge/Archives/`，条目里写指向它的路径。
- **写入通道**：这些条目大多没有 `cand:` 标记，是 CDF 之前写的。MEMORY 和 EVOLUTION 都归 agent 所有（AGENT R21），所以通过 `governed_edit` 写入，带上 actor 和原因，不在 `.context` 里裸改。
- **安全**：先备份 `.context/` 和 `ingestion.db`，确认备份能打开、内容完整。
- **核对**：
  - 整理前出现过的每个 C / K 编号，整理后在主文件、archive 分片或 DDD 里都能找到；
  - 搬走的原文和备份逐字一致；
  - 记下前后的 token 数；
  - diff 留给 XG 随时查看。

## 6. 北极星怎么因此变好

- **重犯**：一类错一条；每次重犯自动归到"没送到"（修召回）或"送到了还错"（升级成规则或机制），每一种都有对应的杠杆。
- **纠正**：每轮注入的内容更少、更密，每条都是跨项目成立的判断，注意力不被单个项目的细节和重复条目稀释。
- **错误来源**：第二环每天可量，第三环由重犯自动归类；月度倒查从"推断"变成"核对"。
- **CDF 自己**：写了却从没送到的目的地会直接显示出来（比如 DDD 4 天写入 1531 条、召回 90 条），之后调整 CDF 写多少、写到哪，有数可依。

## 7. 否决的方案

| 方案 | 为什么不做 |
|---|---|
| 恢复体积上限，超了就归档"价值最低"的条目 | 违反价值优先（10-30 决定）和 STEERING #2；按数字砍掉还在承重的知识，根因还在 |
| 按时间把旧纠正移出每轮注入 | 违反"条目不因时间离开" |
| 让一个模型按体量触发、把多条教训改写成一条（r2 的 B7） | 它看不到当初的对话，是更弱的判断者在改写；压缩会丢掉用户纠正的那个细节（C046）。只保留"判重"这一种关系 |
| 新增 `merges` 声明和 `merged` 状态（r2 的 B3） | 问题出在 `restates` 少了一个条件，改这个条件就够了，不需要新状态 |
| S7 声明"哪条知识影响了决定"（r2 的 A2） | 模型自报，没法证伪，只会往高报；北极星需要的"到达"和"重犯"都能确定性地测 |
| 每轮注入渲染"犯过 N 次"（r2 的 B5） | 要在 prompt 构建器里为 EVOLUTION 单写渲染逻辑，而"数字在面前就少犯"没有证据。重犯次数在数据里、Health 上看得到。等数据显示"已注入的教训仍在重犯"时再加 |
| 代码从 `repeats` 推断"覆盖旧条目" | 那是代码在判断含义 |
| 用正则或关键词判断"属于哪一类错" | 违反"含义由带上下文的 agent 判断" |

## 8. r1 → r2（零上下文前提审查的结论，已逐条核对源码和数据）

| 问题 | r1 | r2 / r3 |
|---|---|---|

**最终不变量**（收尾跑一次，每条做 mutation check）：
