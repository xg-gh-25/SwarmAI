# 知识到达判断

## 0. 目标和五条约束

CDF 是 Swarm 自己的认知引擎，这份设计由 agent 自己决定（XG 2026-10-30 授权，2026-11-02 重申："这是你的认知系统"）。五条约束（XG 2026-11-02）：

1. **朝北极星**：被纠正的会话占比下降，重犯占比趋近于零，能看清错误出在哪一环。
2. **不带来性能问题**：聊天路径不新增模型调用，首 token 时间不变差。
3. **MEMORY、EVOLUTION 不无限膨胀**：增长要由结构决定，不能靠截断。
4. **长期正确**：含义由带上下文的 agent 判断，代码只核对事实；不设预算、不截断；条目不因时间离开。
5. **系统化**：从源头改形状，不在下游打补丁。

## 1. 现状（2026-11-02 实测，r2 已按审查核对）

**EVOLUTION 的体量**（`prompt_metrics` 每轮记录的 token 数）：10-30 18.1K → 10-31 23.0K → 11-01 24.0K → 11-02 24.3K。首 token 时间中位数同期 8.7s → 6.2s，**目前还没有性能问题**；按现在的速度，一个月后会到 60K 以上。MEMORY 是 17.9K（10-31 整理过一次），7 天只写入 6 条。

**EVOLUTION 怎么涨的**（`ingestion.db`）：

- CDF 写入 37 条，其中 **30 条是第一次出现的教训**（21 条纠正、9 条 Competence），**7 条声明了 `repeats` 却作为新条目写入**（action=add）。另有 2 条重犯走了 `same`，正确地加强了已有条目。`_repeat_opens`（`pipeline_v2.py:620-650`）一次都没触发过。
- 根因：**EVOLUTION 里"一件事"的粒度是一次事故，不是一类判断错误。** 21 条纠正大多描述"这次在哪个界面、哪个 API 上犯了错"，而不是"我在哪种判断上会出错"。类别相同、事故不同的纠正，`same` 对不上，于是都成了新条目。
- 体量构成：旧的手写块 `CLASS B` 30.3KB，占全文件 41%；`Governance Candidates` 里已升级规则的说明 6.3KB；CDF 时代的条目平均每条 785B。

**每轮注入的文件没有"离开"这扇门。**

- 10-30 设计约定：MEMORY、EVOLUTION 靠 agent 声明 same / adds / overrides 保持精简，体量明显上升时由 agent 按声明合并（`2026-10-30-cdf-agent-decides.md` §4，`prompt_metrics.py:5-10`）。
- 但 `overrides.check` 只通过 `addressing.matches(project, …)` 解析项目 DDD 的条目（`overrides.py:140-141`），MEMORY、EVOLUTION、General Brain 的条目解析不到。线上全部覆盖都落在 `Projects/…` 和 TIMELINE 上。
- "体量上升时合并"的触发器也从没实现过。
- 结果：same 能加强，但没有任何条目能离开，主文件只能变大。

**知识用没用上，量不出来。**

- C10（`health.py:749-754`）只看写入满 14 天的条目，CDF 第一条写入是 10-29，所以是 `no_data`。
- 即使到期也不准。过去 3 天，对 Brain / Knowledge 文件执行读取命令的次数：Bash（sed、cat、grep 等）131 次，Read 12 次，`cognition get` 24 次，`cognition find` 55 次。用量观察器只挂了 Read 和 Grep（`hook_builder.py:688-696`），**大约四分之三的读取看不到**。
- "用上"没有来源。`cited_as_evidence` 只在 CDF 自己引用 corpus 单元时写（`provenance.py:451-455`），记录是 0。pipeline 的 `knowledge_refs` 已经在 Brain Eval 里统计（`brain_eval.py:195-210`），但没进 `unit_usage`。
- 早期数据（未满 14 天）：DDD 4 天写入 1531 条，被召回 90 条，被打开 16 条。

## 2. 根因（四个）

| # | 根因 | 后果 |
|---|---|---|
| R1 | EVOLUTION / MEMORY 的"一件事"是事故，不是判断类别 | 条目跟着事故数涨（约八成的增长） |
| R2 | 每轮注入的文件和 General Brain 没有离开的门：覆盖解析不到，合并触发器没建 | 条目只进不出 |
| R3 | 重犯写成新条目；拒收路径会丢掉 `repeats` 记录（`pipeline_v2.py:753-754`、`:793-794` 先于 `_with_relations` 返回） | 重犯也在涨，重犯率可能少算 |
| R4 | 用量仪器看不到 Bash；"看到"和"用上"混在一起；"用上"没有来源 | C10 量不出、量不准 |

## 3. 设计

### B. 每轮注入的文件：一类判断一条，按事件离开（治 R1–R3）

**B1 EVOLUTION 的"一件事"是一类判断错误。** S7（会后复盘）的提示词对去往 EVOLUTION 的纠正和 Competence 明确规定：

- 条目写的是**我在哪种判断上会出错**（规则、识别信号、适用范围），不是这次事故的经过。
- 代码给 S7 看最接近的已有纠正（现有的 8 条，`s7_review.py:45`）。如果已有一类覆盖了这次：
  - 什么都没多出来，声明 `same`（加强那一条）；
  - 多出了新的一面，就把那一类的**整条当前教训**重写一遍，并声明 `merges` 那一条（B3）。
- 这次事故里只在某个项目成立的细节（API 名、界面组件、文件名），作为另一个单元写进那个项目 DDD 的 IMPROVEMENT。那个项目活跃时，由 `[DDD:]` 召回送到。
- 含义全部由 S7 判断，代码只核对它点名的 id 和首行。**代码不从 `repeats` 推断任何覆盖或合并**。

**B2 给每轮注入的文件打开离开的门。** `overrides.check` 的解析范围扩到 MEMORY、EVOLUTION 和 General Brain 里由 CDF 写入的条目（带 `cand:` 标记）。规则不变：id 加首行对得上、说得比旧条目晚、不是人手写的。STEERING、USER、TOOLS 归用户所有，这次不动。

**B3 新增一个声明 `merges`：内容带走，不是"变成错的"。**

- `overrides` 的意思是"旧条目不再成立"，退出状态是 `overridden`，属于 `withdrawn.REFUSING`（`withdrawn.py:34`）：之后再有和它相同的说法会被拒收。这是对的，旧说法确实错了。
- 合并不一样，旧条目的内容还在新条目里。所以 `merges` 用一个新的退出状态 `merged`，**不属于** REFUSING，并在撤回记录里存下接手它的条目（head anchor）。
- 之后有单元的内容和一个 `merged` 条目相同（`withdrawn.restates`），或者有声明点名它，一律解析到它的 head，按 `same` 加强 head，不拒收。
- 不改 `_SUPERSEDES_SOURCES`（`pipeline_v2.py:362-367`，10-30 实测模型配对的 supersedes 有 10/16 是错的）：head 记在撤回记录上，是代码写的事实，不是模型声明的边。

**B4 重犯计数一次都不丢。** `repeats` 在每个拒收或加强的返回之前就写进 `version_vector`。所以 `queries.read_corrections`（`queries.py:403-434`）不管单元最后是新增、加强、合并还是被拒，都能数到这次重犯。纯重犯走 `same`，加强已有条目：现有的 `claim_support` 已经在做这件事。

**B5 "犯过 N 次"写在条目上，不改条目 id。** N 由代码按 `claim_support` 加 `repeats` 算出，写进条目的元数据注释。条目的 hash 计算时会去掉注释，所以 id 不变，`<id> | <首行>` 引用不会因为加强而失效。每轮注入渲染 EVOLUTION 时，把这个数显示成 "（犯过 N 次，最近 YYYY-MM-DD）"。渲染只读文件，不读数据库，符合 system prompt 不碰数据库的约定。

**B6 按事件离开的出口。** 退出状态都用 `closed`：不拒收，之后又犯时，现有逻辑把"和已关闭条目相同"当作复发，重新写成新条目（`pipeline_v2.py:796-797`），教训自动回来。

- **升级成规则**：一条规则经 s_self-evolution 落地（AGENT、SOUL、STEERING 或某个 skill）后，它点名的 EVOLUTION 条目以 `closed`（"已升级为 …"）离开。哪一行能成为提案，仍按 governance miner 现有的规则：Checked 那一格由 agent 填了才算（`governance_miner.py:9-17`）。"犯过 N 次"只是提案的证据，不会自动生成提案。
- **结构性修复**：一个会话或 run 落地了让这类错不再发生的机制（钩子、门、测试、代码改动），它的复盘声明关闭这条教训（沿用 gap 关闭的 `override_closes`，`overrides.py:288-292`），并把"这个机制为什么存在"写进那个机制所在项目的 DDD。
- **被合并**：B3。

**B7 合并整理阀：10-30 已约定，这次把它建出来。**

- **触发**：`prompt_metrics` 记录到某个每轮注入文件的 token 数，达到它上次合并后体量的 1.25 倍。这是一个触发器，触发后照常继续，不截断任何东西。1.25 倍按现在的增速大约是几天的量，每次合并的成本大约是一次会话模型读完这份文件。
- **动作**：CDF worker 排一个任务，在串行执行器和内存门控下跑，不和聊天抢资源。用会话本身的模型，把整份文件放进上下文，**只输出类别层面的声明**：`merges`、`same`、`closes`。它不做 `overrides`，也就是不重新判断哪条已经不成立了，只把同一类的条目合并成一条更密的教训。这和 DDD"进来时就定"的原则不冲突：合并不改变任何条目真不真，只改它们的写法。
- **核对**：代码按 B2、B3 的规则核对每条声明。合并后新条目的来源，继承被合并条目的来源：每条都是用户原话或测量时，新条目留在每轮注入的文件里；否则按 K1 规则进 General Brain。
- **合并不动时**：如果 agent 判断现有的每一类都是独立的、都在起作用，就报告"N 类，都在用"，并把基线更新为当前体量。真实的增长被接受，并在 Health 里可见。这和 P6 一致：到了警戒线，如果每一项都在承重，就抬高警戒线，而不是砍掉有用的东西。
- 旧的手写条目（没有 `cand:` 标记，MEMORY 和 EVOLUTION 都归 agent 所有，AGENT R21）也可以被合并。原文逐字搬进对应的 archive 分片（`cognition find --in evolution|memory` 会读所有分片），合并前先备份。

**B8 不变量（替代上限）**：新增 C11 "每轮注入的文件按'类'增长"：7 天内写进 MEMORY / EVOLUTION 的单元里，声明了 `same` 或 `merges`、点名的是**当前有效**条目、却作为新条目落地的数量必须为 0。点名已关闭条目而重新写入的属于 B6 的复发，不算违规。CDF Health 同时显示每个文件 4 周的 token 曲线，以及每周"新增类别数 / 合并数 / 离开数"。

**增长上界（如实说）**：每轮注入的体量 ≈ 当前有效的判断类别数 × 每条教训的长度。

- 同一类错再犯只加强或改写那一条（B1、B4）；
- 类别会因为升级、修复、合并而离开（B6、B3）；
- 写法变散时由合并阀收紧（B7）；
- 只在单个项目里成立的细节不进每轮注入的文件（B1）。

剩下的增长只有一个来源：**真正新的判断错误类别**。这不是一个硬上限，也不该有硬上限，因为硬上限意味着砍掉还在承重的教训。但它把增长和北极星绑在了一起：如果新的错误类别一直在出现，那是北极星本身在变差，并且在 Health 曲线上看得见，而不是藏在一份越来越长的文件里。

### A. 知识到达判断：三级漏斗（治 R4）

| 级 | 含义 | 记为 | 来源 |
|---|---|---|---|
| 写入 | CDF 写进主文件 | `ingestion_writes` | 已有 |
| 送到 | 放到了 agent 面前 | `recall_injected` 或 `read_by_agent` | 每轮注入的文件（按定义每轮都送到）；自动召回、`[DDD:]` 块、`cognition find`（已有）；Read、Grep、`cognition get`（已有）；**Bash 输出里出现的完整单元**（新，A1） |
| 用上 | 它影响了一个决定 | `cited_as_evidence` | **S7 的会话级 `used`**（新，A2）；**pipeline 的 `knowledge_refs`**（新，A3） |

**A1 Bash 也要看到。** 用量观察器的 matcher 加上 Bash。钩子本身只做一件便宜的事：命令里有没有一个 token 指向受管文件。判断方法是按 cwd，以及命令开头的 `cd <目录>` 去解析，看能不能落到 `Projects/*/`、`Knowledge/` 下面。没有就直接返回；有就交给 io 线程池。

线程池里：对这些文件，stdout 里**完整出现**的单元记 `recall_injected`，`grep -n` 形式的 `路径:行号:` 行按行号对应到单元，也记 `recall_injected`。Bash 的输出最多 30000 字符（实测），"是不是整份"判断不了，所以 Bash 一律只记"送到"，不区分整份和片段。实测 721KB 的输出扫一遍大约 40ms，在线程池里跑，不在聊天路径上。

Read 是否整份读取，改为按 `tool_response.file` 的 `startLine`、`numLines`、`totalLines` 判断，不再按"没给 limit"判断。漏斗里两者都算"送到"。

**A2 "用上"由带上下文的 agent 从一份代码给的清单里选。**

- S7 第一轮加一个**会话级**字段 `used`。会话没有产出任何单元时也能填。
- 代码给 S7 一份清单：本会话在 `unit_usage` 里有"送到"记录的条目。只列按需读取的存储（DDD、Knowledge、General Brain、TIMELINE 事件），带 id 和首行。每轮注入的条目不列，见下面"每轮注入的文件怎么算用上"。
- S7 从清单里选出真正影响了某个决定的条目，代码只核对选中的 id 确实在清单里，然后记 `cited_as_evidence`。
- 清单以外的 id 一律丢弃。这样复盘没办法把没见过的条目说成用过。
- 实现前先确认：观察器记录用的会话 id（`app_session_id`）和 S7 复盘的会话 id 是同一个。不是的话，先修这个对应关系，再接 A2。

**A3 pipeline 的引用。** 复用 Brain Eval 已有的 `knowledge_refs` 统计（`brain_eval.py:195-210`）：把 8 位 id 解析成条目 anchor，写入 `cited_as_evidence`，不另起一套。注意：`knowledge_refs` 接受的是本次召回的 id **或**本项目 DDD 里的任何条目（`engine.py:2682-2706`），所以它算"用上"，不一定算"送到"。

**每轮注入的文件怎么算"用上"。** 每轮都送到，问"有没有打开"没有意义；它们有没有用，看的是结果：这一类错**有没有再犯**。

- 一条教训写进去之后没有再犯，就是守住了；
- 再犯了，就是"送到了还错"。这正是月度错误倒查的第三环，现在每次重犯都会自动归到这一环。它对应的杠杆不是"再写一遍"，而是升级成规则或机制（B6）。

按需读取的条目重犯时，代码查这个会话有没有"送到"记录：没有就归到第二环（没送到），杠杆是修召回。

**A4 两个检查。**

- **C10 保留**原来的结果检查："满 14 天的按需条目里，至少有一条被用上"。依据改为 `cited_as_evidence`。
- **新增 C12 "仪器看得到每一扇门"**：过去 7 天有会话的前提下，"送到"的每个来源（召回、Read / Grep / get、Bash）和"用上"的每个来源（S7 `used`、`knowledge_refs`）各至少有一条记录，否则判失败，并指出是哪一扇门。这个检查判断的是测量本身有没有坏，像现在 Bash 读取看不到，就会判失败。
- 比例不设通过线：北极星的详细输出按"DDD / Knowledge / TIMELINE"显示满 14 天条目的送到率和用上率，没满的显示"目前为止"并注明未到期；再加一行"重犯 k 次：教训当时在面前 j 次，不在 k−j 次"。通过线等有 4 周数据再定（P6：先有数，再定标准）。

## 4. 性能

| 路径 | 变化 |
|---|---|
| 聊天每轮 | 只多一个 PostToolUse 过滤（对 Bash 命令做 token 解析，判断有没有指向受管文件，微秒级）。匹配在 io 线程池，单元位置按 路径 + mtime + 大小 缓存。不新增模型调用。 |
| 每轮 prompt | 第一次合并（§5）之后，EVOLUTION / MEMORY 变小；之后按"类"增长。首 token 时间和缓存读取成本只会下降。 |
| 会后复盘 | 第一轮多一个 `used` 字段，第二轮可能多一个 `merges` 声明，都是输出里多几十个 token，不多一次调用。 |
| 合并阀 | 只在触发时跑一次，走 CDF worker 的串行执行器和内存门控。 |

## 5. 第一次合并（迁移就是合并阀的第一次运行）

不另写迁移脚本。B7 建好之后，手动触发一次，用的是同一套规则：

- **EVOLUTION**：`CLASS B` 等旧手写块，以及 CDF 时代同一类的条目，合并成按类别写的教训，原文逐字进 archive 分片。`Governance Candidates` 里已升级规则的说明是历史，搬进 archive。只在 SwarmAI 里成立的细节，进 SwarmAI DDD 的 IMPROVEMENT。
- **MEMORY**：长篇 COE 叙述合并成一条教训，完整复盘作为文件放进 `Knowledge/Archives/`，条目里写指向它的路径。
- **安全**：先备份 `.context/` 和 `ingestion.db`，确认备份能打开、内容完整，再运行。
- **核对**：迁移前出现过的每个 C / K 编号，迁移后在主文件、archive 分片或 DDD 里能找到；搬走的原文和备份逐字一致；记下前后的 token 数。

## 6. 北极星怎么因此变好

- **重犯**：一类错一条，犯了几次写在条目上，第三次犯的时候看到的是一条写着"犯过 3 次"的教训；每次重犯自动归到"没送到"（修召回）或"送到了还错"（升级成规则或机制）。
- **纠正**：每轮注入的内容更少、更密，每条都是跨项目成立的判断，注意力不被单个项目的细节和重复条目稀释。
- **错误来源**：第二环和第三环每天可量，月度倒查从"推断"变成"核对"。
- **CDF 自己**：写了却从没送到、从没用上的目的地会直接显示出来（比如 DDD 4 天写入 1531 条、召回 90 条），之后调整 CDF 写多少、写到哪，有数可依。

## 7. 否决的方案

| 方案 | 为什么不做 |
|---|---|

## 9. 步骤与验证计划

读取方先于写入方。每一步先写会失败的测试，再实现，用 `scripts.mutation_check` 确认回退修复后测试会变红，然后提交。

|---|---|---|
| 1 | 读取方：北极星和 health 读漏斗、C10 新依据、C11、C12；先确认观察器和 S7 的会话 id 对得上 | correctness |

| 8 | 收尾：最终不变量一次跑完；build；部署和重启需 XG 批准（AGENT R12） | — |

**最终不变量**（收尾跑一次，每条做 mutation check）：

- **J1**：一条声明 `repeats` 的纠正，不管最后是新增、加强、合并还是被拒，`read_corrections` 都数到这一次。
- **J2**：MEMORY、EVOLUTION、General Brain 里由 CDF 写入的条目可以被 `overrides` 和 `merges` 点名，人手写的不行（`human_written`）。
- **J3**：一个 `merged` 条目之后被重述或点名时，解析到它的 head 并加强 head，不被拒收；一个 `overridden` 条目被重述时，仍然被拒收。
- **J4**：加强一条条目只改变它注释里的次数，不改变它的 id；每轮注入渲染出"犯过 N 次"。
- **J5**：以 `closed` 离开的条目，之后又犯时会重新写入，不被拒收。
- **J6**：合并阀在体量达到上次合并后的 1.25 倍时排一次任务，不截断任何东西；它的输出里只要出现 `overrides` 就整体拒收；合并后条目的来源继承规则成立。
- **J7**：Bash stdout 含受管文件的完整单元时记 `recall_injected`，命令不涉及受管文件时什么都不记，钩子在交给线程池之前就返回。
- **J8**：`used` 里不在会话清单里的 id 不被记录；在清单里的记 `cited_as_evidence`。
- **J9**：C11 在"点名当前有效条目却作为新条目落地"时失败，点名已关闭条目而重新写入时不失败；C12 在任何一扇门 7 天没有记录时失败，并指出是哪一扇门。
- **J10**：第一次合并后，迁移前出现过的每个 C / K 编号都能找到；搬走的原文和备份逐字一致。
- **J11**：聊天路径没有新增模型调用（静态检查钩子代码）；钩子过滤耗时实测。
